## User Constraints (from CONTEXT.md)

### Locked Decisions

### Authority and provenance

- `InventoryReadPort` remains the only resource identity authority.
- The API derives and enforces effective scope before any native Fabric IQ or
  Data Agent call.
- Native Fabric IQ results are enrichment evidence only and always carry
  exact native provenance, freshness, authorization, ontology/product
  generation, and bounded citation references.
- The existing OneLake ontology projection remains a separately named
  fallback and must never be labeled as native Fabric IQ.
- Deterministic findings remain available and authoritative when native
  services are disabled, empty, denied, slow, malformed, stale, or unavailable.

### Initial native use cases

- Start with topology/blast-radius traversal and policy/governance context.
- Do not enable every specialist or page at once.
- Native answers must cite stable ontology entities/relationships or curated
  Gold evidence visible within the caller's authorized scope.
- Unsupported or conflicting native evidence is qualified or rejected; it
  never silently overrides inventory identity or deterministic checks.

### Authentication and secrets

- Use managed identity and supported token exchange/delegation patterns.
- Do not commit, log, persist, or expose delegated access tokens.
- No browser-provided token becomes backend authority.
- Native Fabric IQ, Data Agent, Foundry, and OneLake identities remain
  distinguishable in audit and telemetry.

### Rollout and measurement

- Rollout is default-off, then shadow, then bounded canary, then explicitly
  approved enablement.
- A kill switch returns immediately to deterministic plus
  OneLake-projection fallback without deleting Fabric data, ontology, Gold,
  evaluation, or audit history.
- Measure native-call rate, successful/empty/denied/unavailable outcomes,
  latency, citation validity, scope violations blocked, fallback rate, cost,
  and answer-quality lift over the existing baseline.
- No promotion occurs without passing deterministic security/contract tests,
  an offline reference set, live canary evidence, and human review of
  disagreements.

### the agent's Discretion

- Exact native Fabric IQ REST/SDK client shape and internal interface names,
  provided first-party supported APIs are used.
- Exact evaluation sample size and thresholds, provided they are explicit,
  statistically interpretable, and compare the same questions/evidence across
  deterministic, OneLake-projection, and native arms.
- Whether Data Agent grounding is enabled in the same canary or a second
  canary step, provided native traversal is independently observable.

### Deferred Ideas (OUT OF SCOPE)

- Native Fabric IQ use for every specialist and every page.
- Autonomous relationship acceptance or production remediation.
- Replacing local orchestration, approval, evidence ledger, or deterministic
  policy checks with a managed agent.
- New Fabric ingestion or page-specific snapshot publication.
- Changes to the independent Phase 03.1 closeout evidence gates.

## Summary

Microsoft now documents a native Fabric IQ ontology surface as a streamable MCP endpoint with the pattern `https://{host}/v1/mcp/dataPlane/workspaces/{workspaceId}/items/{itemId}/ontologyEndpoint`; the supported Foundry integration is the preview `fabric_iq_preview` tool, preferably curated in a versioned toolbox. Ontology requests are translated by NL2Ontology into structured ontology queries and routed to the applicable Fabric engine, including GQL for Graph in Fabric and KQL for Eventhouse. The feature remains public preview, has no SLA recommendation for production workloads, requires published Fabric items, and has item-specific region, licensing, network, and authorization constraints. [CITED: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq] [CITED: https://learn.microsoft.com/en-us/fabric/iq/ontology/overview]

The supported authentication surfaces are not interchangeable. Ontology access through Fabric IQ uses delegated Microsoft Entra OBO via a BYO Entra application or managed OAuth connection; Microsoft documents direct application-only bearer support only for the published Data Agent MCP endpoint. The Data Agent endpoint accepts a user or service-principal token scoped to `https://api.fabric.microsoft.com/.default`, exposes one discovered MCP tool, and requires `initialize` → `tools/list` → `tools/call`; long-running calls can return `tasks/get`/`tasks/cancel` work. [CITED: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq] [CITED: https://learn.microsoft.com/en-us/fabric/data-science/data-agent-mcp-server]

The repository is not yet native. Its runtime explicitly calls `runtime.service.ontology_query(...)` over the local OneLake projection and stamps `"onelake-ontology-projection"`; the Gold client stores a delegated token in `GoldGroundingScope` and posts `tools/call` synchronously without MCP initialization or discovery. [VERIFIED: src/api/runtime.py:2633-2677; src/operations/gold_grounding_specialist.py:22-141; src/fabric/gold_grounding_client.py:1-59] The smallest safe implementation is therefore a default-off, one-seed native tracer behind a new port, with a live schema/auth checkpoint before any result can be stamped `"fabric-iq"` or displayed.

**Primary recommendation:** Provision one version-pinned Fabric IQ ontology toolbox/connection with delegated OBO, drive one inventory-resolved topology seed through a strict native-result adapter, retain the existing projection as a separate fallback, and do not promote beyond default-off until the live endpoint proves stable IDs, path direction, citations, generation/freshness, and scope-safe replay.

### Pattern 1: Authority Before Enrichment

**What:** Authenticate, derive effective scope, resolve the seed through inventory, and compute deterministic findings before any optional native call.  
**When to use:** Every topology, relationship, blast-radius, policy-context, and Gold-grounding request.  
**Why:** The repository already derives `ReadScope` before the handler and its inventory port refuses calls without a server-derived scope. [VERIFIED: src/api/dependencies.py:219-283; src/intelligence/inventory/read_port.py:10-50]

### Pattern 2: Atomic Provider Admission

**What:** Validate a complete provider envelope in this order: schema → operation/predicate/hop/result limits → scope fingerprint → every node/edge/citation through inventory → generation/freshness → citation closure/replay → policy-authority invariance. Reject the whole provider result on any failure.  
**When to use:** Before provider evidence enters a prompt, response, cache, metric detail, or ledger.  
**Why:** Post-filtering only nodes can leak path shape, counts, relationships, and diagnostics; the AI-SPEC requires zero such leakage. [VERIFIED: .planning/phases/03.8-native-fabric-iq-adoption/03.8-AI-SPEC.md:780-899]

### Pattern 3: Separately Named Providers

The allowed exact provenance values are quoted verbatim as `"fabric-iq"`, `"fabric-data-agent-gold"`, and `"onelake-ontology-projection"`. [VERIFIED: .planning/phases/03.8-native-fabric-iq-adoption/03.8-AI-SPEC.md:400-520] Never merge them into one “Fabric” result.

### Pattern 4: Request-Scoped Credentials

**Ontology:** a validated caller assertion is exchanged server-side through supported OBO/managed OAuth; the resulting handle exists only for the request and never determines local scope. [CITED: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq]  
**Data Agent:** the app UAI obtains a short-lived Fabric token immediately before the MCP session; token and `Authorization` header stay in memory and are discarded when the session closes. Direct managed-identity acceptance must be proven in the live workspace because the Data Agent page explicitly names user/service-principal tokens, while managed identity is a service-principal form. ## Common Pitfalls

### Pitfall 1: Preview Capability Is Mistaken for a Production Contract

**What goes wrong:** a working preview call is promoted without an SLA, stable payload contract, or rollback evidence.  
**Why it happens:** the official surface now exists, but preview limitations and constrained capabilities remain. [CITED: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq]  
**How to avoid:** pin connection/toolbox/agent versions, validate payload shape locally, keep default-off, and require repeated live evidence.  
**Warning signs:** undocumented fields become required, toolbox updates alter output, or generation/citations disappear.

### Pitfall 2: OBO Becomes a Confused Deputy

**What goes wrong:** a valid user assertion accesses Fabric data beyond local AIOps grants, or a cached delegated result crosses principals.  
**Why it happens:** Fabric permissions and local AIOps scope are separate authorization systems.  
**How to avoid:** local effective scope remains authoritative; bind delegation and cache keys to principal plus scope fingerprint; post-resolve every identity.  
**Warning signs:** Fabric returns data the local inventory cannot resolve, or identical cache entries serve different principals.

### Pitfall 3: MCP Handshake and Task Semantics Are Incomplete

**What goes wrong:** direct `tools/call` fails, a changed tool argument breaks production, or abandoned long-running work consumes capacity.  
**Why it happens:** the current client skips initialization/discovery and has no task cancellation. [VERIFIED: src/fabric/gold_grounding_client.py:17-59]  
**How to avoid:** implement documented handshake, discovery, task polling, deadline, and best-effort cancellation. [CITED: https://learn.microsoft.com/en-us/fabric/data-science/data-agent-mcp-server]  
**Warning signs:** 400/404 responses, hard-coded tool names, orphaned task IDs, or work continuing after caller cancellation.

### Pitfall 4: Graph Completeness Is Overstated

**What goes wrong:** bounded results are described as the complete blast radius.  
**Why it happens:** cycles, high-degree nodes, hop limits, stale refresh, and truncation are hidden by narration.  
**How to avoid:** include exact hop/result limits, totals when trustworthy, truncation/partial status, omitted reason, and generation/freshness.  
**Warning signs:** “all affected” language with no coverage metadata.

### Pitfall 5: Audit Persistence Is Best-Effort

**What goes wrong:** native output is displayed while the durable ledger write fails.  
**Why it happens:** the current ledger store logs persistence failures but still serves the in-memory result. [VERIFIED: src/operations/autonomous_investigation.py:1100-1145]  
**How to avoid:** for shadow/canary native display, treat missing durable audit as a display-blocking critical failure and return deterministic-only output.  
**Warning signs:** in-memory ledger exists with no OneLake document or audit-completeness metric below 100%.

### Pitfall 6: Dependency Work Is Quietly Waived

**What goes wrong:** Phase 03.8 edits orchestration, inventory, or ontology seams while their prerequisite phases are incomplete.  
**Why it happens:** local code appears present even though deployment/verification gates are open.  
**How to avoid:** make the first executable task a hard dependency preflight. Current evidence says Phase 03.7 is `0/12` executed, Phase 11 has 16 unchecked plans and no verification artifact, and Phase 13 is `19/22` with deployed acceptance blocked. [VERIFIED: .planning/ROADMAP.md:210-257,794-850,857-901; .planning/phases/13-autonomous-ontology-discovery-and-fabric-synchronization/13-VERIFICATION.md:1-45]

async def admitted_native_result(raw, *, scope, inventory, expected_scope_fingerprint):
    result = NativeResult.model_validate(raw)
    if result.scope_fingerprint != expected_scope_fingerprint:
        raise PermissionError("scope fingerprint mismatch")
    for fact in result.facts:
        if inventory.get_resource(scope, fact.subject_id) is None:
            raise PermissionError("subject outside inventory authority")
        if inventory.get_resource(scope, fact.object_id) is None:
            raise PermissionError("object outside inventory authority")

    validate_generation_and_freshness(result)
    return result

## Security Domain

### Applicable ASVS Categories

| ASVS category | Applies | Standard control |
|---|---:|---|
| V2 Authentication | yes | Existing Entra/gateway validation; separate request-scoped OBO and workload credentials; no provider token becomes local authority. [VERIFIED: src/api/auth.py:28-279] |
| V3 Session Management | yes | Bind OAuth/MCP session and any task ID to principal, scope fingerprint, provider, expiry, and request; destroy headers/tokens at session end. |
| V4 Access Control | yes | `Authorizer.effective_scope` before provider access and `InventoryReadPort` resolution before and after traversal. [VERIFIED: src/api/rbac.py:205-240; src/intelligence/inventory/read_port.py:10-50] |
| V5 Input Validation | yes | Strict Pydantic envelope, closed operation/predicate allowlists, bounded hops/results, URL/ID validation, and atomic rejection. |
| V6 Cryptography | yes | Azure Identity and Entra OBO; never implement token signing, refresh, encryption, or key storage locally. [CITED: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/fabric-iq] |
| V7 Error Handling and Logging | yes | Enumerated token-free outcomes, bounded reason text, secret scans, correlation IDs, and no raw provider payloads. Existing Gold metrics already truncate degraded reasons to 40 characters. [VERIFIED: src/operations/gold_grounding_metrics.py:29-40] |

### Known Threat Patterns

| Pattern | STRIDE | Standard mitigation |
|---|---|---|
| OBO confused deputy / scope widening | Elevation of privilege, information disclosure | Local scope remains authoritative; request-scoped exchange; pre/post inventory checks; no cross-principal cache. |
| Cross-scope relationship, aggregate, or path-shape leak | Information disclosure | Reject whole result if any endpoint/citation/diagnostic cannot be authorized; exact adversarial tests. |
| Token or client-secret leakage through prompts, traces, exceptions, ledgers, Terraform, or eval artifacts | Information disclosure | Credential-free models, in-memory headers, structured redaction, secret-pattern tests, and immediate kill switch. |
| Native text reverses deterministic policy or identity | Tampering | Byte-level deterministic invariance checks and explicit `identity_authority=false`; reject unsupported authority claims. |
| User/native prompt injection changes tools or scope | Tampering, elevation of privilege | Treat provider/user text as untrusted data, deterministic tool/argument allowlists, no mutation tools, strict output schema. |
| Endpoint/config SSRF | Spoofing, information disclosure | Build hosts from closed official Fabric/Foundry patterns and validated GUIDs; do not accept arbitrary request URLs. |
| Retry/task amplification and cost exhaustion | Denial of service | Independent deadlines, retry allowlist, task cancellation, circuit breaker, stage percentages, per-turn/daily cost gates. |
| Stale/mixed-generation replay | Tampering | Generation-pinned cache/eval keys, freshness validation, citation replay, and mixed-generation rejection. |
| Audit write failure hidden by in-memory success | Repudiation | Block native display when durable audit fails; deterministic-only response and critical alert. |
