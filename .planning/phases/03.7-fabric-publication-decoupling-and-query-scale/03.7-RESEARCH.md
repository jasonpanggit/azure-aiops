## User Constraints (from CONTEXT.md)

### Locked Decisions

### Publication boundary

- Fabric publication consumes versioned domain products; it does not own the
  business logic that computes every domain product.
- A publication transaction contains only products that require one atomic
  visibility boundary. Unrelated domains may advance independently with their
  own manifests, validation, watermarks, and active pointers.
- Domain projectors own incremental/full-rebuild decisions and emit immutable
  product manifests containing schema version, source generation, row counts,
  hashes, quality status, lineage, and compatibility metadata.
- The publisher validates supplied product manifests, writes or stages the
  declared tables, and conditionally promotes the corresponding pointer. It
  does not create page-specific tables or execute UI composition logic.
- Exposure Gold and ontology keep their existing generation-level consistency
  and rollback guarantees.

### Production read path

- Production health and API requests read published Fabric products through
  explicit domain read ports or bounded status projections.
- `InventoryDatasetMapper.load()` is an ingestion/projection concern and must
  not run in production request or health-probe paths.
- Health probes read compact publication/source-status state and never rebuild
  semantic, network, vulnerability, or inventory models.
- Compatibility generation remapping may remain only behind explicit
  local/test/rollback configuration with telemetry identifying its use.

### Inventory query scale

- Inventory read operations require server-derived scope before query
  compilation.
- Scope, family, resource type, stable ordering, count, and cursor/offset
  pagination are pushed into one Fabric-backed query adapter.
- The read port returns the same consumer-safe projection and per-family
  availability contract regardless of SQL or bounded local/test adapter.
- No implementation may fetch a fixed maximum set and then filter or paginate
  it as though it represented the complete authorized estate.
- Single-resource lookup remains indistinguishable for absent and out-of-scope
  resources.

### Compatibility and rollout

- Preserve current API response contracts unless an explicit versioned
  migration is planned.
- Introduce shadow comparison between legacy and new readers before cutover.
- Rollback selects the prior reader/product pointer without deleting source
  observations, product history, ontology generations, or audit evidence.
- Compatibility aliases may remain temporarily, but production must not write
  duplicate logical and physical copies unless a named consumer still requires
  them and telemetry proves their use.

## Summary

The three issues are coupled by one missing boundary: the repository has durable generation and pointer machinery, but production projection, publication, and serving are not consistently separated by domain. `FabricSyncService._sync_locked()` currently maps a source snapshot, builds workload and temporal/container Exposure products, runs change, predictive, and incident pipelines, synchronizes ontology, validates, writes the broad table set, publishes ontology, stages Exposure Gold, writes completion state, and only then activates the Exposure pointer. [VERIFIED: src/fabric/sync_service.py:482-618,621-810,901-1180] A deterministic local fixture currently reports **71 published tables** and about **0.69 seconds** for one run; this is an illustrative code-path baseline, not a deployed SLO. [VERIFIED: local fixture measurement using `tests/test_fabric_sync_service.py::_service`, 2026-09-13]

The smallest safe migration is not a rewrite. Preserve `DatasetStore` immutable source generations, the Phase 13 fenced/CAS ontology pointer, and the existing Exposure Gold stage/activate pointer. Add one narrow `DomainProductManifest`/publisher seam, lead with an inventory product tracer, then move the remaining projector calls outside the publisher boundary. In parallel, route production readers through already-published products: `/health` and `/ready` must be status-only, while semantic/network/vulnerability providers continue to use last-known-good objects rebuilt only by the background refresher. `_load_snapshot_tables()` remains callable only in explicit local/test/rollback mode and emits compatibility-use telemetry. [VERIFIED: src/storage/datasets.py:40-180,189-335] [VERIFIED: src/ontology_discovery/publisher.py:59-255,363-428] [VERIFIED: src/fabric_pipelines/vulnerability_pipeline.py:218-430] [VERIFIED: src/api/providers.py:98-180,320-340]

For MED-13, make `InventoryReadPort` depend on an `InventoryQueryAdapter`, not on a fully materialized `InventoryService`. The production adapter should compile one generation-pinned, scope-first SQL relation over OS and non-VM/Arc resource observations, run a filtered `COUNT_BIG`, and fetch only the requested stable page. Use the current offset envelope for API compatibility, ordered by `(family, resource_id)`; use direct scope-qualified SQL for single lookup and distinct containment SQL for graph ingestion. The local/test adapter may materialize a configured maximum only if it returns explicit incomplete coverage rather than an apparently complete total. [VERIFIED: src/intelligence/inventory/read_port.py:15-61] [VERIFIED: src/api/dependencies.py:291-312] [VERIFIED: src/api/exposure_query.py:738-862,866-955]

**Primary recommendation:** Build a production tracer in which one combined inventory source generation emits one immutable five-table inventory product manifest, only that product is staged/promoted, and `/api/v1/inventory/resources` reads a generation-pinned SQL page without invoking `InventoryDatasetMapper`; then expand the same publisher contract to the existing ontology and Exposure atomic groups.

## Current-State Findings

### 1. Central publication is a projection orchestrator and publisher

`FabricSyncService.sync()` acquires the OneLake synchronization lock before entering `_sync_locked()`, so snapshot mapping and every projector run while the publication lock is held. [VERIFIED: src/fabric/sync_service.py:453-480] Inside that boundary, `InventoryDatasetMapper.load()` creates Bronze/Silver/ontology datasets, workload and Exposure tables are added, change/predictive/incident pipelines append ontology rows, the complete set is validated, and the resulting tables are written in parallel. [VERIFIED: src/fabric/sync_service.py:532-618,621-810,901-986]

The exact central calls that must move out of the publisher are:

- `"datasets = self.mapper.load(snapshot, run_id, fs=self._source_fs)"`; [VERIFIED: src/fabric/sync_service.py:532-540]
- `"workload_products = self._load_workload_products(snapshot)"`; [VERIFIED: src/fabric/sync_service.py:560-576]
- `"temporal = materialize_temporal_exposure_tables(...)"` and `"container_tables = materialize_container_exposure_tables(...)"`; [VERIFIED: src/fabric/sync_service.py:577-654]
- `"change_pipeline_result = change_pipeline.run(...)"`, `"predictive_pipeline_result = predictive_pipeline.run(...)"`, and `"incident_pipeline_result = incident_pipeline.run(...)"`; [VERIFIED: src/fabric/sync_service.py:745-765]
- `"datasets = self._synchronize_ontology(...)"`. [VERIFIED: src/fabric/sync_service.py:766-810]

`run_inventory_refresh_all_connections()` also makes the duplication explicit: after publishing the inventory-owned Fabric tables, it invokes the full `FabricSyncService.sync()` because the current complete lakehouse expects both table families. [VERIFIED: src/api/inventory_orchestration.py:104-167]

### 2. Request/health compatibility mapping is expensive and incompletely isolated

`_load_snapshot_tables()` lists every connection, resolves each active generation once, reads its manifest, and calls `_load_generation_tables()`, which invokes `InventoryDatasetMapper.load()`. The cache literal is quoted verbatim: `"_SNAPSHOT_TABLES_CACHE_TTL_SECONDS = 30"`. [VERIFIED: src/api/runtime.py:561-572,674-817] The mapper itself reads graph-shaped files, builds ontology entities/relationships, and returns a broad medallion/ontology dataset map. [VERIFIED: src/fabric/dataset_mapper.py:1699-1766,1767-1969]

Production configuration is already `"AIOPS_RUNTIME_MODE" = "production"` with `"AIOPS_ENABLE_FABRIC"` controlled at deployment, and the Fabric provider branch reads published Fabric snapshots rather than `_load_snapshot_tables()`. [VERIFIED: infra/terraform/container_apps.tf:235-275] However, the compatibility loader remains reachable through non-Fabric/demo branches, and the phase context records that deployed health/legacy providers still exercise it. The migration must therefore enforce the boundary in code and configuration rather than assuming every environment always enters the intended branch. [VERIFIED: src/api/runtime.py:3009-3149] [VERIFIED: .planning/phases/03.7-fabric-publication-decoupling-and-query-scale/03.7-CONTEXT.md:49-58]

There is an additional probe bug worth including in MED-12: `/health` uses `health(refresh=False)`, but `/ready` calls `refresh(blocking=False)`. If the refresh lock is free and the interval is due, `blocking=False` still acquires the lock and executes every loader synchronously; it only skips work when another refresh already owns the lock. [VERIFIED: src/api/app.py:463-504] [VERIFIED: src/api/providers.py:141-180] The fix is for both probes to read the last completed state only; the startup/background thread and authenticated manual refresh endpoint remain the only refresh initiators. [VERIFIED: src/api/app.py:157-199,506-517]

### 3. Inventory correctness stops at the pre-pagination ceiling

The current implementation is exactly:

```python
result = self.service.resources(scope, offset=0, limit=10_000)
rows = list(result["data"]["resources"])
# family/type filtering follows
return {
    "resources": rows[offset : offset + limit],
    "total": len(rows),
}
```

[VERIFIED: src/intelligence/inventory/read_port.py:15-42]

`get_resource()` and `list_containment()` repeat the same `limit=10_000` walk. [VERIFIED: src/intelligence/inventory/read_port.py:44-86] A measured fake-service baseline with 10,000 materialized rows and request `offset=10_000, limit=100` returned `0` rows and reported `total=10000`, proving that the present contract cannot represent a larger authorized estate. [VERIFIED: local baseline command against `InventoryReadPort`, 2026-09-13]

The ceiling is also embedded in identity consumers: `InventoryReadAdapter.resources()` and onboarding `_identity_rows_from_inventory()` each request `limit=10_000`. [VERIFIED: src/onboarding/inventory_read_adapter.py:73-86] [VERIFIED: src/onboarding/ingestion_service.py:793-806] These call sites must migrate with the port; otherwise the new SQL adapter would be correct while graph ingestion silently remained truncated.

### Pattern 1: Domain Product Manifest Is Not Either Existing “Manifest”

There are already two different manifest concepts: `DatasetStore` generation `manifest.json` records source generation datasets/hashes, while `PublicationManifestStore` records ontology projection disposition only. The latter explicitly says it is distinct and is an in-memory lifecycle registry. [VERIFIED: src/storage/datasets.py:396-449] [VERIFIED: src/ontology/publication_manifest.py:1-55,88-122] Do not extend either with domain-product transaction semantics; introduce a clearly named contract such as `DomainProductManifest`. [ASSUMED interface name]

Recommended internal shape:

```python
# Proposed internal contract; names are [ASSUMED], required field semantics are locked.
@dataclass(frozen=True)
class DomainProductManifest:
    product_id: str
    product_generation_id: str
    atomic_group_id: str
    manifest_schema_version: str
    product_schema_version: str
    source_generations: tuple[str, ...]
    tables: tuple[ProductTableManifest, ...]
    quality: ProductQuality
    lineage: Mapping[str, Any]
    compatibility: Mapping[str, Any]
    content_hash: str
```

The required semantics—schema version, source generation, row counts, hashes, quality status, lineage, and compatibility metadata—come directly from the locked context. [VERIFIED: .planning/phases/03.7-fabric-publication-decoupling-and-query-scale/03.7-CONTEXT.md:35-45]

Each table entry should declare logical contract name, physical table, row count, content hash, schema hash/version, write mode, and generation partition column. The publisher must reject undeclared tables, duplicate logical names, row-count/hash mismatch, failed quality, incompatible consumers, or a product ID/atomic-group mismatch. [ASSUMED interface details; required behavior derives from locked context]

### Pattern 2: Stage, Verify, Then CAS One Product Pointer

Use the existing Phase 13 sequence: authorize publisher, assert predecessor pointer, validate candidate, stage immutable artifacts with the completeness manifest last, verify persisted content, persist audit, recheck mutable facts, conditionally promote, run post-checks, and roll back to the predecessor with a newer fence if necessary. [VERIFIED: src/ontology_discovery/publisher.py:80-255,363-428] The exact current pointer fields are quoted verbatim: `"active_generation"`, `"prior_generation"`, `"source_generation"`, `"owner_id"`, `"fence"`, and `"compatibility_alias_version"`. [VERIFIED: src/storage/datasets.py:48-105]

The generic publisher API should be product-scoped:


Do not hold the publisher lease while computing unrelated products. Acquire the product-specific lease immediately before pointer precondition checks/staging, and release it after promotion or failed rollback handling. ### Pattern 4: Scope-First Inventory SQL

Follow the existing Exposure compiler:

1. Validate that the caller supplied a server-derived effective scope. [VERIFIED: src/api/exposure_query.py:582-620]
2. Capture one active inventory product generation before compiling any query. [VERIFIED pattern: src/api/exposure_query.py:681-737]
3. Build a canonical union of OS and PaaS rows, with VM/Arc represented only by OS rows because PaaS normalization explicitly excludes `"microsoft.compute/virtualmachines"` and `"microsoft.hybridcompute/machines"`. [VERIFIED: src/intelligence/inventory/normalization.py:317-343]
4. Add every supported scope predicate before family/type filters; if a requested scope dimension is not represented by the product, compile an unsatisfiable predicate rather than silently ignoring it. This preserves current fail-closed `Scope.matches()` behavior. [VERIFIED: src/api/scope.py:69-127] [ASSUMED SQL implementation]
5. Use bound values and allowlisted/bracketed identifiers. [VERIFIED: src/fabric/sql_endpoint.py:88-104,243-276]
6. Run a filtered count and a bounded page query ordered by `family ASC, resource_id ASC`; preserve the existing offset envelope. [VERIFIED current order: src/intelligence/inventory/read_port.py:36-42] [VERIFIED current envelope: src/api/dependencies.py:291-312]
7. Parse `provider_payload_json` and `tags_json` only for returned PaaS rows so the consumer-safe projection remains byte-compatible, including lossless `properties` and `tags`. [VERIFIED: src/intelligence/inventory/models.py:215-288]

## Common Pitfalls

### Pitfall 1: “Refactor” leaves the same giant critical section
**What goes wrong:** Projectors move to helper classes but still run after the publisher lock is acquired.  
**Why it happens:** File/module boundaries are mistaken for transaction boundaries.  
**How to avoid:** Test that an inventory product publish receives already-computed rows/manifest and monkeypatch every unrelated projector to raise if invoked.  
**Warning signs:** Publication duration still includes change/predictive/incident spans, or inventory table count stays near the 71-table fixture baseline.  
[VERIFIED current critical section: src/fabric/sync_service.py:453-540,745-810]

### Pitfall 2: Product pointer exists, but SQL reads mutable current rows
**What goes wrong:** A CAS document names generation B while SQL pages can still see mixed or restored current-table rows.  
**Why it happens:** The pointer is not part of the query predicate.  
**How to avoid:** Store a product-generation discriminator in the new physical inventory tables, capture the pointer once, and bind that generation into count/page/lookup/availability queries.  
**Warning signs:** The query adapter does not accept a generation, or rollback performs multiple table restores before requests switch.  
[ASSUMED mitigation; current table-by-table rollback is at src/fabric/sync_service.py:1223-1241]

### Pitfall 3: `/ready` still triggers refresh
**What goes wrong:** A “nonblocking” readiness call performs all loaders when no other refresh is running.  
**Why it happens:** `Lock.acquire(blocking=False)` means “do not wait,” not “do not execute.”  
**How to avoid:** Both probes call `health(refresh=False)` only; background/manual paths own refresh.  
**Warning signs:** A slow fake loader increases readiness latency or its call count.  
[VERIFIED: src/api/app.py:491-504; src/api/providers.py:141-180]

### Pitfall 4: Unsupported scope is silently dropped
**What goes wrong:** A caller constrained by a dimension not present in inventory rows receives a broader result.  
**Why it happens:** SQL compilers often append only recognized predicates.  
**How to avoid:** Validate all effective-scope dimensions; compile false for unrepresentable constrained dimensions or enrich the product with a governed mapping.  
**Warning signs:** SQL tests pass subscription scope but omit business-service/application/connection cases.  
[VERIFIED current fail-closed matching: src/api/scope.py:108-127]

### Pitfall 5: The port is fixed, but complete-scan consumers keep 10,000
**What goes wrong:** API pages scale, but semantic graph ingestion and compatibility agent queries still truncate identity.  
**Why it happens:** Their literal limits live outside `InventoryReadPort`.  
**How to avoid:** Migrate `InventoryReadAdapter.resources()` and `_identity_rows_from_inventory()` in the same plan; distinguish bounded operator output from complete generation-pinned batch scans.  
**Warning signs:** Repository grep still finds `list_resources(... limit=10_000)`.  
[VERIFIED: src/onboarding/inventory_read_adapter.py:73-86; src/onboarding/ingestion_service.py:793-806]

### Pitfall 6: Availability is inferred from the returned page
**What goes wrong:** A filtered empty page is reported as an unavailable family, or an unavailable family as healthy-empty.  
**Why it happens:** Page rows and source-status facts are conflated.  
**How to avoid:** Query source-status/product-status separately and preserve the existing per-family contract. The current exact source states are `"ready"`, `"partial"`, `"stale"`, `"degraded"`, `"unavailable"`. [VERIFIED: src/intelligence/inventory/models.py:18-18]  
**Warning signs:** Availability changes when only offset/family filter changes.

### Pitfall 7: PageSnapshot is pulled into publication
**What goes wrong:** Publication creates page-specific tables or changes Copilot evidence semantics.  
**Why it happens:** Bounded page context is confused with a persisted domain projection.  
**How to avoid:** Leave PageSnapshot files untouched except for compatibility tests. Existing v1 construction slices selected resources to `50`, freshness to `32`, and evidence to `200`; inventory v2 separately enforces evidence/freshness bounds. [VERIFIED: web/src/lib/services.ts:593-600] [VERIFIED: web/src/lib/copilot/page-adapters.ts:662-840]  
**Warning signs:** A product manifest names a web route, drawer, or PageSnapshot.

### Known Threat Patterns for This Stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Scope predicate applied after count/page | Information Disclosure | Compile effective scope into the base CTE before filters, counts, ordering, or lookup; test unsupported dimensions. |
| Unscoped “does this ID exist?” probe | Information Disclosure | One scope-qualified lookup only; zero rows maps to the same `None`/404 for absent and out-of-scope. |
| Stale publisher promotes after another writer | Tampering | ETag + owner/source/generation conditions + monotonic fence + lease guard. [VERIFIED: src/storage/datasets.py:114-180,299-335] |
| Manifest/table mismatch | Tampering | Recompute persisted row counts/content hashes/schema and reject undeclared/missing tables before CAS. [ASSUMED product validation built on existing immutable-stage verification] |
| Unbounded result or expensive offset abuse | Denial of Service | Existing API limit maximum is `500`; bind page size, query timeout, `max_rows`, and emit rows-materialized metrics. [VERIFIED: src/api/dependencies.py:308-312] [VERIFIED: src/fabric/sql_endpoint.py:243-276] |
| Probe-triggered provider rebuild | Denial of Service | Status-only probes; background/manual refresh ownership. [VERIFIED: src/api/app.py:157-199,463-517] |
| Rollback without durable evidence | Repudiation | Persist promotion/rollback audit before CAS and retain immutable generations. [VERIFIED: src/ontology_discovery/publisher.py:187-255,363-428] |
| Raw provider payload in telemetry | Information Disclosure | Low-cardinality product/adapter/status dimensions only; never log rows, scope values, IDs, manifests containing payload, or exception text from provider data. [VERIFIED pattern: src/fabric/telemetry.py:59-82] |
