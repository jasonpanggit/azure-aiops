<objective>
Fix the confirmed, precise wiring gap in the change/configuration domain: `ChangeIntelligence.knowledge_projection()` already computes `ConfigurationDrift`/`PolicyDeviation`/`SecurityDeviation`/`AuthorizedChange`/`UnapprovedChange` as ontology-shaped rows, but `change_pipeline.run()` never calls it and `ChangePipelineResult` has no `entities`/`relationships` fields — the computed graph is silently discarded. Also resolve the open question of whether the predictive/remediation ontology domain shares the identical gap, and fix the confirmed identical gap in the Incident domain: `IncidentEngine.knowledge_projection()` (`src/intelligence/incidents/incident_engine.py:202`) already builds a bounded `CausalityGraph` of `Incident`/`OperationalFinding`/`BlastRadius`/`DependencyChain`/`OperationalEvent`/`RootCause` rows, but `IncidentEngine` is only ever instantiated in `src/semantic/live_operations.py`'s on-demand query path — never in `sync_service.py`'s dataset-assembly flow — so this graph never reaches ontology publication either.

Purpose: These five change-domain entity types are already registered in `ONTOLOGY_ENTITY_TYPES` and already appear in `ontology_sync.py`'s `compliance_context` view — the ontology schema is ready and waiting for rows that never arrive. This is MED-04's core, most concretely-scoped fix. The Incident domain shares the identical shape of bug: `Incident`/`RootCause` and the `Incident->hasFinding->OperationalFinding`/`Incident->hasBlastRadius->BlastRadius`/`Incident->hasEvent->OperationalEvent`/`Incident->hasProbableCause->RootCause` relationship tuples are already registered in `src/fabric/dataset_mapper.py`, and `sync_service.py` already has an `incident_intelligence_snapshot()` method that builds the exact `{inventory, incidents, alerts, resource_changes, history}` kwargs shape `IncidentEngine.from_snapshot()` needs — today that snapshot is only used piecemeal, folded into `change_intelligence_snapshot()`'s `"incidents"` list, never passed to `IncidentEngine` itself.
Output: `ChangePipelineResult` carries `entities`/`relationships`; `sync_service.py` forwards them into the ontology sync exactly like the existing `lifecycle_catalog`/`remediation_decision_reader` pattern; the predictive/remediation domain gets an evidence-backed disposition; a new `incident_pipeline.py` (mirroring `change_pipeline.py`) forwards `IncidentEngine.knowledge_projection()`'s output into the same ontology sync path.
</objective>
