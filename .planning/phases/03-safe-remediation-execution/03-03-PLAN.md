<objective>
Close the loop Phase 3 promised: after an execution is submitted to Azure, HOG polls the real upstream source of truth to learn what actually happened — rather than trusting the initial 2xx "accepted" response as success — and records the verified outcome, failure details, and manual rollback guidance. Bounded, idempotent, revalidated retries are added for failed/interrupted executions, without any automated rollback (patches generally cannot be cleanly undone; this phase records guidance only, per the locked EXEC-06 boundary).

Purpose: An "accepted" ARM response is not proof of success — Update Manager and AKS are the actual authorities. Without this plan, Phase 3 would let HOG claim outcomes it never verified, which is exactly the failure mode the existing `azure_adapter.py` docstring already warns against ("HOG does not claim success").
Output: `execution_verifier.py`, retry support in `execution_service.py`/`execution_store.py`, and an enriched `GET /executions/{id}` response.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Verifier → Azure ARM operation URL | Read-only GET against an upstream long-running-operation endpoint; must not be confused with a mutating call |
| HTTP client → POST /executions/{id}/retry | Untrusted `execution_id`; must re-validate approval, not just replay the original decision |
