<objective>
Add the single bounded execution capability this phase authorizes: `POST /api/v1/remediation/plans/{id}/execute`, reachable only for an already-approved `controlled-patch-recovery` plan, generalizing (not duplicating) the existing `operations.patching` stack. Execution is tracked as a durable job (queued → running → succeeded/failed/retrying/cancelled) using the same async-job pattern already established for connection sync, persisted so status survives a process restart and is pollable.

Purpose: This is the only place in Phase 3 where HOG is allowed to change Azure state. Every constraint here exists to keep that one path bounded and auditable: no fan-out, no widened target, no bypassing the approval workflow that Phase 2 built.
Output: `execution_store.py`, `execution_service.py`, the `execute`/`executions/{id}` endpoints, and tests proving the approval gate and non-widening guarantee.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → POST /plans/{id}/execute | The only state-mutating endpoint this phase adds; untrusted `plan_id`, principal-derived `requested_by` |
| Execution service → PatchingService/AzureArmPatchExecutionAdapter | In-process trusted call, but the approval gate is the security boundary that must not be bypassable |
| Execution service → Azure ARM | Real state-changing network call once past the gate |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Elevation of Privilege | execute() approval gate | critical | mitigate | Approval status, action_version currency, and expiry are checked before any target resolution or Azure call, with dedicated tests for each rejection path (Task 1). |
| T-03-05 | Tampering | execute() target/patch selection | critical | mitigate | Execution service's public method signature accepts no target/patch/operation parameter from the caller at all — only `plan_id` and `requested_by`; all execution parameters are read from the stored, already-approved plan. |
| T-03-06 | Repudiation | execution record | medium | mitigate | Every execution is durably stored with requested_by/approved_by/timestamps/provider_job_id before and after each transition (Task 2). |
| T-03-07 | Denial of Service | duplicate concurrent execute calls | medium | mitigate | `RemediationExecutionStore.create` rejects a second non-terminal execution for the same plan_id (Task 2 Test 2). |
| T-03-08 | Tampering | ARM API version pinning | high | accept | Unchanged: `AzureArmPatchExecutionAdapter` already pins Compute 2024-07-01, HybridCompute 2024-07-10, ContainerService 2024-05-01; this plan reuses it without modification. |
</threat_model>
