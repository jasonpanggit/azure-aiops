<task type="tracer" tdd="true">
  <name>Task 1: Atomically claim execute/retry and append immutable attempt history</name>
  <files>src/intelligence/remediation/execution_store.py, src/intelligence/remediation/execution_service.py, src/storage/locking.py, tests/test_remediation_execution_service.py, tests/test_remediation_execution_retry.py, tests/test_storage_locking.py</files>
  <behavior>
    - Store creation keys identity by plan ID plus approved snapshot hash/action version and returns whether newly claimed.
    - Duplicate execute returns the same record without trigger after queued, running, retrying, failed, cancelled, or succeeded.
    - Atomic compare-and-set retry claim permits exactly one failed/cancelled -> retrying transition for the expected status/revision.
    - Two independent stores sharing a local root or OneLake backend serialize claims through a dedicated remediation-execution lock; concurrent execute, retry, or cancel/retry races have one winner and at most one trigger call.
    - Retry rejects queued, running, retrying, and succeeded and uses only the approval decision's immutable execution_snapshot.
    - Every attempt and transition appends a timestamped immutable entry preserving actor, target, patches, provider_job_id, verified_state, failure_details, and outcome.
    - A crash after a durable claim does not auto-resubmit; it leaves an observable interrupted/active attempt requiring explicit operator recovery.
  </behavior>
  <action>Generalize `RunLock` to accept a safe explicit lock-document name while preserving its existing ingestion default. Give `RemediationExecutionStore` a dedicated `state/remediation_execution.lock` rooted beside its file/OneLake document; local roots use OS `flock`, OneLake uses the existing finite ADLS lease. Hold this cross-process/replica lock only around read-validate-write claims, not during Azure network calls. Add explicit store operations (`create_or_get`, `claim_retry`, atomic cancel, and transition append or equivalent) that compare expected execution revision/status and return a typed conflict to losers before any Azure call. Execution identity is plan ID + approved snapshot hash + action version and is permanent: once any matching execution exists, execute returns it regardless of terminal state; only retry may append another bounded attempt. Keep retry source states exactly `{failed, cancelled}` and the attempt ceiling. Build every attempt from the approved decision snapshot. Because installPatches/AKS node-image APIs expose no documented idempotency token, record this limitation in the adapter/service contract and use durable pre-submit claims as the safety boundary; never auto-resubmit a claimed attempt after ambiguous process failure. Preserve backward readability with defaults. Test two independent store instances against the same local backend, duplicate execute after every status, concurrent retry, cancel/retry races, lock-document isolation from ingestion, and adapter call counts.</action>

  </verify>
  <done>All submission paths are side-effect idempotent under concurrency and every attempt remains durably auditable.</done>
