## 1. System Classification

**System Type:** Hybrid structured-extraction and autonomous proposal agent

**Description:**
The system uses a versioned Microsoft Foundry prompt agent to propose evidence-backed ontology relationships from bounded, scope-filtered Azure and Fabric evidence. Deterministic application code owns scheduling, durable state, proposal policy, validation, and authoritative Fabric publication. Good behavior means precise, cited, schema-valid proposals that preserve tenant isolation and defer uncertain changes for human review.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. An unsupported, out-of-scope, or contradictory model-proposed relationship is published as authoritative.
2. A stale or duplicate autonomous run overwrites a newer valid ontology generation.
3. Prompt injection embedded in resource metadata causes tool misuse or unauthorized Fabric mutation.
4. Missing or degraded evidence is converted into a definitive relationship rather than an explicit review/escalation result.
5. Autonomous refresh fails silently and leaves operators believing Fabric is current.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Enterprise Azure cloud operations, semantic topology, and governed data/knowledge management

**User Population:** Azure platform engineers, SREs, cloud security engineers, Fabric/data-governance teams, ontology stewards, and auditors who maintain or consume the operational graph

**Stakes Level:** High

**Output Consequence:** Accepted proposals become part of a shared Fabric semantic layer used for dependency traversal, impact analysis, incident triage, security/compliance context, and agent grounding. A false edge can misstate blast radius or ownership; a missed or stale edge can conceal a real dependency. The proposal agent is advisory, but errors become operationally consequential if deterministic policy or human review allows them into an authoritative generation.

### What Domain Experts Evaluate Against

**Dimension: Evidence-backed relationship semantics**  
**Good (domain expert would accept):** Subject and object resolve to exact canonical Azure resource IDs in the authorized inventory; their current types permit the directional predicate; and the edge cites independently retrievable source records, observation times, and generation context. Naming similarity, co-location, or a shared tag is treated only as a lead unless the predicate policy explicitly permits it and corroborating evidence exists.  
**Bad (domain expert would flag):** The proposal reverses dependency direction, uses an unapproved predicate/type pair, cites narrative that cannot be retrieved, joins on display names, or presents a tag-based inference as an observed connection.  
**Stakes:** Critical  
**Source:** Microsoft Fabric ontology guidance on shared entity/relationship meaning and constraints; W3C SHACL graph validation and PROV-O provenance standards.

**Dimension: Operational coverage with honest gaps**  
**Good (domain expert would accept):** Evaluation separates precision and recall by predicate and Azure resource family, includes additions, changes, retirements, unresolved endpoints, and stale observations, and exposes source degradation or bounded coverage. Missing evidence produces a pending, review, or degraded result rather than either inventing an edge or asserting that no dependency exists.  
**Bad (domain expert would flag):** Aggregate accuracy hides poor coverage for a critical resource family; deleted resources leave live edges; unresolved endpoints are dropped silently; or a partial scan is presented as a complete current topology.  
**Stakes:** High  
**Source:** Linked-data quality practice treats correctness, completeness, consistency, timeliness, and verifiability as distinct qualities; Phase 13 operational requirements require explicit freshness, reconciliation, and pending-edge state.

**Dimension: Tenant and subscription boundary integrity**  
**Good (domain expert would accept):** Every endpoint, citation, lookup, proposal, and review action remains within the caller's effective tenant/subscription scope. The curator has only scoped read and proposal-submit capabilities, while a separate least-privilege publisher performs authoritative writes. Isolation tests include colliding names and identifiers from unauthorized scopes.  
**Bad (domain expert would flag):** An edge or citation reveals an unauthorized resource, a cross-scope join is accepted because names match, the agent can invoke a general query/write tool, or publication runs under a broad shared identity.  
**Stakes:** Critical  
**Source:** Microsoft Foundry RBAC guidance and established zero-trust/least-privilege practice; OWASP LLM01:2025 prompt-injection guidance.

**Dimension: Generation integrity and recoverability**  
**Good (domain expert would accept):** Replaying the same evidence and policy produces the same content-addressed proposal decisions; duplicate work is harmless; only the fenced current writer can atomically promote a fully validated generation; and operators can trace and roll back to the preceding valid generation.  
**Bad (domain expert would flag):** Concurrent or timed-out runs create duplicate edges, publish a partial graph, overwrite newer state, lose retirement history, or cannot identify which evidence, policy, agent version, and reviewer produced an active edge.  
**Stakes:** Critical  
**Source:** Cloud platform and data-governance practice for idempotency, single-writer fencing, lineage, versioning, and rollback; NIST AI RMF Generative AI Profile governance guidance.

**Dimension: Steward reviewability and controlled promotion**  
**Good (domain expert would accept):** A reviewer can distinguish observed facts from inference, reproduce cited evidence as-of the stated time, see contradictions and uncertainty, and make a versioned approve/reject decision. Novel predicates, weak or single-source evidence, and policy exceptions remain in review; auto-accept is limited to reversible, allowlisted predicate/type pairs whose per-predicate performance has been calibrated with experts.  
**Bad (domain expert would flag):** Model confidence alone authorizes publication, rationale substitutes for evidence, ontology vocabulary changes silently, or a reviewer cannot reconstruct why an edge was promoted.  
**Stakes:** High  
**Source:** NIST AI RMF Generative AI Profile; established ontology-stewardship and model-risk governance practice.

### Known Failure Modes in This Domain

- **Semantic overreach from operational metadata:** Similar resource names, tags, regions, or deployment timing are mistaken for `depends_on`, `routes_to`, or ownership relationships, producing a false blast radius.
- **Temporal ghost topology:** Missed tombstones, stale watermarks, failed pending-edge recovery, or an old writer cause retired resources and superseded relationships to remain active, or cause “not observed yet” to be interpreted as “does not exist.”
- **Identity and scope bleed:** Case normalization, aliases, reused names, or incomplete Azure IDs merge distinct resources or connect entities across subscriptions/tenants, leaking topology and corrupting ownership.
- **Untrusted metadata bypasses governance:** Instructions embedded in tags, descriptions, or source text redirect the curator toward unauthorized lookups, unapproved predicates, or mutation attempts; treating resource metadata as commands turns a data-plane value into a control-plane action.

### Regulatory / Compliance Context

No sector-specific regulatory regime is established by the deployment context. Directly applicable enterprise constraints are authorization-bound data access, least privilege and separation of duties, immutable decision/publication audit trails, evidence retention, data residency, and documented human accountability for exceptions. If resource metadata contains personal data, the organization's applicable privacy regime (for example, GDPR) governs minimization, purpose, retention, access, and deletion; applicability must be confirmed for each deployment rather than assumed.

NIST AI RMF and its Generative AI Profile are voluntary risk-management baselines, not legal certification, but are directly useful for governance, provenance, monitoring, incident handling, and human oversight. Fabric Ontology is documented as a preview capability, so enterprise release governance must explicitly assess preview support terms, regional availability, compatibility, and rollback rather than treating it as a generally available production control.

## 2. Framework Decision

**Selected Framework:** Microsoft Foundry Prompt Agent through `azure-ai-projects` and the Responses API

**Version:** `azure-ai-projects>=2.0,<3`, matching the repository's existing Foundry runtime contract

**Rationale:**
The repository already provisions code-first Foundry prompt agents, grants bounded MCP tools, and invokes them through the Responses API. The agent needs only managed structured proposal generation; custom scheduling and publication logic stays in deterministic Python code and a durable ACA Job/coordinator.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Microsoft Foundry Hosted Agent | Adds a maintained container runtime and cost without improving the proposal-only boundary; reconsider only if custom agent-side protocols become necessary. |
| Ephemeral Responses API agent | Keeps the definition in application code but gives up the managed versioned agent resource and dedicated deployment identity used elsewhere in the repository. |
| Microsoft Agent Framework orchestration | Durable scheduling, leases, review, and publication are deterministic workflow state rather than model-planned agent state. |

**Vendor Lock-In Accepted:** Partial — Foundry hosting, identity, tracing, and MCP integration are intentional; proposal contracts and deterministic governance remain provider-independent.

import json
import os

from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential


def request_proposals(evidence_package: dict[str, object]) -> str:
    """Invoke the deployed, versioned prompt agent; validation is shown in 4b."""
    with (
        DefaultAzureCredential() as credential,
        AIProjectClient(

                "role": "user",

                    "evidence": evidence_package,
                }),
            }],
            max_output_tokens=2_000,
        )
        return response.output_text

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `AIProjectClient` | Entra-authenticated client for the Foundry project data plane (`...services.ai.azure.com/api/projects/...`). | Create/version the agent in deployment code and obtain its OpenAI-compatible client. |
| `PromptAgentDefinition` | Declarative, versioned model + system instructions + tools; Foundry owns execution and scaling. | Define `ontology-curator-agent`; keep custom scheduling and policy outside it. |
| Agent-bound OpenAI client | `project.get_openai_client(agent_name=...)` returns the client used for Responses API calls. | Submit one bounded evidence batch and read `response.output_text`. |
| Responses API response | One model/tool execution result, with response ID, output text, and usage. | Correlate one proposal attempt with the durable discovery run ledger. Do not use a conversation for cross-run memory. |
| `MCPTool` / project connection | A remote MCP server plus an explicit `allowed_tools` subset and project-managed identity. | Expose only scope-filtered ontology evidence and approved vocabulary reads. |

### Common Pitfalls
1. **Using the wrong endpoint, API version, or token audience.** The project
   endpoint is `https://<account>.services.ai.azure.com/api/projects/<project>`,
   the current data-plane API is literal `v1`, and the Entra scope is
   `https://ai.azure.com/.default`; an ARM token is rejected.
2. **Assuming agent responses are schema-enforced.** Microsoft's structured
   outputs page currently says structured outputs are not supported with
   Foundry Agent Service. A `PromptAgentDefinition` therefore must not be
   treated as a trusted `response_format`; parse with Pydantic and retry as
   described in 4b.
3. **Giving `require_approval="never"` to a mutating MCP tool.** That setting is
   acceptable only because this agent's allowlist is read-only. The agent must
   never receive Fabric publication, arbitrary SQL, Azure mutation, or proposal
   approval tools.
4. **Treating missing evidence as an MCP failure.** Existing Foundry runs can be
   aborted when a tool result sets `isError=true`. Return a successful,
   structured `status="empty"` result for a valid lookup with no evidence;
   reserve errors for malformed, denied, or failed calls.
5. **Enabling verbose SDK/tracing logs without a data policy.** Foundry traces
   and debug logs can contain prompts, tool arguments, and outputs. Keep SDK
   body logging disabled, redact resource metadata, and restrict Application
   Insights/Log Analytics access and retention.

## 4. Implementation Guidance

**Model Configuration:**

- Use the repository deployment `gpt-5.4-mini`, model version `2026-03-17`,
  `GlobalStandard`, rather than introducing a second ungoverned deployment.
- Set `max_output_tokens=2_000` on every Responses call. Keep each request to at
  most 50 changed entities, 200 candidate pairs, and 40 evidence records; tune
  these limits from evals rather than allowing an unbounded batch.
- Leave `temperature` unset for the initial deployment. The official prompt
  agent quickstart also omits sampling controls, and GPT-family parameter
  support varies. If the deployed model accepts temperature, evaluate `0.1`
  offline before adding it to `PromptAgentDefinition`; never change both
  `temperature` and `top_p`.
- Use a 60-second request deadline, at most two transient transport retries with
  exponential backoff/jitter, and at most two separate schema-repair attempts.
  A failed batch is recorded and sent to review; it never blocks deterministic
  ontology refresh or triggers publication.

**Core Pattern:**

The scheduled ACA Job acquires a fenced lease, computes a deterministic
incremental evidence package, invokes the prompt agent once per bounded batch,
validates the complete response, and writes advisory proposals. A separate
policy service may admit reviewed proposals into a candidate generation; only
the publisher identity can validate and promote that generation.

```python
def run_batch(batch: EvidenceBatch, deps: DiscoveryDependencies) -> None:
    lease = deps.runs.acquire_fenced_lease(batch.scope, batch.source_generation)
    deterministic_edges = deps.graph_builder.build(batch)

    # The model sees only server-scoped evidence and can return proposals only.
    raw = deps.proposer.propose(batch, max_output_tokens=2_000)
    proposals = validate_with_retries(raw, batch=batch, proposer=deps.proposer)

    # Re-derive trusted fields; never accept tenant, subscription, timestamps,
    # endpoint existence, predicate validity, or confidence policy from the LLM.
    governed = deps.policy.evaluate(
        proposals,
        authoritative_batch=batch,
        active_generation=deps.generations.active(batch.scope),
    )
    deps.proposals.append_content_addressed(governed, lease.fencing_token)

    # In Phase 13 shadow mode, model proposals stop at the review queue.
    candidate = deps.generations.stage(deterministic_edges, lease.fencing_token)
    deps.validator.validate_or_raise(candidate)
    deps.publisher.promote_if_current(candidate, lease.fencing_token)
```

**Tool Use:**

Provision the versioned prompt agent through the existing
`create-foundry-agent.sh`/Terraform path, or its SDK-equivalent below. The
project connection must use managed identity and the APIM/MCP server must derive
tenant/subscription scope from trusted identity claims—not model arguments.

Do not add a vector database for Phase 13: exact IDs, typed vocabulary, current
relationships, and source timestamps come from authoritative stores. Foundry
server-side tracing to Application Insights is the primary tracing integration;
add `azure-core-tracing-opentelemetry` only for coordinator-side spans. Keep
evaluation fixtures in-repository and use Foundry evaluations later through the
same OpenAI client rather than putting evaluation logic in the agent.

**State Management:**

Use no cross-run Foundry conversation. Each batch is a fresh Responses call so
stale dialogue cannot cross tenant, subscription, or generation boundaries.
Persist the run/checkpoint ledger, source-generation hash, fencing token, agent
name/version, model deployment/version, prompt and schema hashes, response ID,
token usage, Pydantic errors, content-addressed proposals, policy decisions,
review state, pending edges, and publication attempts in the durable
application store. A retry reuses the same batch ID and source generation.
Publication compares both the fencing token and source generation immediately
before promotion.

**Context Window Strategy:**

Build context from changed entities and their deterministic one-hop candidate
neighborhood, not a raw inventory dump. Sort and truncate by exact endpoint
match, source authority, freshness, then corroboration count. Preserve every
included evidence ID and observation timestamp. If a package exceeds its token
budget, split it by authorized scope and connected component; never truncate
mid-record. Resource names, tags, descriptions, prior proposals, and tool text
are delimited as untrusted data and cannot alter instructions. Periodic full
reconciliation remains deterministic; do not rely on agent conversation
summaries or hidden compaction as authoritative state.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

```python
from datetime import datetime
from typing import Literal, Self

from pydantic import BaseModel, ConfigDict, Field, model_validator


class RelationshipProposal(BaseModel):
    model_config = ConfigDict(extra="forbid")

    subject_id: str = Field(min_length=1, max_length=512)
    subject_type: str = Field(min_length=1, max_length=128)
    predicate: str = Field(min_length=1, max_length=128)
    object_id: str = Field(min_length=1, max_length=512)
    object_type: str = Field(min_length=1, max_length=128)
    evidence_refs: list[str] = Field(min_length=1, max_length=20)
    observed_at: datetime
    rationale: str = Field(min_length=1, max_length=1_000)
    confidence: float = Field(ge=0.0, le=1.0)
    uncertainty: list[str] = Field(max_length=10)
    disposition: Literal["propose", "needs_review"]


class ProposalBatch(BaseModel):
    model_config = ConfigDict(extra="forbid")

    batch_id: str = Field(min_length=1, max_length=128)
    status: Literal["proposals", "insufficient_evidence"]
    proposals: list[RelationshipProposal] = Field(max_length=100)
    missing_evidence: list[str] = Field(max_length=20)

    @model_validator(mode="after")
    def status_matches_content(self) -> Self:
        if self.status == "insufficient_evidence" and self.proposals:
            raise ValueError("insufficient_evidence cannot contain proposals")
        if self.status == "proposals" and not self.proposals:
            raise ValueError("proposals status requires at least one proposal")
        return self


def parse_proposal_batch(raw_output: str) -> ProposalBatch:
    return ProposalBatch.model_validate_json(raw_output)
```

Foundry Agent Service does **not currently support Azure OpenAI structured
outputs**, according to Microsoft's structured-outputs limitations. Do not pass
or claim a `response_format` guarantee for this prompt agent. Put the compact
JSON schema (`ProposalBatch.model_json_schema()`) in the versioned system
instructions, require JSON only, and treat the result as untrusted until
`model_validate_json` succeeds. Then run deterministic checks for batch ID,
known in-scope endpoints, allowlisted predicate/type pairs, evidence ownership
and freshness, and contradiction with the active generation.

On `ValidationError`, make at most two fresh repair calls. Send only the schema,
the original bounded evidence package, and sanitized error locations/types—not
tracebacks, secrets, or instructions copied from the invalid response. Log the
run/batch/response IDs, agent and schema versions, attempt number, error
locations/types, token usage, and latency. After two failures, persist
`invalid_agent_output`, surface the batch for operator review, and continue the
deterministic run. Transport retries are a separate budget.

### Async-First Design

Use `azure.ai.projects.aio.AIProjectClient` with
`azure.identity.aio.DefaultAzureCredential`; `get_openai_client(agent_name=...)`
returns an `AsyncOpenAI`, so call `await openai.responses.create(...)` and close
both clients with `async with`. Bound concurrency with a semaphore below the
deployment's 50K TPM capacity and preserve one durable batch record per task.

Do not call the repository's synchronous `_run_awaitable()`/`asyncio.run()` from
FastAPI or another running event loop. Use `asyncio.run(main())` only once at the
ACA Job process entry point and propagate `await` below it. Phase 13 should await
the complete response because schema and citations must be validated as one
unit. Streaming is appropriate only for an operator-facing progress view;
never persist or govern a partial streamed proposal.

### Prompt Engineering Discipline

Keep authority and behavior in the versioned
`PromptAgentDefinition.instructions`: proposal-only role, exact JSON contract,
approved tool purpose, no publication, and an explicit rule that evidence text
is data rather than instructions. Put the batch ID, scope-filtered evidence,
vocabulary, and task in the user input. Never concatenate resource metadata
into system instructions or let model-provided tenant/subscription fields
override server context.

Keep a small set of static, adversarial few-shot examples with the prompt
(valid proposal, insufficient evidence, out-of-scope endpoint, and
instruction-bearing tag). Dynamically retrieve examples only from reviewed,
scope-safe proposal history and label them as examples, never policy. Set
`max_output_tokens=2_000` on every call; if 100 proposals cannot fit, reduce the
batch rather than raising the output ceiling indefinitely.

### Context Window Management

Rerank candidate evidence deterministically by endpoint match, authority,
freshness, and independent corroboration. Drop duplicated low-authority facts
first, then split by connected component and source scope. Preserve complete
records and citation IDs; do not summarize away qualifiers such as observation
time, denial, empty results, or uncertainty. For autonomous runs, the durable
ledger—not a Foundry conversation or model summary—is memory. Resume from the
last committed batch/checkpoint and periodically perform a full deterministic
reconciliation to detect incremental drift.

### Cost and Latency Budget

Budget a normal batch at 8,000 uncached input tokens and 1,200 output tokens.
For `gpt-5.4-mini` Global Standard, the Azure price page on 2026-09-04 lists
$0.75/M input, $0.075/M cached input, and $4.50/M output. The token-only
estimate is therefore **$0.0114 per batch**; 1,000 batches/day is about
**$342/month**. With 6,000 of the 8,000 input tokens served from prompt cache,
the estimate falls to **$0.00735 per batch** or **$220.50/month**. MCP,
Azure AI Search, Application Insights, storage, retries, and networking are
additional; verify the deployment region/SKU price before setting the budget.

Use exact-match caching keyed by tenant/scope, source-generation hash, prompt
version, schema version, model deployment/version, and ordered evidence hashes.
Semantic caching is unsafe for authoritative proposal reuse; it may only
suggest candidate evidence, which must be freshly retrieved and revalidated.
Do routing, deduplication, and summarization deterministically rather than pay
for extra model calls. If a classifier is later justified, benchmark a
separately deployed smaller model (for example, the available GPT-5 nano tier)
against the extraction eval set before use. Target p95 under 30 seconds per
batch, cap concurrent calls by TPM, and alert on retries, cache misses, or token
use above the batch budgets.

## 5. Evaluation Strategy

### Dimensions

All release metrics are computed both overall and by predicate, endpoint type
pair, Azure resource family, and evidence-source status. Aggregate scores must
not hide a failing critical slice. Precision is `TP / (TP + FP)` and recall is
`TP / (TP + FN)` against steward-labeled edges and explicit no-edge cases.

| Dimension | Domain rubric | Measurement Approach | Priority |
|-----------|---------------|----------------------|----------|
| Relationship precision and field accuracy | **PASS:** Canonical subject/object IDs and types, direction, and predicate match the expert-labeled relationship; overall precision is at least 0.98 and every critical predicate/resource-family slice is at least 0.95, with zero reversed, invented, or unapproved relationships. **FAIL:** A display-name/tag/co-location lead is asserted as fact, direction is reversed, an endpoint is misidentified, or either threshold is missed. | Code against labeled graph + Human adjudication | Critical |
| Relationship recall and honest coverage | **PASS:** Overall recall is at least 0.90 and each critical slice is at least 0.85 across additions, changes, retirements, and unresolved endpoints; every partial, stale, empty, or degraded scan is represented as pending/review/degraded rather than “no relationship.” **FAIL:** A material expected edge or retirement is missed, an unresolved endpoint disappears silently, or bounded coverage is represented as complete. | Code + Human | High |

### Release Gates

1. CI fails on any Critical rubric failure. High dimensions must meet their
   stated thresholds; approved exceptions require an owner, expiry, and audit
   record and cannot waive scope, injection, citation, publication, or audit
   safety.
2. Phase 13 begins in **shadow mode**: all agent proposals stop in the review
   queue and deterministic publication continues without them.
3. A predicate/type pair may become eligible for auto-accept only after at
   least 30 consecutive shadow days and 200 expert-adjudicated eligible
   proposals for that pair, with zero Critical failures, review/escalation
   recall of 1.00, recall of at least 0.90, and a 95% Wilson lower confidence
   bound for precision of at least 0.98. An ontology steward, security owner,
   and Fabric governance steward must approve the versioned allowlist.
4. Auto-accept remains reversible and disabled by default per scope. Any
   Critical production event or threshold breach disables the affected
   allowlist entry and returns it to review-only shadow operation.

### Reference Dataset

**Size:** Start during Plan 13-01 with at least 32 scenario bundles and at least
100 labeled candidate pairs (positive edges plus hard negatives) before model
integration. Expand from adjudicated shadow traffic. Auto-accept uses the
larger per-predicate shadow requirement in the release gates, not the seed set.

**Composition:**

- 8 normal additions/changes/retirements spanning containment, operational,
  topology, connection metadata, and approved tag-derived relationships.
- 4 direction/type/vocabulary traps, including plausible but false
  name-, region-, timing-, and tag-based relationships.
- 4 stale, contradictory, missing, partial, empty, and degraded evidence cases
  with unresolved endpoints and tombstones.
- 4 tenant/subscription isolation cases with case variants, aliases, reused
  display names, colliding identifiers, and unauthorized citations.
- 4 direct and indirect prompt-injection cases in names, tags, descriptions,
  prior proposals, and MCP tool results.
- 4 duplicate/retry/restart/concurrent-writer cases, including stale fencing
  tokens, reordered events, partial stage failure, and rollback.
- 4 review/escalation and budget cases: novel predicates, weak single-source
  evidence, oversized batches, transport/schema failures, cancellation, and
  timeout.

Every bundle preserves the input scope, authoritative entities, candidate
pairs, evidence IDs and observation times, source generation, approved
vocabulary, expected/forbidden edges, required disposition, allowed tool calls,
expected normalized hash, and expected audit/publication outcome.

**Labeling:**

- An Azure platform architect labels canonical identity and direction; an
  ontology steward labels predicates/type pairs and expected edges/no-edges.
- An SRE labels operational significance, gaps, and retirements; security and
  Fabric stewards label isolation, injection, lineage, and promotion outcomes.
- Two experts independently label Critical cases; disagreements are adjudicated
  and retained with rationale and label version. Dataset changes require review.
- Code computes exact metrics. An LLM judge may assist only with rationale and
  citation-support triage after calibration against at least 50 expert labels
  reaches correlation/agreement of at least 0.70; judge disagreement and every
  auto-accept candidate remain human-review signals.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Scope, identity, citation, and read-only tool boundary | Every evidence lookup, proposal, review action, and tool call; unknown/out-of-scope endpoint, citation, or tool | Derive scope from identity claims, not model arguments. Deny the call, quarantine the proposal, record a security event, and never reveal the unauthorized record. |
| Strict contract and deterministic policy gate | Every model response; parse error, unapproved vocabulary/type pair, missing/unsupported/stale evidence, contradiction, or unknown endpoint | Make no more than two sanitized schema repairs. Then persist `invalid_agent_output` or route to review. No failed proposal enters a candidate generation. |
| Shadow/review and separation-of-duties gate | Every model proposal before staging | While shadow mode is active, route all proposals to review. Later, admit only an explicitly enabled allowlisted pair with current threshold evidence; otherwise review. The curator identity has no approval or Fabric-write capability. |
| Fenced validation and atomic publication | Every stage/promote attempt; stale lease/source generation, incomplete graph, validation failure, lost audit write, or publisher identity mismatch | Fail closed before promotion, leave the current generation unchanged, mark the attempt terminal, alert operators, and retain/offer the last valid generation for rollback. |
| Bounded execution | Before and during each batch; entity/pair/evidence/token limit, retry limit, cancellation, or 60-second request deadline reached | Stop further model/tool calls, persist checkpoint and explicit degraded/failed status, route unresolved proposals to review, and allow deterministic refresh to continue. |
| Injection tripwire | Non-allowlisted action/tool request, scope-change instruction, secret request, or policy/publication instruction appears in model output or tool arguments | Terminate the agent attempt, deny the action, retain sanitized forensic metadata, and raise a security alert; do not echo the injected content into repair prompts. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Precision and recall by predicate/type/resource family | Weekly on 100% of reviewed/auto-accepted proposals plus stratified hard negatives and missed-edge reconciliation samples | Disable affected allowlist entry; return to shadow, adjudicate errors, and update evidence/prompt/policy or labels before re-release. |
| Citation support, validity, and freshness | Daily code checks on all proposals; weekly expert review of all failures and a 10% valid sample | Quarantine affected proposals/generations, investigate source/watermark drift, and expand source-specific fixtures. |
| Review/escalation calibration and reviewer disagreement | Weekly on all policy escalations/rejections and a stratified 10% of ordinary shadow proposals | Recalibrate thresholds and rubric; do not loosen mandatory-review rules from model confidence alone. |
| Injection and scope-bleed resistance | Full adversarial suite on every prompt/tool/policy change; monthly red-team expansion from production metadata patterns | Block release, rotate/reduce grants if needed, add the attack to regression data, and security-review traces. |
| Replay, idempotency, fencing, restart, and rollback | Nightly deterministic replay/property tests and weekly fault-injection runs | Stop publication rollout, preserve current generation, repair coordinator/store/publisher, and prove replay before resuming. |
| Cost, latency, retries, and completion | Daily aggregation by agent/prompt/model/schema version and source-status class | Reduce/split batches, investigate cache/tool/deployment drift, or pause agent calls while deterministic refresh continues. |
| Audit-chain completeness | Daily validator over all consequential transitions; monthly auditor sample | Page on publication/review gaps, fail closed for new promotions, and repair forward without mutating historical records. |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix over OpenTelemetry for self-hosted evaluation and
replay inspection, with the same sanitized coordinator spans and Foundry
server-side traces exported to the repository's Application Insights
environment for production operations. Correlation keys are opaque run, batch,
proposal, source-generation, and publication IDs; sensitive bodies are not
recorded.

**Key Metrics to Track:**

1. `ontology_proposal_precision`, `ontology_proposal_recall`, and
   `ontology_escalation_recall`, sliced by predicate/type pair, resource family,
   agent/prompt/policy version, and source-status class.
2. Citation resolution/support/freshness rates; Pydantic validity, repair,
   vocabulary rejection, contradiction, prompt-injection, scope-denial, and
   forbidden-tool counts.
3. Due-to-start delay, run/task terminal completion, checkpoint age, pending
   edge age, retries, cancellations, deterministic replay mismatch, duplicate
   suppression, and stale-writer rejection.
4. Candidate validation, stage, atomic promotion, rollback, active-generation
   age, and publication/audit-chain completeness.
5. Input/output tokens, estimated token cost, cache hit rate, tool/model
   latency, end-to-end p50/p95/p99, timeout rate, and batch limit utilization.

**Alert Thresholds:**

- **Immediate page and automatic auto-accept disable:** any scope disclosure,
  unauthorized/mutating tool call, successful prompt injection, invalid or
  unsupported edge promoted, stale writer promotion, partial generation made
  active, missing consequential audit event, or inability to identify/rollback
  the active generation.
- **Page:** no successful browser-independent run for two schedule intervals;
  active generation exceeds its configured freshness objective; a fenced
  publication repeatedly fails; pending critical edges exceed their SLO; or a
  run remains non-terminal beyond its timeout/retry envelope.
- **Alert within one hour:** citation validity below 100%, citation freshness
  below 99%, post-repair schema validity below 100%, repair rate above 5%,
  timeout rate above 1%, p95 model latency above 30 seconds for 15 minutes, any
  request above the 60-second deadline, or any configured token/retry/batch cap
  violation.
- **Weekly quality gate:** overall precision below 0.98, a critical slice below
  0.95 precision, overall recall below 0.90, a critical slice below 0.85
  recall, escalation F1 below 0.95, mandatory-review recall below 1.00, or an
  enabled pair's precision Wilson lower bound below 0.98. Disable only the
  affected allowlist entry unless a systemic failure requires global shadow
  mode.

**Smart Sampling Strategy:**

Retain metric/span metadata for 100% of runs. Human-review 100% of shadow-mode
proposals, auto-accepted proposals during canary operation, policy exceptions,
novel predicates/type pairs, stale/contradictory/degraded evidence, citation or
schema repairs, scope denials, injection tripwires, retries/timeouts, reviewer
disagreements, replay mismatches, and publication/rollback failures. After an
allowlisted pair exits canary, review a stratified 10% of its accepted proposals
plus 5% of clean ordinary runs, oversampling rare predicates, resource families,
source degradations, high-confidence rejections, and near-threshold decisions.
Feed adjudicated failures back into the versioned reference dataset without
copying secrets or unauthorized production metadata.
