<objective>
Give the API process an autonomous, bounded, restart-safe background worker
that drives every non-terminal or unreconciled remediation execution to a
real terminal outcome, using exactly the store/service machinery built in
Plans 03.4-01 and 03.4-02 -- closing CR-03's "verification depends on
someone keeping a browser tab open" finding for good, and making browser
polling (plan_workflow/get_execution's existing opportunistic
poll_verification calls) a convenience rather than a correctness dependency,
per 03.4-CONTEXT.md's Verification Lifecycle decision.

This plan wires, it does not reinvent: the coordinator's own logic is
iteration plus per-record dispatch plus error isolation. All scheduling,
deadlines, backoff, and reconciliation semantics already live in Plan
03.4-02's service methods.

Purpose: An execution's fate no longer depends on anyone's browser session;
it is driven to completion by the process itself, and that process can be
killed and restarted without losing track of in-flight work.
Output: RemediationVerificationCoordinator, wired into src/api/app.py's
startup/shutdown lifecycle exactly like the existing provider-refresh
thread, backed by a runtime.py-resolved target_evidence_refresher over the
existing hybrid_vulnerability live ARG path.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Background coordinator thread -> execution_store | The coordinator is an in-process, unauthenticated, always-on caller of the same store every HTTP-authenticated route uses; it must never bypass a safety invariant (bounded attempts, immutable snapshot, CAS transitions) that the HTTP path enforces. |
| _target_evidence_refresher -> hybrid_vulnerability -> live ARG | Reuses an existing, already-audited live Azure Resource Graph read path; introduces no new external network destination. |
| Coordinator thread lifecycle -> process lifecycle | Thread start/stop must be deterministic so tests and production deployments never leak a thread across app instances (each `create_app()` call, e.g. in tests, must get its own bounded thread and a working shutdown hook). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.4-08 | Elevation of Privilege | RemediationVerificationCoordinator's unrestricted execution_service | high | mitigate | The coordinator-owned RemediationExecutionService is constructed with `plan_repository=None, patching_service=None` and only ever calls `poll_verification`/`reconcile_evidence`/`reconcile_ambiguous_submission` -- none of which touch `self._plans`/`self._patching` (verified in Plan 03.4-02) -- so it structurally cannot execute, retry, or supersede a plan; it can only observe/reconcile already-durable records. |
| T-03.4-09 | Denial of Service | Coordinator background thread | medium | mitigate | Bounded 10s poll interval, per-record try/except isolation (one failing record never blocks the batch or crashes the loop), and a 5s-timeout join on shutdown identical to the existing `_start_background_refresh` pattern -- no new unbounded resource growth. |
| T-03.4-10 | Tampering | Two processes/threads racing the same execution record | medium | mitigate | Proven end-to-end against the real file-backed store in Task 3 (not just fakes): the existing revision-and-status CAS in RemediationExecutionStore.transition, combined with Plan 03.4-02's ExecutionClaimConflict-catching wrapper, is the sole serialization mechanism and is shown to produce exactly one coherent outcome under concurrent access. |
| T-03.4-SC | Tampering | Supply chain (no new packages) | n/a | accept | This plan adds no new pip/npm/cargo dependency; the existing Package Legitimacy Audit gate does not apply. |
