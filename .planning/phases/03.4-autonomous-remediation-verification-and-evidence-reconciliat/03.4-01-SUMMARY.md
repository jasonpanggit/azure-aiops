# Phase 03.4 Plan 01: Durable verification scheduling + nested Azure result parsing Summary

Gave `RemediationExecutionStore` five new durable, schema-versioned (2.2.0) fields for verification scheduling/deadline/evidence tracking with conservative legacy defaults, added a pure `list_due_for_verification` query that answers "what needs a verification pass right now" from disk state alone, and deepened `ExecutionVerifier.verify()` to parse ARM's nested `properties.status`/patch counts/error details so a `CompletedWithWarnings` or non-zero `failedPatchCount` result is never misread as a clean envelope-level success.

## Accomplishments

- `RemediationExecutionStore` schema bumped to `2.2.0`, adding `verification_deadline_at`, `next_verification_at`, `verification_attempts`, `verification_evidence`, and `evidence_reconciliation` to every record, all defaulting to inert/empty values (legacy pre-2.2.0 records read back safely via `_with_defaults`).
- `_transition_locked`'s per-attempt field passthrough list now also carries `verification_evidence`, so a future `transition(..., verification_evidence=...)` call lands on both the record and the current attempt with no further store changes.
- `RemediationExecutionStore.list_due_for_verification(now=...)` — read-only, uses the same lock as `get()`/`list_all()` (no CAS claim since nothing is mutated) — implemented via two new module helpers: `_needs_verification_pass` (the due/not-due decision per status) and `_is_patch_evidence_candidate` (KB-reconciliation eligibility, exported in `__all__` for Plan 03.4-02 to reuse rather than re-derive).
- `ExecutionVerifier._parse_patch_properties` extracts `installedPatchCount`/`failedPatchCount`/`pendingPatchCount`/`notSelectedPatchCount` (each coerced via `max(0, int(...))` with try/except) and provider error text from `properties.error`/`properties.errorDetails` (truncated to 500 chars), never raising on a malformed/absent/non-dict `properties` body.
- `verify()`'s non-defender branch now checks nested `CompletedWithWarnings`/`failedPatchCount > 0` *before* the existing envelope-only success check, so a partially-failed patch run can never be read as a clean success; every returned dict in that branch now also carries `verification_evidence` with the full parsed detail. The defender_configuration branch is untouched and intentionally omits `verification_evidence` (nested patch counts don't apply there).

## Deviations from Plan

None — plan executed exactly as written. All five `list_due_for_verification` eligibility rules, the nested-parsing precedence rule, and the legacy-default behavior all passed on first test run with no adjustment needed to the initial implementation.
