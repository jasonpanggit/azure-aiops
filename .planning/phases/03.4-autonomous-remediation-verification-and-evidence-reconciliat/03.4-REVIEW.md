# Phase 03.4: Autonomous Remediation Verification and Evidence Reconciliation — Deep Code Review

**Reviewed:** 2026-09-04T10:12:37+08:00
**Depth:** deep (store → verifier → service → coordinator → API startup/shutdown call-chain traced)
**Files Reviewed:** 7 (key-files from `03.4-01-SUMMARY.md`, `03.4-02-SUMMARY.md`, `03.4-03-SUMMARY.md`; test files read for coverage cross-checks only, not findings targets)
**Status:** issues_found

## Summary

Phase 03.4 sets out to close Phase 03's Recommendation 3 (CR-03/WR-11): make remediation verification autonomous, deadline-bounded, deeply-parsed, and evidence-reconciled, independent of any browser session. The `list_due_for_verification`/deadline/backoff machinery is genuinely well-built where it is exercised: `_transition_or_current` correctly absorbs concurrent `ExecutionClaimConflict`s so two racing callers never crash and always converge on one persisted outcome (verified empirically and by the phase's own concurrency test), and the coordinator's per-record `try/except` correctly isolates one bad record from blocking the rest of a pass.

However, the review found the **deadline mechanism is not actually wired into the CAS transition that first claims "running"/"retrying" status** — it is only set later, inside `_submit_and_record`'s own success/ambiguous-failure branches. This means the specific crash window the phase's own restart-recovery goal is meant to close (a process dying mid-execution) is *not* closed for the narrow but entirely realistic case of a crash between the pre-submission status claim and the actual provider call. I reproduced this empirically: a record can sit in `status="running"` with an empty `verification_deadline_at` for 1000 simulated days and still never reach a terminal outcome, because the "no provider job id" / "not verifiable" branch of `poll_verification` only ever reschedules with backoff and never sets a deadline itself. The same pattern (claim status via one CAS write, only schedule a deadline in a later, separate write) is duplicated across all three entry points (`execute`, `retry`, `supersede`), and for `retry()` specifically the intermediate `"retrying"` state is *not even a status `list_due_for_verification` recognizes as due*, so a crash in that even-narrower window produces a permanently invisible, never-polled record.

Separately, the new live evidence-reconciliation path (`_target_evidence_refresher` in `runtime.py`, feeding `reconcile_evidence`/`reconcile_ambiguous_submission`) does not validate the subscription id it derives from a record's own scope before using it to scope a live query, and the underlying `asset_exposures()` projection encodes "no findings for this asset" and "asset not found at all" as the identical empty result. Combined, an execution record with an unresolvable or empty subscription scope (a real, not merely theoretical, category for pre-Phase-03.2 legacy records) can be reported `reconciled_clean`, or have a `submission_ambiguous` failure promoted straight to `succeeded`, without the evidence refresher ever having queried the correct subscription. This is precisely the "false clean success" failure mode Recommendation 3 exists to prevent, now reintroduced one layer downstream.

Both are provable, both are outside what the phase's own test suite exercises (the phase's tests only ever transition through the full `execute()`/`retry()`/`supersede()` happy paths, which always do set a deadline, and only ever supply well-formed `subscription_id`s), and both directly bear on the phase's stated must-haves ("every provider-submitted execution reaches a terminal outcome by its deadline", "never report clean while KBs remain").

## Narrative Findings (AI reviewer)

### Critical

#### CR-01: The verification deadline is set one write *after* the CAS transition it is meant to bound, leaving a crash window in which a "running"/"retrying" record never reaches a terminal outcome — reproduced empirically

**File:** `src/intelligence/remediation/execution_service.py:188-195` (execute), `:502-517` (retry), `:644-651` (supersede), vs. the deadline being set only inside `_submit_and_record`'s own success (`:404-409`) and ambiguous-failure (`:348-355`) branches; `src/intelligence/remediation/execution_store.py:730-764` (`_needs_verification_pass` has no case for `"retrying"`)

**Issue:** `execute()`, `retry()`, and `supersede()` each perform two *separate* durable writes: (1) a CAS transition that claims `"queued"→"running"` (or `"retrying"→"running"`) with **no scheduling fields**, immediately followed by (2) a call into `_submit_and_record`, which is the only place `verification_deadline_at`/`next_verification_at` are ever set — and only on its own success or submission-ambiguous-failure paths. If the process crashes between (1) and (2) — a fully realistic event (OOM, node eviction, deploy rollout) since this is exactly the crash-safety boundary the store's own docstring calls out ("a process crash leaves an observable active attempt") — the persisted record has `status="running"`, `provider_job_id=""`, `verification_deadline_at=""`, `next_verification_at=""`.

On restart, `list_due_for_verification` correctly picks this record up (empty `next_verification_at` means "due now"), and `poll_verification` is called. But `_is_verification_deadline_exceeded` explicitly treats an empty deadline as "never expired" (its own docstring: "absence of a deadline is not the same as an expired one"), so the deadline check never fires. The verifier then returns `{"verifiable": False, "reason": "no provider job id"}` (no `provider_job_id` was ever recorded), which lands in the "not verifiable" branch — the *only* branch of `poll_verification` for a running record that neither sets a deadline nor reaches a terminal state. The record reschedules with capped backoff (5s→60s) **forever**.

I reproduced this directly against the real store/service classes (no mocks beyond a fake clock):

```
day 0:    status='running' deadline='' attempts=1
day 1:    status='running' deadline='' attempts=2
day 10:   status='running' deadline='' attempts=3
day 100:  status='running' deadline='' attempts=4
day 1000: status='running' deadline='' attempts=5
```

This is not a hypothetical — it is the exact class of bug CR-03/Recommendation 3 was written to eliminate ("Any unrecognized ARM status falls through to running… There is no max-age after which an execution becomes unknown/timed_out"), reintroduced at a narrower but still entirely reachable point.

The `retry()` path has a second, worse variant of the same root cause: `claim_retry()` first persists `status="retrying"` in its own CAS write, and *only the next, separate* `transition(...)` call moves it to `"running"`. `_needs_verification_pass` (`execution_store.py:730-764`) has branches for `"running"`, `"failed"`, and `"succeeded"` only — **no branch for `"retrying"`** — so a crash between `claim_retry()` and the subsequent transition leaves a record that is not merely undeadlined but *invisible to the coordinator, to `list_due_for_verification`, and to browser polling entirely*. `execution_view` also has no explicit reason string for `"retrying"`, so an operator reading it later sees the generic `"execution_not_retryable"` with no actionable path forward and no autonomous recovery — the exact opposite of this phase's goal.

**Fix:** Seed the scheduling fields in the *same* CAS write that claims `"running"`/`"retrying"`, not in a later write, so no crash window exists between claim and deadline:
```python
# execute() / retry() / supersede(), at the queued->running / retrying->running transition
record = self._store.transition(
    execution_id,
    expected_revision=int(record.get("revision") or 0),
    expected_status="queued",  # or {"retrying"} / etc.
    status="running",
    actor=requested_by,
    verification_deadline_at=(
        self._now() + timedelta(seconds=self._verification_deadline_seconds)
    ).isoformat(),
    next_verification_at=self._now().isoformat(),
    verification_attempts=0,
    now=self._now(),
)
```
and give `_needs_verification_pass` a `"retrying"` branch (treat it identically to `"running"` — due immediately if unscheduled) so a crash inside that even-narrower window is still recoverable rather than invisible. `_submit_and_record`'s own scheduling writes then become idempotent re-confirmations rather than the *only* place the deadline is ever established.

#### CR-02: The live evidence refresher can report "nothing missing" for an unresolvable/empty subscription scope, producing false `reconciled_clean` or false promotion of a submission-ambiguous failure to `succeeded`

**File:** `src/api/runtime.py:2933-2957` (`_target_evidence_refresher`); `src/intelligence/remediation/execution_store.py:653-673` (`execution_scope_attributes`); `src/intelligence/vulnerability/service.py:412-427` (`asset_exposures` groups only *active findings*, so an unmatched asset produces the same empty result as a genuinely clean one)

**Issue:** `_target_evidence_refresher(subscription_id, target_id)` is the sole live-evidence source for both `reconcile_evidence` (verified-succeeded patch executions) and `reconcile_ambiguous_submission` (previously-permanent ambiguity clearing) — both of which the phase's own `CONTEXT.md` explicitly warns must "never report clean while KBs remain" / must reconcile "only" on "a proven terminal provider result." The refresher does not validate `subscription_id` before use:
```python
def _target_evidence_refresher(subscription_id: str, target_id: str) -> dict[str, Any] | None:
    service = hybrid_vulnerability([subscription_id])   # no guard on subscription_id == ""
    if service is None:
        return None
    rows = service.asset_exposures()
    target_row = next((row for row in rows if str(row.get("asset_id") or "").casefold() == target_id.casefold()), None)
    missing_kbs = list(target_row.get("missing_kbs") or []) if target_row else []
    return {"missing_kbs": missing_kbs, "assessed_at": service.freshness}
```
`subscription_id` is supplied by `execution_scope_attributes(record).get("subscription", "")`, which — per its own docstring — returns `{}` (and therefore `""`) whenever a record has no stored `scope_attributes` *and* its immutable snapshot's `target_id` does not parse a `/subscriptions/{id}/` segment. This is a real, not merely theoretical, category: legacy pre-Phase-03.2 execution records (the exact class `orphaned_executions()` elsewhere in this same file is designed to detect) predate `scope_attributes` entirely.

`hybrid_vulnerability([""])` is passed straight through to `LiveResourceProvider.query`, whose only guard is `if not subscription_ids: raise` — but `[""]` is a non-empty *list* containing an empty string, so that guard does not fire. The call proceeds to Azure Resource Graph with `"subscriptions": [""]` in the request body. Whether ARG's real API hard-errors or silently returns zero rows for a malformed subscription id is not verifiable from this codebase alone, but *either* is a live, reachable outcome given the code path, and the "zero rows" outcome is indistinguishable downstream from "this asset has no exposures" — `asset_exposures()` (in `intelligence/vulnerability/service.py`) only emits a row when `by_server[server_id]` has at least one *active* finding; an asset that was never queried (wrong subscription scope) produces exactly the same absent-row result as an asset that is genuinely fully patched. `_target_evidence_refresher` explicitly documents this conflation as *intentional* for the genuinely-clean case ("an empty exposure list for the target is itself evidence that nothing is missing") — but that reasoning silently also covers the wrong-scope case, since both produce `target_row is None → missing_kbs=[]`.

The consequence reaches both reconciliation methods: `reconcile_evidence` would compute `kbs_remaining = selected & set() = []` → `reconciled_clean`, and `reconcile_ambiguous_submission` would satisfy `if selected and not kbs_remaining:` → promote a `submission_ambiguous` failure straight to `status="succeeded"`, `verified_state="reconciled_from_target_evidence"` — clearing a safety brake that exists specifically because the operation's true outcome against the provider is unknown, based on evidence that was never actually collected against the right (or any) subscription.

**Fix:** Fail closed on an unresolvable subscription rather than querying with it:
```python
def _target_evidence_refresher(subscription_id: str, target_id: str) -> dict[str, Any] | None:
    if not subscription_id.strip() or not target_id.strip():
        return None  # unresolvable scope: unavailable, not "nothing missing"
    service = hybrid_vulnerability([subscription_id])
    ...
```
and consider having `asset_exposures()` (or a narrower single-asset lookup) distinguish "asset not observed in this subscription's inventory at all" from "asset observed with zero active findings," so the refresher's own "empty means clean" reasoning is only ever applied to the case it was designed for.

#### WR-01: `ExecutionVerifier.verify()` does not treat a non-zero `pending_count` as failure/partial-success, despite `CONTEXT.md`'s explicit "partial success … never clean success" decision

**File:** `src/intelligence/remediation/execution_verifier.py:160-187`

**Issue:** The nested-failure check is `detail["detail_status"].casefold() == "completedwithwarnings" or detail["failed_count"] > 0` only. Reproduced directly:
```
properties: installedPatchCount=3, failedPatchCount=0, pendingPatchCount=7 (of 10 selected)
=> {'outcome': 'succeeded', 'verified_state': 'Succeeded', 'verification_evidence': {..., 'pending_count': 7, ...}}
```
Only 3 of 10 selected patches installed, 7 still pending, yet the raw ARM-verification `outcome`/`verified_state` read as a clean `"succeeded"`. This is materially mitigated in practice because `reconcile_evidence` independently re-checks live target evidence against the *selected KB set* regardless of what `verify()` concluded, and the phase's own design explicitly does not let evidence reconciliation widen a provider "succeeded" outcome — so the eventual `evidence_reconciliation.status` should still catch a genuinely-still-missing KB. However, `verify()`'s own `outcome`/`verified_state` fields are consumed directly in several places (`poll_verification`'s status transition, any future direct consumer of the execution record) without waiting for reconciliation, so a "succeeded" label with 7/10 patches still pending is a real, currently-uncaught precision gap relative to the stated goal.

**Fix:** Extend the nested-failure predicate to also flag material incompleteness:
```python
nested_failed = (
    detail["detail_status"].casefold() in {"completedwithwarnings", "partialsuccess", "timedout"}
    or detail["failed_count"] > 0
    or detail["pending_count"] > 0
)
```
(or, at minimum, surface a distinct `"succeeded_with_pending_patches"` `verified_state` rather than an unqualified `"Succeeded"`, so a consumer reading the raw outcome cannot mistake it for a fully clean result).

```python
if snapshot.get("snapshot_kind") == "defender_configuration":
```

```python
if context.verification_coordinator_provider is None:
```

#### WR-04: `_claim_lock`'s 5-second contention timeout surfaces as an undifferentiated `RuntimeError`, counted as an "errored" pass by the coordinator under legitimate multi-replica load

**File:** `src/intelligence/remediation/execution_store.py:536-559` (`_claim_lock`); `src/intelligence/remediation/verification_coordinator.py:75-93` (`run_once`'s generic `except Exception`)

**Issue:** Under multiple concurrent workers/replicas all running their own verification-coordinator thread against the same durable store, `_claim_lock` retries for up to 5 seconds before letting `RunLock.__enter__()`'s `RuntimeError` propagate. This is correctly absorbed by the coordinator's per-record `except Exception` (so it cannot crash the batch), but it is logged identically to a genuine bug (`remediation_verification_pass_failed`) and counted in `errored`, with no way for an operator to distinguish "transient multi-replica lock contention, will resolve on its own next pass" from "an actual defect in verification logic." This is a diagnosability gap, not a correctness one, but the review was explicitly asked to assess multi-worker behavior and this is the one place where legitimate multi-replica concurrency produces visible errors rather than silent, cheap retries.

**Fix:** Let `RunLock`'s contention error carry (or the coordinator catch) a distinguishable type/attribute so `run_once` can count it separately (e.g., `"skipped_contended"`) rather than folding it into `"errored"`.

#### WR-05: The coordinator's background thread introduces a new, unlocked concurrent-access pattern on the pre-existing process-global `hybrid_vulnerability` cache

**File:** `src/api/runtime.py` (`_hybrid_vulnerability_cache` module-level dict; `hybrid_vulnerability`, read at `_target_evidence_refresher`)

**Issue:** `_hybrid_vulnerability_cache` is a plain, unlocked module-level dict, previously only ever read/written from FastAPI request-handling threads. #### CR-03 (NEW): WR-01's own fix misclassifies a genuinely still-in-progress patch installation as terminally "failed," reintroducing a worse-in-kind version of the exact problem WR-01 was meant to close — reproduced empirically end-to-end

**File:** `src/intelligence/remediation/execution_verifier.py:178-195` (the `nested_failed` predicate, unconditional on ARM envelope status)

Reproduced directly against the real `ExecutionVerifier` class:

```python

        "installedPatchCount": 3, "failedPatchCount": 0, "pendingPatchCount": 7}}
verifier.verify(record)
# => {'outcome': 'failed', 'verified_state': 'succeeded_with_pending_patches', ...}
```

3 of 10 selected patches installed so far, 0 failed, 7 not yet processed — completely ordinary mid-flight progress for Update Manager's own progressive count reporting — is reported as a terminal failure while Azure is still actively working. is_terminal_envelope = normalized in (
```python
    _TERMINAL_SUCCEEDED_STATUSES | _TERMINAL_FAILED_STATUSES | _TERMINAL_CANCELLED_STATUSES
)
nested_failed = is_terminal_envelope and (
    detail["detail_status"].casefold() in {"completedwithwarnings", "partialsuccess", "timedout"}
    or detail["failed_count"] > 0
    or detail["pending_count"] > 0
)
```
(`failed_count > 0` arguably deserves the same envelope-terminal gate for consistency, though a genuine mid-flight failed-patch count is a weaker false-positive risk than a mid-flight pending count, since most installs have `pending > 0` for nearly their entire duration but `failed > 0` only when something has actually gone wrong.) ### New finding — this pass

#### CR-04 (NEW, pre-existing — not introduced by any 03.4 fix pass): `ExecutionVerifier._poll()` sends a hardcoded literal `"******"` string as the Authorization header, never the real bearer token — every live verification poll against Azure ARM will fail authentication

**File:** `src/intelligence/remediation/execution_verifier.py:301-303` (`_poll`), vs. the unused `_token()` method (`:285-299`)

**Issue:** `ExecutionVerifier._token()` correctly acquires a real management token via `self._credential.get_token(ARM_SCOPE)`, but it is **never called anywhere in the module**:
```python
def _poll(self, operation_url: str) -> httpx.Response:
    headers = {"Authorization": f"******"}
    client = self._client or httpx.Client(timeout=self._timeout)
    ...
```
This is not a redaction of secret text in a log/display path — it is the literal HTTP header sent on every real request. Reproduced empirically against the real class (fake transport recording the actual header the class sends, not a test that merely ignores header content the way every existing test in `tests/test_remediation_execution_verifier.py`/`tests/test_remediation_verification_review_fixes.py` does):
```
Captured Authorization header: '******'
```
Against real Azure Resource Manager, this will deterministically return `401 Unauthorized` on every poll, which `_poll` converts to `ExecutionVerificationUnavailable` (correct fail-closed handling of the symptom) — but the root cause means the phase's central, stated goal ("move remediation verification into a bounded server-side lifecycle... interpret complete Azure patch-operation results") cannot be met against a live environment at all: every running execution will exhaust its retries/attempts and eventually hit `verification_deadline_exceeded` via the "not verifiable"/unavailable path, never once successfully learning Azure's real outcome. Production wiring confirmed reachable: `_execution_verifier()` (`runtime.py:2400-2406`) constructs `ExecutionVerifier(credential=credential)` with no `client=` override, so `_client` is `None` and the bare, header-broken `httpx.Client` path above is exactly what runs in production.

This is not new to this session — `git log -p` shows the line has read `f"******"` unchanged since its introduction in commit `fdf704b0` ("poll upstream ARM operation URL for verified execution outcome"), predating Phase 03.4 entirely, and is untouched by any of this phase's three diffs. It was invisible to every prior review pass (the original deep review, the fixer's two passes, and the first final re-review) and to the entire test suite, because no test — old or new, including all of this session's own new regression tests — ever asserts on the actual header value sent; every fake transport in the suite accepts any header. An identical instance of the same broken pattern exists in the sibling adapter this verifier is meant to check, `src/operations/patching/azure_adapter.py:163-165` (`_post`, the actual mutating patch-submission POST) — also pre-existing, also untouched by any Phase 03.x diff (confirmed via `git diff`), also invisible to its own test suite for the same reason. The correctly-implemented sibling adapter, `src/operations/defender_configuration.py:224-225`, shows the intended pattern (`"Authorization": "Bearer " + token`) and proves this is a fixable, isolated defect rather than an inherent limitation.

**Fix:**
```python
def _poll(self, operation_url: str) -> httpx.Response:
    headers = {"Authorization": f"Bearer {self._token()}"}
    ...
```
(mirroring `defender_configuration.py`'s already-correct pattern exactly), and add a regression test asserting the actual header value sent (e.g. a `FakeTransport` that records `request.headers["authorization"]` and asserts it starts with `"Bearer "` and contains the token the fake credential returned) so this class of defect cannot silently reappear. The same fix is very likely warranted in `azure_adapter.py:163-165`, though that file's diff is outside this phase's own touched-file scope and is called out here only as corroborating evidence of the pattern, not as this phase's own regression.
