<objective>
Give the remediation execution store durable verification scheduling/deadline
metadata and give the ARM verifier deep nested-result parsing, so that Plan
03.4-02's service layer and Plan 03.4-03's background coordinator can build a
bounded, restart-safe autonomous verification lifecycle on top of them
without inventing a second execution state machine (Recommendation 3,
Verification Lifecycle and Azure Result Semantics decisions in
03.4-CONTEXT.md).

This plan touches only the store and the read-only verifier -- it adds
fields and a query, and it deepens result parsing. It does not change any
execution lifecycle behavior yet (that is Plan 03.4-02); every new field
defaults to an inert/empty value until Plan 03.4-02 starts writing to it.

Purpose: Make "what needs verifying right now, durably" and "what did Azure
actually report, in full nested detail" both answerable from disk alone, so
a process restart loses no in-flight verification state and a partially
failed patch run can never be misread as a clean success.
Output: RemediationExecutionStore carries scheduling/deadline/evidence
fields and a `list_due_for_verification` query; ExecutionVerifier.verify()
returns structured installed/failed/pending/not-selected counts and
provider error text extracted from the ARM operation's nested `properties`
body, in addition to its existing envelope-level outcome.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Azure ARM response -> ExecutionVerifier | The ARM operation-status JSON body is untrusted external input; only its `status`/nested `properties.*` shape is trusted to inform outcome, never used to construct a command or path. |
| Durable execution record (disk/OneLake) -> future process | A record read back after restart must not let a malformed/legacy document crash the store or silently vanish work. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.4-01 | Tampering | ExecutionVerifier._parse_patch_properties | medium | mitigate | All nested-properties extraction uses isinstance guards and max(0, int(...)) coercion with try/except, so a malformed or adversarial-shaped ARM/Defender response body cannot raise an unhandled exception or coerce a negative/non-numeric count; provider error text is truncated to 500 chars before being persisted, matching the existing _error_message convention. |
| T-03.4-02 | Denial of Service | RemediationExecutionStore._read_state via list_due_for_verification | low | accept | The method is read-only and bounded by the existing max_executions store cap (already enforced by create_or_get/create_superseding); no new unbounded growth path is introduced in this plan. |
| T-03.4-03 | Information Disclosure | verification_evidence.provider_errors | low | accept | Provider error text originates from Azure's own operation-status response (already a source the operator is authorized to see via the existing failure_details field) and is truncated identically to the pre-existing _error_message helper; no new external input source is introduced. |
| T-03.4-SC | Tampering | Supply chain (no new packages) | n/a | accept | This plan adds no new pip/npm/cargo dependency; the existing Package Legitimacy Audit gate does not apply. |
