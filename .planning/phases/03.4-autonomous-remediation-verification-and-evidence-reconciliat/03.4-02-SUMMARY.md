# Phase 03.4 Plan 02: Deadline-aware verification, evidence reconciliation, and ambiguity clearing Summary

Turned Plan 03.4-01's durable scheduling fields into actual bounded lifecycle behavior: `poll_verification` now checks the deadline before ever touching the verifier, `reconcile_evidence` compares a verified-succeeded patch execution's immutable selected KBs against freshly refreshed live target evidence without ever widening Azure's own reported outcome, and `reconcile_ambiguous_submission` gives a previously-permanent `submission_ambiguous` dead end two honest exits: proven success, or a bounded reclassification to an ordinary retryable failure.

## Accomplishments

- `VERIFICATION_DEADLINE_SECONDS = 1800` module constant plus `verification_deadline_seconds`/`target_evidence_refresher` constructor parameters on `RemediationExecutionService`.
- `execute()`'s successful-submission transition and the ambiguous-submission-failure transition (inside `_submit_and_record`'s exception handler) both now seed `verification_deadline_at`/`next_verification_at`/`verification_attempts=0` -- a plain non-ambiguous failure gets none of this scheduling since it has nothing left to reconcile.
- `poll_verification` rewritten deadline-first: an expired deadline transitions straight to `status="failed"`, `outcome="unknown"`, `failure_class="verification_timed_out"` before the verifier is ever called; every other branch (degraded/still-running/succeeded/failed/cancelled) now also persists `verification_evidence`, bumps `verification_attempts`, and (for non-terminal branches) reschedules `next_verification_at` via `_next_backoff_seconds` (capped exponential: 5,10,20,40,60,60...). The succeeded branch additionally restarts the deadline window so a freshly-succeeded patch record is immediately due for evidence reconciliation.
- `reconcile_evidence(execution_id)`: no-op for defender_configuration/empty-patch_ids records or already-terminally-reconciled ones; compares `execution_snapshot.patch_ids` against the injected refresher's `missing_kbs`, recording `reconciled_clean`/`reconciled_incomplete` while leaving `status` untouched at `"succeeded"`; a missing/raising/empty refresher result is `"pending"` (retried with backoff) until the deadline, then terminally `"unreconciled"`.
- `reconcile_ambiguous_submission(execution_id)`: promotes a submission-ambiguous failure to `status="succeeded"`, `failure_class=""`, `verified_state="reconciled_from_target_evidence"` only when the refresher proves every selected KB installed; otherwise stays ambiguous within the deadline (bounded backoff) or reclassifies to `failure_class="submission_unconfirmed"`/`verified_state="reconciliation_timed_out"` past it -- an ordinary bounded, retryable/supersedable failure at that point. A defender_configuration or empty-patch_ids ambiguous failure skips the refresher call entirely (no comparable KB evidence exists) and applies only the deadline branch.
- `_transition_or_current` -- one shared private helper wrapping `self._store.transition(...)` in `try/except ExecutionClaimConflict: return self.execution_view(self._store.get(execution_id))`, used by all three of `poll_verification`, `reconcile_evidence`, and `reconcile_ambiguous_submission` so a losing concurrent caller always reads back the winner's already-persisted, equally valid outcome instead of raising.

## Deviations from Plan

**1. [Rule 1 - Test fixture bug, not implementation]** The first evidence-reconciliation test run silently swallowed its own `assert`-based fixture checks because the refresher callable is invoked inside a `try/except Exception` in `_refresh_target_evidence` (by design, per CONTEXT.md: a refresher failure must never propagate) -- `AssertionError` is an `Exception` subclass, so an assertion inside a test's fake refresher was caught as "refresher unavailable" instead of failing loudly. Fixed by moving the assertions out of the refresher body into a `calls` list checked after the call. No production code changed; this was purely a test-authoring pitfall worth flagging for future work in this area.
- **Found during:** Task 2, writing `test_reconcile_evidence_incomplete_when_selected_kbs_remain`.
- **Fix:** Replaced in-refresher `assert` statements with a `calls.append(...)` recorder, asserted after the call.
- **Files modified:** tests/test_remediation_evidence_reconciliation.py.

**2. [Rule 1 - Test fixture gap]** The shared test plan fixture's `resource` dict lacked a `subscription_id` key. Since `execution_scope_attributes` only falls back to deriving the subscription from the execution snapshot's `target_id` when the record's stored `scope_attributes` dict is *entirely* empty, and this fixture's plan had non-empty `business_service`/`application` scope attributes (but no `subscription`), the refresher was called with an empty `subscription_id`. Fixed by adding `"subscription_id": "sub-1"` to the test plan's `resource` dict (matching how real `LiveRemediationPlanner`-sourced plans already populate it). No production code changed.
- **Found during:** Task 2, same test as above.
- **Fix:** Added `subscription_id` to the test fixture's `resource` dict.
- **Files modified:** tests/test_remediation_evidence_reconciliation.py.
