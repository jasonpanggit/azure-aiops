<objective>
Turn Plan 03.4-01's durable scheduling fields and deep verifier parsing into
actual bounded lifecycle behavior: a deadline that terminates stuck
verifications honestly, an evidence-reconciliation step that refuses to call
a patch run "clean" while its selected KBs remain, and a
submission-ambiguity reconciliation path that is currently a permanent dead
end in the codebase (retry()/supersede() both refuse forever on
failure_class == "submission_ambiguous" and nothing today ever clears that
classification -- confirmed by reading execution_service.py's retry()/
_supersede_eligibility comments, which explicitly defer this to "Phase
03.4's verification worker").

This closes Recommendation 3's Deadline and Recovery, Evidence
Reconciliation, and the ambiguity-clearing half of Azure Result Semantics
(03.4-CONTEXT.md), reusing the existing execution-store CAS transitions
exclusively -- no new execution status value, no second state machine.

Purpose: Make "terminal" mean something honest (a real Azure result, a real
KB check, or an explicit, actionable timeout) and make an ambiguous
submission recoverable without ever guessing at what Azure actually did.
Output: RemediationExecutionService gains deadline-aware poll_verification,
reconcile_evidence, and reconcile_ambiguous_submission, all safe under
concurrent callers.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| target_evidence_refresher callable -> RemediationExecutionService | The refresher returns live Azure assessment data (subscription-scoped ARG read via Plan 03.4-03's wiring); this plan treats it as untrusted-shape input (may be None, may raise, may return an unexpected dict shape) and never lets a refresher failure block a terminal deadline outcome. |
| Concurrent callers (browser read path + background coordinator) -> execution_store CAS | Two processes/threads may race to transition the same execution_id; the existing revision-and-status CAS is the only serialization boundary, and this plan must never let a lost race surface as an unhandled exception to an HTTP caller. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.4-04 | Denial of Service | poll_verification / reconcile_* deadline logic | high | mitigate | Every non-terminal branch (still-running, still-ambiguous, still-pending-evidence) is bounded by verification_deadline_at and a capped exponential backoff (_next_backoff_seconds, ceiling 60s); no execution can stay "running" or "submission_ambiguous" indefinitely -- this is the direct fix for CR-03's "if the operator closes the tab, the execution stays running forever" finding. |
| T-03.4-05 | Elevation of Privilege | reconcile_ambiguous_submission's proven-success promotion | high | mitigate | Promotion from failed/ambiguous to succeeded requires the refreshed target evidence to show every one of the immutable execution_snapshot's own selected patch_ids installed -- never a caller-supplied or partial match; the snapshot itself was already hash-bound and validated at approval time (Phase 3), so this plan cannot be used to launder an unapproved outcome. |
| T-03.4-06 | Tampering | Concurrent CAS transitions on one execution record | medium | mitigate | _transition_or_current relies exclusively on the pre-existing expected_revision/expected_status compare-and-set in RemediationExecutionStore.transition; a losing caller only ever reads back the winner's already-persisted, equally-authorized record -- it can never apply its own now-stale intent on top. |
| T-03.4-07 | Repudiation | evidence_reconciliation / verification_evidence audit trail | low | accept | Every reconciliation decision (cleared/remaining KBs, timed-out reclassification) is persisted on the durable, revisioned, append-only-history execution record exactly like every other Phase 3 lifecycle transition -- no new unaudited write path is introduced. |
