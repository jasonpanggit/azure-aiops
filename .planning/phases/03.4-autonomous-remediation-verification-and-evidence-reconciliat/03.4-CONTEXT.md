# Phase 03.4: Autonomous Remediation Verification and Evidence Reconciliation - Context

**Gathered:** 2026-09-04
**Status:** Ready for planning
**Mode:** Autonomous decisions derived from Phase 03 deep review

<domain>
## Phase Boundary

Move remediation verification into a bounded server-side lifecycle that does
not depend on an open browser, interpret complete Azure patch-operation
results, and reconcile a verified success against refreshed target evidence.
Approval governance and operator-facing workflow presentation remain in Phases
03.5 and 03.6.

</domain>

<decisions>
## Implementation Decisions

### Verification Lifecycle
- Persist verification scheduling/deadline metadata on the execution record and resume non-terminal work after process restart.
- Use one bounded background coordinator with existing execution-store CAS transitions; do not create a second execution state machine.
- Browser polling remains a read convenience and may opportunistically advance verification, but correctness must not depend on it.
- Every provider-submitted execution reaches a terminal outcome by its configured deadline.

### Azure Result Semantics
- Interpret both envelope and nested `properties.status`.
- Treat failed patch count, explicit error details, partial success, and completed-with-warnings as failure, never clean success.
- Preserve structured installed/failed/pending counts and provider errors in verification evidence.
- Reconcile submission-ambiguous executions before allowing retry or supersession; only a proven terminal provider result clears ambiguity.

### Deadline and Recovery
- A verification deadline produces a terminal `unknown`/`verification_timed_out` outcome with actionable guidance, not indefinite `running`.
- Transient poll failures back off within the deadline; persistent failures terminate explicitly.
- Worker operations must be idempotent and safe under concurrent browser polling or multiple process workers.

### Evidence Reconciliation
- After provider success, trigger the narrowest available live assessment refresh for the target; do not wait for a full Fabric publication.
- Compare the immutable selected KB set with refreshed evidence and persist `kbs_cleared`, `kbs_remaining`, assessment timestamp, and reconciliation status.
- Selected KBs remaining means the remediation is not reported clean even if Azure's operation envelope says succeeded.
- If assessment is unavailable by deadline, preserve provider success separately but expose an explicit unreconciled terminal outcome.

### the agent's Discretion
- The worker may use the repository's existing application-lifespan/background-loop pattern or a testable coordinator service, provided startup/shutdown are bounded and deterministic in tests.

</decisions>

## Existing Code Insights

### Reusable Assets
- `ExecutionVerifier` already polls ARM operation locations and is invoked through `RemediationExecutionService.poll_verification`.
- `RemediationExecutionStore.transition` provides revision/status CAS.
- Phase 03.3 added `provider_submitted`, `failure_class`, and ambiguity guards.
- Inventory/vulnerability services expose current target patch evidence.

### Established Patterns
- Provider submission status and actual-state verification remain distinct.
- Durable records preserve immutable execution snapshots and append-only history.
- Runtime providers are constructed through `src/api/runtime.py`; FastAPI lifecycle wiring already hosts background operational services.

### Integration Points
- `src/intelligence/remediation/execution_verifier.py` for deep ARM parsing.
- `src/intelligence/remediation/execution_service.py` for CAS-safe verification and reconciliation.
- `src/intelligence/remediation/execution_store.py` for schedule/deadline/evidence fields.
- `src/api/runtime.py` and application lifespan/startup for the autonomous coordinator.
- Existing vulnerability/patch assessment reads for target-scoped reconciliation.

</code_context>

<specifics>
## Specific Ideas

Tests must prove: no browser request is needed for a submitted execution to
terminate; nested `CompletedWithWarnings` plus failed patches is failed; a
deadline produces an explicit terminal unknown state; successful provider work
with selected KBs still present is not reported clean; and an ambiguous
submission remains non-retryable until provider reconciliation proves terminal.

</specifics>
