# Phase 03.4 Plan 03: Autonomous background coordinator + runtime wiring Summary

Gave the API process an autonomous, bounded, restart-safe background worker that drives every non-terminal or unreconciled remediation execution to a real terminal outcome, using exactly the store/service machinery Plans 03.4-01 and 03.4-02 already built. Closes Recommendation 3's central finding (CR-03) for good: an execution's fate no longer depends on anyone's browser session, and the process can be killed and restarted without losing track of in-flight work.

## Accomplishments

- `src/intelligence/remediation/verification_coordinator.py` -- `RemediationVerificationCoordinator`, constructed with `execution_store`, `execution_service`, and an injectable `now` callable. `run_once(now)` calls `execution_store.list_due_for_verification(now=now)` and dispatches each returned record purely by shape (`"running"` -> `poll_verification`; `"failed"` + submission-ambiguous -> `reconcile_ambiguous_submission`; `"succeeded"` -> `reconcile_evidence`), catching and logging (`remediation_verification_pass_failed`) any per-record exception so one failing record never blocks the batch. Returns `{"processed": int, "errored": int}`. The module imports no FastAPI/HTTP/threading symbol at all, so it is directly constructible and callable in a plain unit test with fakes.
- `src/api/dependencies.py`: `ApiContext.verification_coordinator_provider: Callable[[], Any] | None = None`, following the existing provider-field comment convention.
- `src/api/runtime.py`: `_target_evidence_refresher(subscription_id, target_id)` (a `build_context()`-local closure, since it calls the equally-local `hybrid_vulnerability`) resolves live missing-KB evidence via the existing per-request TTL-cached ARG path -- returns `None` only when no vulnerability service is configured for the subscription; an empty exposure list for the target is itself "nothing missing" evidence, not an unavailable signal. `ENV_REMEDIATION_VERIFICATION_DEADLINE_SECONDS` (`AIOPS_REMEDIATION_VERIFICATION_DEADLINE_SECONDS`) optionally overrides `VERIFICATION_DEADLINE_SECONDS`, read once per `_execution_service_for_scope`/`_verification_coordinator` call. `_verification_coordinator()` builds the coordinator's own `RemediationExecutionService` with `plan_repository=None, patching_service=None` (it never calls `execute`/`retry`/`supersede`) and is wired into `ApiContext(...)` as `verification_coordinator_provider`.
- `src/api/app.py`: `_start_verification_coordinator(app, context)` mirrors `_start_background_refresh` exactly -- `threading.Event`, a daemon thread named `"remediation-verification-coordinator"`, a 10-second poll interval (shorter than provider-refresh, since per-record backoff already caps at 60s), an immediate first pass at thread start (mirroring the provider-refresh loop's immediate forced refresh), per-pass `try/except` logging, and a `5`-second-timeout `@app.on_event("shutdown")` join. Guarded internally by `if context.verification_coordinator_provider is None: return`, so every existing API test (which constructs `ApiContext` directly, not via `build_context()`) starts no new thread and is completely unaffected.

## Deviations from Plan

**1. [Rule 3 - blocking issue, resolved via closure scoping]** The plan's literal phrasing calls for "a module-level `_verification_coordinator()` singleton builder ... constructing `RemediationVerificationCoordinator(..., target_evidence_refresher=_target_evidence_refresher)`", but `_target_evidence_refresher` itself must call `hybrid_vulnerability`, which is a per-request TTL-cached closure defined inside `build_context()` -- it does not exist at true module scope. A truly module-level `_verification_coordinator()` cannot reference it. Resolved by defining both `_target_evidence_refresher` and `_verification_coordinator` as closures nested inside `build_context()` (alongside the structurally identical `_execution_service_for_scope`), preserving every behavioral requirement (one coordinator instance per `build_context()` call, wired into `ApiContext` as a provider) without the literal "module-level" placement. No behavior differs from what the plan's tests require; `build_context()` is called once per process at startup, so this is not a per-request cost.
- **Found during:** Task 2.
- **Fix:** Nested closures inside `build_context()` instead of true module-level functions.
- **Files modified:** src/api/runtime.py.
