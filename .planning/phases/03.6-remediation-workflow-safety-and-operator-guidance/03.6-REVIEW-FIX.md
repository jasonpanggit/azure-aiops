### WR-02: Unrecognized blocker-code telemetry is wired only in `WorkflowBlockers`, not in the two other `blockerCopy()` call sites

**Files modified:** `web/src/app/remediation/blockers.ts`,
`web/src/app/remediation/page.tsx`, `web/src/app/remediation/page.test.tsx`
(new file: `web/src/app/remediation/blockers.test.ts`)
**Commit:** none (no commits made this session, per instruction)
**Applied fix:**
- Centralized the "seen unknown codes" tracking out of `WorkflowBlockers`'s local
  `useRef<Set<string>>` into a new module-level singleton
  (`seenUnknownBlockerCodes`) inside `blockers.ts`, behind a new exported
  `blockerCopyWithTelemetry(code, serverStep, serverMessage?, serverNextAction?,
  serverSeverity?)` function that wraps `blockerCopy` and fires
  `console.warn("remediation.blocker.unknown_code", { code })` exactly once per
  distinct unrecognized code for the lifetime of the module — mirroring
  `blockerCopy`'s own "unrecognized" condition (absent from `BLOCKER_VOCABULARY`
  and no server-supplied `message`).
- All three render-path call sites in `page.tsx` — `WorkflowBlockers`,
  `stepBlockerEcho`, and `RecoveryControls`'s supersede-ineligibility-reason
  callout — now call `blockerCopyWithTelemetry` instead of the bare
  `blockerCopy`. The bare `blockerCopy` export remains for direct/pure lookups
  where no telemetry is desired.
- Removed `WorkflowBlockers`'s now-redundant local `useRef`/inline
  unrecognized-code check (the shared helper subsumes it).
- Added focused tests: a new `web/src/app/remediation/blockers.test.ts` unit-tests
  `blockerCopyWithTelemetry` directly (once-per-code dedup, independent codes,
  recognized-code no-telemetry, server-message-present no-telemetry, and dedup
  across the two distinct call-site shapes) — 5 tests, all passing in isolation
  from the full page render. Added one new `page.test.tsx` integration test
  ("logs unknown-code telemetry (WR-02) when a supersede race refusal returns a
  reason RecoveryControls has never seen via workflow.blockers[]") proving the
  `RecoveryControls` call site telemeters independently — it uses a code that
  never appears in `workflow.blockers[]`, so the telemetry cannot be attributed
  to `WorkflowBlockers` firing first for the same code.
- Verification: `cd web && npx vitest run src/app/remediation/page.test.tsx
  src/app/remediation/blockers.test.ts` — **52 passed** (46 in `page.test.tsx`
  per `03.6-REVIEW.md`'s baseline + 1 new `page.test.tsx` integration test = 47,
  plus 5 new tests in the new `blockers.test.ts` = 52 total). `cd web &&
  npx tsc --noEmit` — clean. `cd web && npx playwright test
  e2e/remediation-workflow-safety.spec.ts` — 4 passed (unaffected by this
  frontend-internal refactor, confirming no regression to the real-browser
