# Phase 03.6 — UI Design Contract

> Visual and interaction contract for remediation workflow safety and operator guidance.
> This closes Phase 03 deep-review Recommendation 5: it makes the existing five-step
> `/remediation` workflow (`web/src/app/remediation/page.tsx`) explain its real safety
> state — server-computed blockers and degradation, honest step outcomes, a fail-safe
> patch picker, authoritative cancel/retry/supersede controls, and bounded polling. It
> consumes the durable identity, retry/supersession, verification, and approval contracts
> already implemented in Phases 03.2–03.5 without redesigning them.

---

## Phase Boundary (do not exceed)

**In scope for this contract:**

1. A `blockers[]` panel: every `ineligibility_reason`/`failure_class` the backend can emit
   maps to a rendered sentence, an affected step, and a concrete next action — including a
   safe fallback for any code not yet in the locked vocabulary below.
2. A `degradation[]` panel surfaced before the Approve and Run controls (also rendered on
   Review, since degraded evidence changes what "impact" means there).
3. Honest step projection: the `verify` step (and, transitively, the step nav's status
   text) reflects execution *outcome*, never mere existence or terminality.
4. A fail-safe patch picker: `null` = all eligible, non-empty array = exactly that
   explicit set, empty is refused client-side and never silently reinterpreted as "all".
5. Cancel / Retry / Supersede controls, each independently gated by its own
   server-authoritative boolean and reason — plus permanent visibility of remaining
   attempts, verification deadline, evidence reconciliation, and supersession lineage.
6. Bounded, deterministic client polling with backoff and a hard ceiling.

**Explicitly preserved, not redesigned:**

- The five-step nav (`Select fix → Review impact → Approve → Run → Verify`), its markup,
  labels, and keyboard behavior (`03.5-UI-SPEC.md`'s Five-Step Workflow Preservation
  Contract — unchanged, extended, never replaced).
- The Phase 03.5 Approval Requirement Contract, Demo Self-Approval Disclosure Contract,
  Approve vs Operate Authorization Contract, and Stale Approval State Contract — this
  phase adds blockers/degradation/recovery controls *around* them, never restyles or
  reorders them.
- Existing spacing/typography/color tokens and component set (`PageHeader`, `EvidenceBar`,
  `StatePanel`, `StatusBadge`, `StructuredData`). No shadcn initialization.
- The responsive collapse breakpoint (`900px`, single-column) already declared in
  `globals.css:6450-6456`.

`web/src/app/remediation/` beside the existing `ApprovalRequirementsList`/`ApprovalStatusLine`/
`ExecutionAudit`.

### Visual direction

- Blockers and degradation are **disclosure, not decoration**: every row carries a text
  sentence and a named next action; color/tone never stands alone.
- A blocked step is visually distinct from a merely-pending one (never identical gray
  text), but the step nav's five-cell grid layout, button shape, and index numerals do not
  change — only the existing `<small>{status}</small>` text's color token changes.
- Degradation uses the same amber `Stale`/warning treatment already established in
  `03.1-UI-SPEC.md`'s Source-Specific State Contract — never success green, never
  represented as a healthy-empty state.
- Recovery controls (Cancel/Retry/Supersede) are never all three enabled at once for the
  same execution in ordinary operation — each renders strictly from its own server field,
  so the visible set is whatever is truthfully eligible, including zero controls.
- Reconciliation results that show remaining KBs use warning tone even though the
  provider-level status is "succeeded" — a verified success is never re-painted as
  success-green when the change is not provably complete.

## Blocker Contract (`workflow.blockers[]`)

Replaces the current silent/partial rendering — today only `can_approve`/`can_operate`
reasons (Phase 03.5) render at all; every other `ineligibility_reason` value the backend
already produces (see Blocker Vocabulary below) is either dropped or shown as an opaque
generic message.

### Required data shape

```
workflow.blockers: Array<{
  code: string;               // machine-readable, matches an existing `reason`/
                               // `ineligibility_reason`/`failure_class` value
  message: string;             // human sentence — server-provided; client falls back to
                                // the locked table below only if the server omits it
  step: "select" | "review" | "approve" | "run" | "verify";
  next_action: string;         // concrete next operator action — same fallback rule
  severity?: "warning" | "critical";  // client derives from the table below if absent —
                                       // never "info"; a row that requires no action is not
                                       // a blocker at all (see "Excluded from Blockers" below)
}>
```

- A blocker never disappears for an unrecognized `code` — the client always renders
  *something*: the server's own `message`/`next_action` if present, otherwise the safe
  fallback row (see below), never a blank/omitted row.
- An unrecognized code additionally logs one client-side telemetry event
  (`console.warn("remediation.blocker.unknown_code", { code })` at minimum — actual
  telemetry sink is an implementation detail, but the call site is required) exactly once
  per distinct code per page load, never repeated per render.

### Placement

Two rendering locations, both required, showing the *same* blocker rows (no duplication of
data, only of presentation):

1. **Cross-step summary panel** (`<section className="remediation-blockers">`), rendered
   directly beneath the five-step nav (`.remediation-workflow-steps`) and above the
   `remediation-workflow-layout` grid, whenever `workflow.blockers.length > 0`. Each row
   shows: `StatusBadge` (severity tone, label `Blocked`) · the affected step's label as a
   small chip (e.g. `Approve`) · the message · the next action as a bold-led sentence
   (`Next: {next_action}`). This lets an operator on "Run" see an unmet "Approve" blocker
   without switching tabs. Omit the panel entirely when there are zero blockers — no empty
   shell.
2. **Inline step echo**: the currently active step's own matching blocker(s) (`step ===
   activeStep`) also render at the top of that step's content, in a `.callout
   callout-warning` (or `callout-critical` for `critical` severity), directly replacing
   today's ad hoc `preview_error`/`manual_review_reason` callouts — see the
   `workflow.preview_error` synthesis rule immediately below the vocabulary table for
   exactly how the `preview_error` callout becomes a blocker row (it is never rendered
   with a literal `code: "preview_error"`); `manual_review_reason` becomes the
   `action_not_executable` row keyed off `workflow.action.executable === false`.

### Blocker Vocabulary (locked; the planner/executor must not invent new copy ad hoc)

Every `reason`/`ineligibility_reason` value already emitted by
`src/intelligence/remediation/execution_service.py`, the Defender-configuration adapter
(`src/operations/defender_configuration.py`, including its constructor's own
`defender_configuration_unavailable` default `reason`), the workflow router's
plan-eligibility gate (`src/api/routers/remediation.py`), and
`src/intelligence/remediation/approval_decisions.py`'s `build_execution_snapshot` (whose
every raise site constructs an `ExecutionSnapshotError` carrying a `.reason` — this is the
function the router's `preview_plan` endpoint calls, and the sole origin of
`workflow.preview_error`'s value; see the synthesis rule below) maps to exactly one row
below — this is an **exhaustive** vocabulary of every code any of those four call sites can
currently produce, not a representative sample. Codes not yet emitted by any backend call
site are out of scope until a plan introduces them, but the fallback rule still applies if
one appears. The lone deliberate exception is `already_succeeded`, which is excluded from
this table entirely — see "Excluded from Blockers" below.

`defender_configuration_unavailable`, `configuration_execution_unavailable`,
`azure_arm_token_unavailable`, `unsupported_configuration_action`,
`configuration_target_not_supported`, and `scope_not_authorized` are the six
Defender-configuration-family failure codes (`src/operations/defender_configuration.py`),
mirroring the existing patch-family rows (`patch_execution_unavailable`/`store_not_configured`/
`target_not_found`) one-for-one so the two action families never diverge in operator-facing
honesty. `execution_active`/`already_superseded` are the two Supersede-specific ineligibility
codes (`_supersede_eligibility` in `execution_service.py`) that can only ever surface via
`execution.supersede_ineligibility_reason` — see the Supersede interaction's "Race handling"
note below for how they render there using this same locked copy.

**Dual-sourced codes (locked):** `target_not_found`, `action_not_executable`,
`patch_execution_unavailable`, and `configuration_execution_unavailable` are each raised from
**two** distinct call sites that share the identical code string: once inside
`build_execution_snapshot` (`approval_decisions.py`), reached only via `preview_plan` at
review time, and again inside `execution_service.py`'s execution-submission path, reached at
run time. The table's `step` column for these four rows reflects their **run-time** arrival
(`approve` for `action_not_executable`, `run` for the other three); their **review-time**
arrival via `workflow.preview_error` is always rendered at `step: "review"` regardless — see
the `workflow.preview_error` synthesis rule immediately below. The message/next-action copy is
identical either way; only the affected-step placement differs, because the two arrivals are
genuinely different moments in the workflow (a preview that never had a valid snapshot to
approve, versus an approved snapshot that failed when actually submitted).

### `workflow.preview_error` synthesis rule (locked)

`workflow.preview_error` (`web/src/lib/services.ts`'s `preview_error: string` field, populated
by the router as `preview_error = str((exc.details or {}).get("reason") or exc.code)` when
`preview_plan` raises — `src/api/routers/remediation.py`) is **never itself a blocker code**,
and the literal string `"preview_error"` must never appear as a `code` value anywhere in this
contract — it is only the name of the API field carrying the real code. The field's *value*,
whenever it is non-empty, is always one of the `ExecutionSnapshotError.reason` values raised by
`build_execution_snapshot` (patch family: `no_patches_available`, `patch_ids_not_available`,
`no_patches_selected`, `target_not_found`, `patch_execution_unavailable`,
`action_not_executable`; Defender-configuration family: `configuration_execution_unavailable`,
`unsupported_configuration_action`, `configuration_target_not_supported`,
`azure_arm_token_unavailable`, `scope_not_authorized`, `defender_configuration_unavailable`) —
or, only in the defensive case where the router's own `exc.details` omits a `reason` (not
currently reachable, since every `ExecutionSnapshotError` raise site supplies one), the raw
`exc.code` HTTP-error-code string, which then falls through to the unrecognized-code row below
exactly like any other code not present in the vocabulary table.

Per CONTEXT.md ("The workflow API returns `blockers[]`..."), `workflow.blockers[]` is
backend-authoritative: `plan_workflow` (`src/api/routers/remediation.py`) constructs this row
server-side as part of assembling the array — the client performs no special-case
`preview_error`-reading logic beyond the ordinary vocabulary-lookup/fallback/telemetry rules it
already applies to every other row in `blockers[]`. Concretely, whenever `preview_plan` (called
internally by `plan_workflow`) raises and yields a non-empty `preview_error` value, `plan_workflow`
must include exactly one additional entry in the `blockers[]` array it returns:

1. `code` is set to the `preview_error` value verbatim (e.g. `code: "no_patches_available"`) —
   the field's literal value, never a fictional constant and never the field name itself. If the
   router chooses to stop returning the standalone `preview_error` scalar once `blockers[]`
   subsumes it, this is the row that replaces it; if `preview_error` is retained for backward
   compatibility, both must carry the identical value — they must never diverge.
2. `step` is set to `"review"` unconditionally — regardless of what the Blocker Vocabulary
   table's own `step` column says for that code — per the "Dual-sourced codes" note above, a
   `preview_error` is definitionally a review-time condition even for the four codes that can
   also arrive later at `approve`/`run` via a different field
   (`execution.failure_class`/`ineligibility_reason`).
3. `message`/`next_action` are taken from the Blocker Vocabulary table above (or from the
   underlying `ExecutionSnapshotError`'s own message where the table defers to
   server-provided text), exactly like any other row — no separate copy path.
4. This row is never synthesized for `already_succeeded` — not reachable via `preview_error` in
   practice (a succeeded plan has a preview, not a preview error), and excluded from
   `blockers[]` entirely per "Excluded from Blockers" below regardless of source.

The client's only obligation here is the one already specified for every row in `blockers[]`:
render whatever `code`/`message`/`step`/`next_action` arrives, falling back to the locked
vocabulary table (and its one-time telemetry) only for a code the table doesn't recognize. No
client code may ever hardcode the literal string `"preview_error"` as a `code` value, and no
client code may re-derive `step` for this row independently of what `plan_workflow` sent.

### Excluded from Blockers (locked)

`already_succeeded` (the `ineligibility_reason` `execution_view` assigns when
`execution.status === "succeeded"`, purely to explain why Retry is correctly hidden) is the
one code this table deliberately omits. It is never rendered as a blocker row — not in the
cross-step summary panel, not as an inline step echo — because it describes a successful
terminal outcome, not a condition needing operator action; a "blocker" panel containing a
row that says "no further action is needed" is a contradiction in terms, not a UI nuance.
Client code must special-case `ineligibility_reason === "already_succeeded"` to synthesize
no blocker row for it at all — this is a **recognized, deliberately-suppressed** code, so it
must never trigger the unrecognized-code fallback or its one-time telemetry either. The
underlying fact is already fully communicated without a blocker: the `succeeded` `StatusBadge`
on the execution, plus (when applicable) the Reconciliation Contract's own `reconciled_clean`/
`reconciled_incomplete` row, are the single source of truth for a succeeded execution's real
completeness — a redundant info-toned blocker row would only add a second, weaker copy of the
same fact. (This is the preferred resolution; an alternative of making `severity` accept an
`info` value and every blocker-rendering surface `info`-aware was considered and rejected — it
would require every consumer of `workflow.blockers[]`, including the cross-step summary panel's
`Blocked` `StatusBadge` label, to special-case a non-blocking row anyway, with no reduction in
code paths versus simply never emitting the row.)

## Degradation Contract (`workflow.degradation[]`)

Addresses WR-02/WR-03/WR-04: provider/source degradation, coverage gaps, and overstated
freshness must reach the operator, not just a server log.

### Required data shape

```
workflow.degradation: Array<{
  source: string;                 // e.g. "Defender findings", "AUM patch inventory"
  availability: "degraded" | "unavailable" | "partial";
  reason: string;                 // free text sentence fragment, always rendered even if
                                   // the exact wording isn't in a fixed enum
  dropped_count?: number;         // evidence rows dropped from this response for this scope
  unmatched_count?: number;       // evidence rows that could not be matched to a canonical target
  freshness?: string;             // ISO timestamp or relative label; absent means "unknown",
                                   // never rendered as "current" without one
}>
```

### Placement and rendering

- Rendered as `<section className="remediation-degradation">` at the top of the `review`,
  `approve`, and `run` step content — directly below any active blocker echo, above the
  step's own primary content (impact grid / approval form / run controls). Omit the section
  entirely when `degradation.length === 0` — no empty shell (matches the 03.5 self-approval
  banner precedent).
- Each row: `StatusBadge` (`warning` tone, label = titleized `availability`, e.g.
  `Degraded`) · `source` (Label size) · the `reason` sentence · a secondary line built only
  from present fields:
  - Counts clause, omitted entirely when both counts are zero/absent:
    `"{dropped_count} evidence row(s) dropped, {unmatched_count} unmatched for this scope."`
  - Freshness clause, always present: `"Last known good: {freshness}"` when `freshness` is
    present, otherwise the literal `"Freshness: unknown"` — never a bare omission and never
    the word "current" without a timestamp behind it.
- This panel is the source of truth for "provider degradation is visible before

## Honest Step Projection Contract

Replaces the current unconditional step-nav status pass-through
(`workflow?.steps.find(...)?.status ?? "pending"`), which today can show `complete` for a
Verify step whose execution actually failed.

### Locked "Verify step is `blocked`" rule

The `verify` step's projected `status` is `"blocked"` (never `"complete"`) whenever any of
the following is true of `workflow.execution`:

1. `execution.status === "failed"` or `execution.status === "cancelled"`.
2. `execution.status === "succeeded"` **and**
   `execution.evidence_reconciliation.status` is `"reconciled_incomplete"` or
   `"unreconciled"` — a provider-reported success whose selected patches are confirmed
   still present, or whose presence could not be confirmed at all, is not a *complete*
   remediation from the operator's point of view even though Azure's own outcome is
   preserved unchanged.
3. `execution.remaining_attempts === 0` and `execution.status !== "succeeded"` (an
   exhausted, non-terminal-success execution — "exhausted" per CONTEXT).

`verify` is `"complete"` only when `execution.status === "succeeded"` and
`evidence_reconciliation.status` is `""` (not applicable — e.g. Defender-configuration
family) or `"reconciled_clean"`. It is `"current"` while `execution` exists but is still
`queued`/`running`/`retrying`, or while `evidence_reconciliation.status === "pending"`.
`"pending"` (unset) is treated as still-current, not blocked — reconciliation has not yet
had a chance to run.

When `verify` is `"blocked"`, the step nav's `<small>` text renders `Blocked` in
`--color-warning`, or `--color-critical` if any of that step's active blockers are
`critical` severity (per the Blocker Vocabulary table) — no new nav element, only the
existing text's color token changes.

### Verify-step content honesty

- `!workflow.execution` still shows the existing `Not run yet` `StatePanel` — unchanged
  (no execution exists yet is a genuinely different fact from a failed one).
- When `execution` exists, `ExecutionAudit` always renders the recovery-control section
  (Cancel/Retry/Supersede Contract below) directly beneath the existing provider-state
  paragraphs — never only the Retry button gated on `execution.retryable` as today.
- A pre-submission refusal (`execution.provider_submitted === false` on the latest attempt)
  renders distinctly from a post-submission provider failure. **Both sentences read from the
  exact same single field, `execution.failure_details`** — there is no separate "ineligibility
  reason" field to fall back to, and no open-ended `||` fallback chain is introduced:
  `"Blocked before submission: {failure_details}. No change was sent to the provider."` vs.
  the existing `"Submitted; provider reported: {failure_details}."` wording for a genuine
  post-submission failure. Only the surrounding sentence — never the field read — differs,
  gated purely on `execution.provider_submitted`. This distinction is required so an operator
  never believes a change reached the target when it never left the platform.
- **This single-field read is only truthful once `execution.failure_details` is reliably
  non-empty on every execution that reaches a terminal `"failed"` status — which is not yet
  the case today** for `failure_class === "verification_timed_out"` or
  `"submission_unconfirmed"` outcomes specifically (see the Failure Details Authoritative
  Contract immediately below, which this phase's plan must implement, plus a required test,
  before this bullet's claim holds for those two failure classes). Regardless of source, no
  sentence in this contract may ever interpolate an empty `failure_details` and leave
  dangling punctuation (`"Submitted; provider reported: ."`) — see that contract's
  Empty-Value Punctuation Rule, which governs both of the sentences above without exception.

### Failure Details Authoritative Contract (locked — backend requirement, this phase)

The two Verify-step sentences above are only truthful if `execution.failure_details` is
reliably non-empty on every execution that reaches a terminal `"failed"` status. Today it is
not: `execution_service.py`'s `poll_verification` (both `failure_class:
"verification_timed_out"` transitions — the `retrying`-branch at a claim-resume deadline, and
the `running`-branch at a verification deadline) and `reconcile_ambiguous_submission` (its
`failure_class: "submission_unconfirmed"` transition, on reconciliation timeout) each call
`_transition_or_current` with a human-readable `message=` note but do **not** also pass
`failure_details=` — so `execution.failure_details` is left at its prior (frequently empty)
value on exactly the three failure paths this phase's honesty contract most depends on.

**Required backend normalization (preferred resolution; implemented by this phase's plan, not
deferred):** each of those three `_transition_or_current` call sites must additionally pass
`failure_details=` set to the same operator-facing sentence currently passed only as
`message=` (the existing note text, reused verbatim — this is a parameter-plumbing fix, not
new copy). This makes `execution.failure_details` authoritative for every terminal-failure
path the backend can produce, patch and Defender-configuration families alike, with one field
remaining the single source of truth rather than a second, competing one.

**Required test (explicit acceptance criterion, equal in weight to this contract's UI
criteria):** an exhaustive backend test, parametrized over every `execution_service.py` call
site that transitions an execution to a terminal `"failed"` status — pre-submission
provider-unavailable failures (existing behavior, already correct), both
`verification_timed_out` branches, and the `submission_unconfirmed` branch — must assert
`execution.failure_details` is non-empty on the resulting record for each one. A single
example-based test is insufficient; the test must enumerate all such call sites so that a
future call site omitting `failure_details` fails the suite instead of silently reintroducing
blank copy.

**Empty-Value Punctuation Rule (locked, defense in depth — applies to every field
interpolation in this contract, not only `failure_details`):** even after the backend
normalization above ships, a pre-Phase-03.6 legacy execution record may still carry an empty
`failure_details`. No sentence in this contract may ever render with dangling punctuation
around an empty interpolated value (e.g. `"Submitted; provider reported: ."`, or a counts
clause with a blank clause where a number should be). Specifically for the two Verify-step
sentences: when `failure_details` is empty, render a closed fallback sentence in its place —
never the templated sentence with nothing substituted in:

| Condition | Fallback copy (used only when `failure_details` is empty) |
|-----------|-------------------------------------------------------------|
| Pre-submission, `failure_details` empty | `Blocked before submission: no failure detail was recorded for this attempt. No change was sent to the provider.` |
| Post-submission, `failure_details` empty | `Submitted; the provider did not return failure detail for this attempt.` |

This fallback is expected to be unreachable once the backend normalization and its required
test above ship for every new execution — it exists as a closed, tested safety net for
legacy/pre-existing records, not as license to leave the backend gap unfixed.

## Patch Selection Safety Contract

Fixes CR-07 (`page.tsx`'s deselect-all-then-widens-to-all-again bug, still present in the
current implementation's `setSelectedPatchIds(next.length === all.length ? [] : next)`
logic — deselecting the last checked patch produces `next = []`, and `[]` is the same
sentinel the code uses for "all", silently re-checking every patch).

### State model (locked)

Client component state is `selectedPatchIds: string[] | null`:

- `null` — **all eligible patches** (the default on every fresh workflow load / plan
  change).
- Non-empty `string[]` — **exactly these patches, explicitly**, no more, no fewer.
- Empty `string[]` (`[]`) is an **invalid transient**, never a stored state. The state
  setter must never be called with `[]`; the wire layer already treats zero `patch_id`
  query parameters as "all" (unchanged), so `null` continues to serialize to zero
  parameters — only the *client-local* meaning of an empty array changes (it is no longer
  overloaded to also mean "all").

### Interaction rule (locked)

On a checkbox toggle:

1. Compute `current = selectedPatchIds === null ? allPatchIds : selectedPatchIds`.
2. Compute `next = checked ? [...current, patchId] : current.filter(id => id !== patchId)`.
3. If `next.length === allPatchIds.length` → set state to `null` (back to "all" — the
   *default*, reached deliberately by re-checking everything, never by deselecting
   everything).
4. Else if `next.length === 0` → **refuse**: do not call the state setter at all (state is
   unchanged, so the just-clicked checkbox re-renders exactly as it was — visually, the
   click has no effect on selection). Render the refusal message described below. This is
   the "clear empty-selection refusal, never silently widens back to all" requirement —
   an operator cannot reach an empty selection by any sequence of individual clicks.
5. Else → set state to `next` (the explicit non-empty subset).

### Refusal message

Rendered as `<p className="callout callout-warning" role="alert">` directly beneath the
patch list, only while the most recent toggle attempt would have produced an empty set:
`"At least one patch must remain selected for this plan to be approved. Select a patch
below, or use the mode line above to restore all eligible patches."` This message clears
the next time selection changes to a non-empty state (explicit or "all") or a different
plan is selected — it is not persistent chrome.

### Mode line (locked, always visible above the patch list)

- `null` (all): `"All eligible patches selected ({N})."`
- explicit: `"{N} of {M} patches explicitly selected."`

This is the literal display of "all eligible" vs "N explicitly selected" CONTEXT requires,
and it must always precede the checkbox list, matching the existing `<p>Select which
patches to install:</p>` position.

### Evidence-refresh reconciliation (locked)

When a refreshed `workflow.preview.execution_snapshot.available_patches` arrives with a
smaller set than before:

- If mode is `null` (all): no client action needed — "all" still means whatever the
  current eligible set is.
- If mode is explicit: intersect `selectedPatchIds` with the new available patch ids.
  - If the intersection is still non-empty, set state to that intersection (removal-only,
    never widened — satisfies "may remove unavailable patches but must not add/widen").
  - If the intersection is empty, do **not** fall back to `null` ("all"). Instead render
    the same empty-selection refusal state as above, with the additional sentence:
    `"Your previously selected patches are no longer available. Choose at least one
    currently available patch."` Approval remains blocked (`approval_requirements_unmet`-
    adjacent — surfaced as a `review`-step blocker with code
    `execution_snapshot_changed`) until the operator makes a new explicit choice.

### Snapshot-hash binding (locked)

The approve payload's `selected_patch_ids` field is `null` when mode is "all", or the
exact explicit array otherwise — never `[]`. `workflow.preview.execution_snapshot.snapshot_hash`
must be re-fetched (existing `workflowRefresh`/`selectedPatchIds`-keyed effect already does
this) every time the mode changes, so `Record decision` always binds to the snapshot that
matches the currently visible mode line — this is already true of the existing effect
dependency array and is preserved, not re-architected.

## Bounded Polling Contract

Replaces the current unbounded `setTimeout(() => refresh, 1500)` loop
(`page.tsx:324-329`), which repeats forever for any execution left in
`queued`/`running`/`retrying`.

### Backoff sequence (locked, deterministic — no jitter)

Poll delays, in order, one per consecutive non-terminal refresh of the *same* execution:
`1500ms, 3000ms, 6000ms, 12000ms, 24000ms, 30000ms, 30000ms, …` (doubles each step, capped
at 30000ms). Deterministic so a fake-timer test can assert the exact sequence.

### Ceiling (locked)

Polling for a given `execution_id` stops — permanently, until a manual check or a plan/
selection change resets it — the moment **either**:

1. 40 consecutive poll requests have been issued for that execution, or
2. 600000ms (10 minutes) have elapsed since the first poll for that execution,

whichever comes first. On reaching the ceiling, render a `<p className="callout
callout-warning" role="status">` beneath the execution status: `"Live updates paused after
{N} checks. This execution may still be progressing server-side."` with a `Check now`
button. `Check now` performs exactly one manual refresh and does not resume the automatic
interval — the operator must click again for each subsequent check once paused. (Server-
side verification remains authoritative and continues independently of client polling —
see `verification_coordinator.py` — so pausing client polling never stops real progress,
only the live display of it.)

### Stop-on-terminal rule (locked)

Automatic polling also stops immediately — with no ceiling message, since this is the
expected happy path, not an exhaustion — the moment
`execution.status` leaves `{"queued", "running", "retrying"}`, i.e. reaches `"succeeded"`,
`"failed"`, or `"cancelled"`, **regardless** of `evidence_reconciliation.status`. If
`evidence_reconciliation.status === "pending"` at that moment (reconciliation still running
server-side in the background against an already-terminal execution status), render a
single `Check reconciliation` manual-refresh button beside the Reconciliation Contract's
`pending` row — a one-off fetch, not a resumed automatic loop, consistent with "server-side
verification remains authoritative."

### Counter reset (locked)

The poll counter and elapsed-time clock reset to zero whenever `selectedPlanId` changes or
`workflow.execution.execution_id` changes (a new execution — e.g. after Retry/Supersede
succeeds) — a fresh execution always gets its own full bounded polling budget.

### Test injectability (locked)

The two ceiling branches must be provable **independently** of one another, which the fixed
backoff sequence above does not allow for free: summing `1500 + 3000 + 6000 + 12000 + 24000
+ 30000×N` shows the 600000ms elapsed-time ceiling is always reached by roughly the 24th
poll under real wall-clock time — meaning a test that only fast-forwards a fake timer
through real backoff delays can *never* isolate the 40-request ceiling from the 10-minute
ceiling; one of the two branches would always be untestable in isolation, and a regression
that broke the request-count check specifically could hide behind the elapsed-time check
always firing first.

To make both branches independently triggerable, the elapsed-time measurement is read from
an **injected clock function**, decoupled from the timer scheduling itself:

- The polling hook/module accepts a `now: () => number` dependency (defaulting to
  `Date.now` in production), used only to compute elapsed time since the first poll for the
  current execution — never used to schedule the `setTimeout` delays themselves, which
  remain driven by the fake-timer-controlled backoff sequence above.
- **Request-count branch, isolated:** a test supplies a `now` stub that advances by a
  fixed, small increment (e.g. `+1ms`) on every call, then fast-forwards fake timers through
  40 consecutive polls. Elapsed time under the stub never approaches 600000ms, so reaching
  exactly 40 requests is what triggers the ceiling — proving the request-count branch fires
  on its own.
- **Elapsed-time branch, isolated:** a test supplies a `now` stub that jumps straight to
  `firstPollTimestamp + 600000ms` (or beyond) after only 1–2 real polls, then fast-forwards
  a single additional fake-timer tick. The ceiling fires at the 2nd poll, long before 40
  requests, proving the elapsed-time branch fires on its own, independent of request count.
- Both tests assert the exact ceiling-reached copy (`"Live updates paused after {N}
  checks..."`) and that automatic polling does not schedule a further `setTimeout` after
  the ceiling fires, regardless of which branch triggered it.
