<domain>
## Phase Boundary

Make the remediation workflow explain its real safety state: project
server-derived blockers and degraded inputs, render failures honestly, make
patch selection fail-safe, and provide bounded actionable recovery controls.
This phase consumes the durable identity, retry/supersession, verification, and
approval contracts from Phases 03.2-03.5 without redesigning them.

<decisions>
## Implementation Decisions

### Blockers and Degradation
- The workflow API returns `blockers[]` with stable code, human message, affected step, and one concrete next action.
- Every execution/approval ineligibility reason emitted by the backend maps to an operator-facing blocker; unknown codes use an explicit safe fallback and telemetry, never disappear.
- `degradation[]` reports source/provider, availability, reason, dropped/unmatched evidence counts, and freshness where known.
- Provider degradation is visible before approval/run controls and never represented as healthy-empty data.

### Honest Lifecycle Projection
- Step completion derives from successful outcome, not mere execution existence or terminality.
- Failed, cancelled, unknown, unreconciled, and exhausted executions block Verify and recommend the actual available recovery action.
- Retry, supersede, cancel, or wait controls are rendered only from server-authoritative eligibility fields.
- Selected provider counts, remaining attempts, verification deadline, reconciliation result, and audit lineage remain visible.

### Patch Selection Safety
- Represent selection explicitly: `null` means all eligible patches; a non-empty list means exactly those patches; an empty list is invalid and cannot be approved.
- Deselecting the last visible patch produces a clear empty-selection refusal, never silently widens back to all.
- The UI displays whether scope is "all eligible" or "N explicitly selected", and the approved snapshot hash must match that visible mode.
- Evidence refresh may remove unavailable patches but must not add/widen the operator's explicit selection.

### Recovery Controls and Polling
- Use bounded exponential backoff with jitter-free deterministic tests and a hard elapsed-time/request ceiling.
- Stop client polling on every server terminal state, including unknown/unreconciled failure states; server-side verification remains authoritative.
- Render cancel only for queued unsubmitted work, retry only for safe retryable work, and supersede only for eligible exhausted work with a required reason.
- Recovery actions preserve current scope and refresh the server workflow projection afterward.

### Freshness and Coverage
- Compute citation/source freshness from real timestamps and thresholds; never assert `"current"` without evidence.
- Surface patch-evidence canonical-target misses as structured coverage counts while retaining aggregate warning logs.
- Do not let optional provider degradation crash core workflow reads.

### the agent's Discretion
- Exact component extraction and layout details follow the Phase 03.6 UI-SPEC and existing remediation design tokens.

</decisions>

## Specific Ideas

Tests must enumerate the full ineligibility vocabulary and prove every code has
copy plus a concrete next action; prove failure never marks Verify complete;
prove deselect-all cannot become select-all and snapshot scope matches visible
selection; prove degraded providers are visible before approval; and prove a
stuck execution cannot exceed the client polling request ceiling.

</specifics>
