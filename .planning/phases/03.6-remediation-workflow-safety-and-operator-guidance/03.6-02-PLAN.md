<objective>
Implement the Phase 03.6 UI-SPEC's Blocker Contract, Degradation Contract, and
Honest Step Projection Contract on the backend: `plan_workflow`
(`src/api/routers/remediation.py`) gains `blockers[]` and `degradation[]`
arrays and an honestly-computed `verify` step status, and
`src/semantic/live_operations.py`'s two hardcoded `"freshness": "current"`
evidence-citation fields are replaced with a real threshold-based computation.
This satisfies CONTEXT.md's "Blockers and Degradation" and "Honest Lifecycle
Projection" decision groups and the "Compute citation/source freshness from
real timestamps and thresholds; never assert 'current' without evidence"
decision, using only fields the router already assembles and one existing,
already-shared helper (`api.evidence.classify_freshness`, already used
identically by `intelligence/remediation/defender_correlation.py`).

Scope note (explicit, non-reduction): CONTEXT.md's "Surface patch-evidence
canonical-target misses as structured coverage counts" decision refers to a
canonical-target-match step. Investigation confirmed the *live* remediation
planner (`LiveRemediationPlanner._plan`/`_configuration_plan` in
`live_operations.py`) builds every evidence citation directly from rows that
already passed a canonical-target join upstream (in the live query itself) --
there is no separate "evidence row dropped because it didn't match
inventory" step in this code path to count, unlike the unrelated
Fabric-dashboard `PatchIntelligence.from_semantic_engine` correlation (a
different subsystem entirely, never reached by `/remediation`). `dropped_count`/
`unmatched_count` are optional fields in the locked contract ("where known");
this plan correctly omits them for the live planner because there is no real
count to report, not because the work was skipped. This is recorded as a
scope note in the SUMMARY, not silently dropped.

Purpose: gives the frontend (Plan 03.6-03/04) a fully-populated, honest
`workflow` payload to render against, with zero fabricated data.
Output: `plan_workflow`'s response envelope carries `blockers`/`degradation`
arrays and an honest `verify` step; two live citation freshness fields are
real.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator (read scope) -> `GET /plans/{id}/workflow` | Already-authenticated/scoped read; this plan adds derived fields only, no new input surface. |
| `_collect_degradation` -> `context.provider_runtime.health()` | Internal, trusted; wrapped in try/except so a misbehaving provider health call cannot become a workflow-read outage. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-036-03 | Information Disclosure | `_collect_degradation`'s `degraded_reason` passthrough | low | accept | `ProviderState.degraded_reason` already excludes secrets by construction (`to_dict()`'s existing "secret-free provider health contract" contract, unchanged by this plan) -- no new field is invented here. |
| T-036-04 | Denial of Service | `_collect_degradation`'s `context.provider_runtime.health(refresh=False)` call | low | mitigate | `refresh=False` is used deliberately so this read never triggers a blocking provider refresh on a request-serving thread (matching `ProviderRuntime.get()`'s own non-blocking-refresh precedent); the whole call is wrapped in try/except so any failure degrades to an empty degradation list rather than a 500. |
| T-036-05 | Tampering | Honest step projection (`verify_blocked`/`verify_complete`) | medium | mitigate | Computed purely from server-authoritative `execution.status`/`evidence_reconciliation.status`/`remaining_attempts` fields already written by the trusted execution service -- no client input participates in this computation. |

</threat_model>
