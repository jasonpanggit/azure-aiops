`poll_verification`'s two `verification_timed_out` branches (the `"retrying"`-branch

## What Was Built

- **`src/intelligence/remediation/execution_service.py`**: the `"retrying"`-branch and
  `"running"`-branch `verification_timed_out` transitions inside `poll_verification`,
  and the `submission_unconfirmed` timeout transition inside
  `reconcile_ambiguous_submission`, each gained `failure_details=` alongside their
  existing `message=` argument, reusing the identical note text verbatim.
- **`tests/test_remediation_failure_details_authoritative.py`** (new): documents the
  Failure Details Authoritative Contract in its module docstring; provides
  `_retrying_past_deadline()`/`_running_past_deadline()` fixture helpers; four
  dedicated test functions (`test_retrying_branch_verification_timed_out_...`,
  `test_running_branch_verification_timed_out_...`,
  `test_reconcile_ambiguous_submission_timeout_...`,
  `test_pre_submission_provider_unavailable_...`) plus one
  `@pytest.mark.parametrize`-driven exhaustive regression test
  (`test_exhaustive_terminal_failure_call_sites_populate_failure_details`) covering
  all four call sites the plan named: pre-submission provider-unavailable,
  the two `verification_timed_out` branches, and the `reconcile_ambiguous_submission`
  timeout.
- **`tests/test_remediation_evidence_reconciliation.py`**: the existing
  `test_reconcile_ambiguous_submission_reclassified_after_deadline_with_no_proof` test
  gained an `assert result["failure_details"]` assertion.

## Post-review follow-up (WR-01, same review cycle)

The Phase 03.6 code review (`03.6-REVIEW.md`) found that this exhaustive test's own
docstring claim ("enumerates all four such call sites") did not actually include two
further terminal-transition call sites in `poll_verification` — the ARM-verified real
`result_outcome == "failed"` (`failure_class="provider_rejected"`) and
`result_outcome == "cancelled"` branches, both of which did an unguarded pass-through
of `outcome.get("failure_details", "")` with no defensive fallback. This was fixed as
part of the review-fix pass: both call sites now default to
`"Provider reported a terminal outcome with no additional detail."` when the injected
`ExecutionVerifier` omits `failure_details`, and the exhaustive test now covers six
call sites, not four (two new cases: `provider_rejected_failed`,
`provider_rejected_cancelled`, plus two new dedicated regression tests using a
`_FakeTerminalVerifier` test double). See `03.6-REVIEW-FIX.md` for the fix commit
details.
