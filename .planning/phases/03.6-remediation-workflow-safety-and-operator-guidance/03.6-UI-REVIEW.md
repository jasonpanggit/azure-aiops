# Phase 03.6 — UI Review

**Audited:** 2026-09-05  
**Baseline:** `03.6-UI-SPEC.md` and current deployed UI evidence  
**Screenshots:** Captured from the deployed URL at desktop/tablet/mobile, but the authenticated remediation screen was not reachable with the available browser state; captures show the sign-in gate. Authenticated findings use the supplied live evidence, the phase's archived Chromium screenshots, and code/CSS inspection.

---

## Pillar Scores

| Pillar | Score | Key Finding |
|--------|-------|-------------|
| 1. Copywriting | 3/4 | Safety copy is strong, but grammar and machine-oriented labels reduce polish. |
| 2. Visuals | 1/4 | Native-looking controls, unstructured approval metadata, and dominant identifiers visibly break the product's card language. |
| 3. Color | 2/4 | Tokens are reused, but brand blue is applied to blocker and recovery surfaces contrary to the contract. |
| 4. Typography | 2/4 | New remediation UI uses undeclared 11/13px sizes and 650/700 weights, weakening hierarchy. |
| 5. Spacing | 2/4 | Numerous off-scale values and weak grouping produce both cramped metadata and excessive empty space. |
| 6. Experience Design | 2/4 | Core lifecycle states are covered, but responsive overflow and incomplete form semantics remain. |

**Overall: 12/24**

---

## Top 3 Priority Fixes

1. **Replace browser-default form presentation with a scoped remediation form system** — the approval/search/supersede controls look unrelated to the rest of the application — style `.remediation-approval-form` and `.remediation-supersede-form` labels plus their `input`, `select`, and `textarea` children with the existing 38px field height, surface, border, radius, padding, and focus treatment already used by `.remediation-form-grid`.
2. **Turn approval requirements and execution facts into structured rows** — badges, roles, policy IDs, stages, dates, and facts currently run together and are hard to scan — use a responsive metadata grid/definition list with one labeled value per cell, clear row separators, and grouped card sections.
3. **Demote and abbreviate opaque identifiers while restoring action hierarchy** — full resource IDs and snapshot/execution hashes dominate the task content, while every recovery action appears primary — show a human label plus middle-truncated ID with copy/full-value affordance, and reserve `.button-primary` for the confirmation action only.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

- **WARNING — Incorrect singular count.** The badge always renders `${planRows.length} fixes`, producing “1 fixes” in the captured UI (`web/src/app/remediation/page.tsx:592`). Use `1 fix` / `{N} fixes`.
- **WARNING — Machine labels leak into operator-facing UI.** `titleize(reconciliation.status)` exposes labels such as “Reconciled Incomplete” instead of a concise operator state (`page.tsx:1083-1085`). Use the same human label table as the reconciliation message.
- **WARNING — Identifier-heavy copy obscures the decision.** Full resource, target, snapshot, execution, and lineage IDs are inserted inline (`page.tsx:612, 668, 780-782, 1199, 1241-1245`). Keep full values available, but lead with a short resource name and move IDs to secondary metadata/copy controls.
- **Pass evidence:** Blocker next actions, degradation explanations, empty/loading/error messages, and confirmation labels are specific and substantially match the locked copy contract (`page.tsx:41-60, 580-626, 995-1095`).

### Pillar 2: Visuals (1/4)

- **BLOCKER — Form controls do not use the product visual language.** The live evidence shows browser-default select/input/textarea controls. Global CSS only inherits the font (`globals.css:228-233`), while `.remediation-approval-form` defines only grid gap/max-width (`globals.css:6518-6522`). The styled `.remediation-form-grid` rules at `globals.css:3751-3773` do not apply to the approval form (`page.tsx:790-842`) or supersede form (`page.tsx:1153-1172`).
- **BLOCKER — Approval requirements have class names but no visual layout rules.** `ApprovalRequirementsList` emits status, role, policy ID, stage, explanatory copy, and details as adjacent flow content (`page.tsx:138-176`), but no `.remediation-approval-requirements` or `.remediation-approval-requirement-row` CSS exists. This directly explains the reported metadata running together.
- **BLOCKER — Raw identifiers become focal points.** The plan list renders a full Azure resource path (`page.tsx:611-613`), Review renders a full target (`page.tsx:668`), Approve renders the snapshot hash (`page.tsx:780-782`), and Verify renders execution/lineage IDs (`page.tsx:1199, 1241-1245`). `overflow-wrap:anywhere` prevents overflow but does not create hierarchy; it turns IDs into large text blocks.
- **WARNING — Card treatment is inconsistent.** Evidence and patch items receive bordered sub-surfaces (`globals.css:6465-6472, 6503-6509`), while approval requirements and execution facts remain unboxed paragraphs. The same workflow therefore alternates between polished cards and document-like raw text.
- **WARNING — The main task lacks a stable focal section.** `ExecutionAudit` is a long stream of paragraphs and nested lists (`page.tsx:1192-1279`), so status, recovery, rollback, attempts, and decisions compete equally. Split it into “Outcome”, “Recovery”, and collapsible “History” sections.

### Pillar 3: Color (2/4)

- **WARNING — Active blocker rows use forbidden brand accent.** `.remediation-blocker-row-active` adds a blue brand border (`globals.css:6348-6351`), although the contract reserves accent for primary CTAs/focus/links and explicitly excludes blocker rows. Use the blocker severity token for the border.
- **WARNING — All recovery actions are painted primary.** Cancel, Retry, and Supersede triggers all use `.button-primary` (`page.tsx:1121-1151`). The contract reserves accent for the primary action inside the confirmation step. Use neutral/quiet triggers; apply primary only to `Confirm cancel` or `Confirm supersede`.
- **WARNING — Excessive near-identical pale surfaces flatten hierarchy.** Cards, blocker/degradation panels, patch rows, and evidence rows rely on very similar white/subtle-gray surfaces (`globals.css:6322-6332, 6465-6472, 6503-6509`). Add semantic warning tint/border to disclosure panels and keep neutral sub-surfaces for ordinary metadata.
- **Pass evidence:** New rules mostly use existing CSS variables and semantic badge tones rather than adding arbitrary colors.

### Pillar 4: Typography (2/4)

- **WARNING — New text roles diverge from the approved scale.** The contract permits 12px metadata, 14px body, 18px section headings, and 28px display text with weights 400/600. Remediation additions introduce 11px and 13px text (`globals.css:6474-6488, 6503-6509`) and 700 weight (`globals.css:6302-6311, 6524-6528`).
- **WARNING — Section headings inherit 15px/650 rather than the specified 18px/600.** Global `h3` is `15px/650` (`globals.css:264-267`), and remediation sections do not override it. “Workflow blockers”, “Degraded inputs”, “Approval requirements”, and “Provider verification” consequently read too close to body copy.
- **WARNING — Dense paragraphs have no metadata hierarchy.** Review facts and execution facts use repeated plain `<p>` elements (`page.tsx:656-669, 1198-1248`) rather than label/value typography. Add 12px semibold labels and 14px regular values with consistent line height.

### Pillar 5: Spacing (2/4)

- **WARNING — Phase additions violate the declared 4/8/16/24px scale.** Examples include `padding: 11px 13px` (`globals.css:6375-6383`), 6px gaps (`globals.css:6457-6463, 6495-6501, 6511-6515`), 2px gaps (`globals.css:6465-6468`), and 6px/10px padding (`globals.css:6503-6509`). Replace these with scale tokens.
- **WARNING — Related approval metadata has no spacing contract.** Because requirement rows have no CSS, status/role/policy/stage content collapses into inline flow (`page.tsx:145-174`), matching the reported “running together” defect.
- **WARNING — The form is artificially narrow inside a large card.** `.remediation-approval-form` caps content at `42rem` without a complementary summary column (`globals.css:6518-6522`), leaving unused space on desktop while fields still look cramped. Use a two-column approval layout on wide screens and one column below 900px.
- **WARNING — Mobile page overflow was previously measured at about 1235px for a 375px viewport.** The archived QA explicitly records this despite marking phase-local elements as passing (`03.6-MANUAL-QA.md:47-57`). A current-page audit cannot treat off-canvas UI as acceptable; fix the banner/shell min-width and verify `scrollWidth <= clientWidth`.

### Pillar 6: Experience Design (2/4)

- **WARNING — Supersede semantics do not meet the accessibility contract.** The textarea is visually labeled but lacks `required`, `aria-describedby`, and adjacent explanatory text (`page.tsx:1153-1167`). The archived accessibility snapshot confirms only `textbox "Reason"` and a disabled button, not a required state or disabled reason (`manual-qa-evidence/manual-qa-3-accessibility-snapshot.yaml:72-75`).
- **WARNING — Recovery hierarchy encourages accidental action.** Cancel, Retry, and Supersede are all one-click primary-looking triggers (`page.tsx:1121-1151`). Keep conditional visibility, but use neutral triggers and visually isolate the confirmation state.
- **WARNING — Long histories are always expanded.** Attempts and decisions render inline before recovery controls (`page.tsx:1248-1279`, with controls mounted at `910-918`), pushing the next safe action below audit detail. Put recovery immediately after outcome/facts and collapse attempt history by default.
- **WARNING — Fresh deployed captures could not verify the authenticated workflow.** The available storage state contained no usable authenticated origin/cookies, so the deployed URL only exposed the sign-in page. This review therefore relies on supplied live evidence and repository-held Chromium captures for authenticated states.
- **Pass evidence:** Loading, error, empty, blocked, degradation, confirmation, polling-paused, reconciliation, and conditional recovery states are implemented (`page.tsx:216, 580-626, 770-923, 1051-1181`). Destructive workflow changes use confirmation and server-authoritative eligibility.
