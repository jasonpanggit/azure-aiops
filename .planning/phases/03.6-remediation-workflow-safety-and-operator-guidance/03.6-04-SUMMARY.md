# Phase 03.6 Plan 04: Blocker Contract Rendering, Degradation Rendering, Verify-Step Honesty Summary

> **Note:** This SUMMARY was generated retroactively (see 03.6-REVIEW.md WR-03) from
> `03.6-04-PLAN.md`'s locked `<behavior>`/`<action>` sections and the actual diff in
> `web/src/app/remediation/page.tsx` / `web/src/app/remediation/blockers.ts`, since the
> original execution session did not produce it. A follow-up fix (this same review
> cycle, WR-02) centralized this plan's unknown-code telemetry — see "Post-review
> follow-up" below.

`WorkflowBlockers`/`WorkflowDegradation` components render the Phase 03.6 UI-SPEC's
full locked Blocker Vocabulary and Degradation Contract client-side, replacing the
prior ad hoc `preview_error`/`manual_review_reason` callouts. The Verify step's
failure sentence now reads `execution.failure_details` through one of two
`provider_submitted`-gated templates with closed fallback copy, never a dangling
interpolation of an empty value.

## What Was Built

- **`web/src/app/remediation/blockers.ts`** (new, extracted from `page.tsx`):
  `WORKFLOW_STEPS`, the `BLOCKER_VOCABULARY` lookup table reproducing the UI-SPEC's
  locked vocabulary verbatim (every code's severity/message/step/nextAction, omitting
  `already_succeeded`), and `blockerCopy(code, serverStep, serverMessage?,
  serverNextAction?, serverSeverity?)` — resolves the server's own fields when present,
  otherwise the vocabulary table's fallback, otherwise the safe unrecognized-code
  fallback sentence.
- **`web/src/app/remediation/page.tsx`**:
  - `WorkflowBlockers({ blockers, activeStep })` — cross-step summary panel; filters
    `already_succeeded`; renders `StatusBadge`/step chip/message/next-action per row;
    (original implementation) tracked seen-unknown-codes via a local `useRef`.
  - An inline per-step `stepBlockerEcho(blockers, step)` function renders blockers
    matching the active step directly beneath that step's content.
  - `WorkflowDegradation({ degradation })` — renders `Degraded inputs` section above
    the Approve/Run controls when non-empty, with counts/freshness clauses.
  - The step-nav's blocked-step label color now reflects the worst severity among that
    step's own blockers (`--color-critical`/`--color-warning`).
  - `ExecutionAudit`'s Verify-step sentence now selects one of four fixed sentences
    (pre-/post-submission × populated/empty `failure_details`) instead of the single
    prior `{execution.failure_details && <p>...}` line.
  - Removed the old `workflow.preview_error &&` review-step callout and the
    `!workflow.action.executable && <p>Manual review required...</p>` callout — their
    information now arrives as ordinary `workflow.blockers[]` rows (Plan 03.6-02).
- **`web/src/app/globals.css`**: `.remediation-blockers`/`.remediation-degradation`
  rules added, reusing existing spacing/color tokens only.
- **`web/src/app/remediation/page.test.tsx`**: new tests for recognized-code rendering,
  unrecognized-code fallback + one-time telemetry, `already_succeeded` exclusion, the
  three `WorkflowDegradation` variants, and all four `failure_details` sentence
  variants.

## Post-review follow-up (WR-02, same review cycle)

The Phase 03.6 code review found that the unknown-blocker-code `console.warn`
telemetry this plan introduced was wired only inside `WorkflowBlockers` (via a local
`useRef<Set<string>>`) — the module-level `stepBlockerEcho` function and
`RecoveryControls`'s (Plan 03.6-05) supersede-ineligibility-reason callout both called
`blockerCopy()` directly and rendered its safe fallback copy correctly, but neither
ever telemetered. This was fixed as part of the review-fix pass: the seen-codes
tracking moved into `blockers.ts` as a module-level singleton behind a new
`blockerCopyWithTelemetry()` export, and all three render-path call sites
(`WorkflowBlockers`, `stepBlockerEcho`, `RecoveryControls`) now call it instead of the
bare `blockerCopy()`. New focused tests were added: a dedicated
`web/src/app/remediation/blockers.test.ts` unit-testing the dedup/telemetry logic
directly, plus one new `page.test.tsx` integration test proving `RecoveryControls`'s
call site telemeters independently (via a code that never appears in
`workflow.blockers[]`, so it cannot be attributed to `WorkflowBlockers` firing first).
See `03.6-REVIEW-FIX.md` for the fix commit details.
