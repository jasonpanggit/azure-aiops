## Warnings

### WR-01: The "exhaustive" Failure Details Authoritative test does not cover two real terminal-failure call sites in `poll_verification`

**File:** `src/intelligence/remediation/execution_service.py:1233-1259` (consumed
by the "exhaustive" test at `tests/test_remediation_failure_details_authoritative.py:1-9,131-158`)

**Issue:** `poll_verification`'s ARM-verified outcome branches —
`result_outcome == "failed"` (line 1233, `failure_class="provider_rejected"`,
a genuine terminal `"failed"` transition) and `result_outcome == "cancelled"`
(line 1247) — populate `failure_details=outcome.get("failure_details", "")`,
i.e. an **unguarded pass-through** of whatever the injected `ExecutionVerifier`
happens to return, defaulting silently to `""` if the key is absent.

`tests/test_remediation_failure_details_authoritative.py`'s own module
docstring states: *"This file exhaustively enumerates all four such call
sites so a future omission fails the suite instead of silently reintroducing
blank copy"* — but the enumerated four (pre-submission `_submit_and_record`,
the two `verification_timed_out` timeout branches, and
`reconcile_ambiguous_submission`'s `submission_unconfirmed` timeout) do **not**
include this `provider_rejected` (ARM-verified real-failure) branch, which is
also a terminal `"failed"`-producing call site per the phase's own locked
truth: *"Every execution that reaches a terminal failed status carries a
non-empty execution.failure_details."*

Reproduced directly against the shipped code (not hypothetical):
```
$ PYTHONPATH=src:tests python3 - <<'EOF'
from test_remediation_execution_service import _plan, _service_with_store, NOW
plan = _plan()
service, store = _service_with_store(plan=plan)
result = service.execute(plan["plan_id"], requested_by="operator@example.com")
execution_id = result["execution_id"]

class _FakeVerifier:
    def verify(self, record):
        return {"verifiable": True, "outcome": "failed", "verified_state": "Failed"}

service._verifier = _FakeVerifier()
polled = service.poll_verification(execution_id)
print(polled["status"], polled["failure_class"], repr(polled["failure_details"]))
EOF
failed provider_rejected ''
```
This confirms an `ExecutionVerifier.verify()` outcome that reports a terminal
`"failed"` ARM status without a `failure_details` key produces an empty
`failure_details` on the stored record — exactly the case the phase's
Failure Details Authoritative Contract exists to close, at a call site the
new exhaustive test does not exercise. In production, the shipped
`ExecutionVerifier` (`execution_verifier.py`'s `_error_message` helper)
populates this field in the overwhelming majority of cases, and the
frontend's Plan 03.6-04 closed-fallback rendering (`page.tsx`'s
`ExecutionAudit`) already renders a safe non-blank sentence when
`failure_details` is empty — so this does not currently produce a dangling/
blank interpolation for an operator. It does mean a future regression in the
verifier's `failure_details` population on this specific path would ship
silently, contradicting the test file's own "exhaustive" claim.

**Fix:** Add the two missing scenarios to
`tests/test_remediation_failure_details_authoritative.py`'s parametrized
case list (a fake `ExecutionVerifier` whose `verify()` returns
`{"outcome": "failed", ...}` / `{"outcome": "cancelled", ...}` without a
`failure_details` key, asserting the call site defensively backfills a
non-empty value), and add a defensive fallback in `execution_service.py`
at both call sites, e.g.:
```python
failure_details=outcome.get("failure_details") or "Provider reported a terminal outcome with no additional detail.",
```

### WR-02: Unrecognized blocker-code telemetry is wired only in `WorkflowBlockers`, not in the two other `blockerCopy()` call sites

**File:** `web/src/app/remediation/page.tsx:41-60` (`stepBlockerEcho`), `:1181-1185`
(`RecoveryControls`'s supersede-ineligibility-reason callout), `:995-1031`
(`WorkflowBlockers`, the only site with `useRef<Set<string>>` telemetry tracking)

**Issue:** Plan 03.6-04's Task 1 requires `blockerCopy`'s unrecognized-code
resolution to fire `console.warn("remediation.blocker.unknown_code", { code })`
"exactly once per distinct unrecognized code," and Plan 03.6-05 explicitly
states the Supersede race-handling callout reuses `blockerCopy`
"anything else falls through to the same unrecognized-code fallback/telemetry
Plan 03.6-04 already implemented." In the shipped code, the
`seenUnknownCodes` `useRef` tracking and the `console.warn` call live only
inside the `WorkflowBlockers` component (page.tsx:1002-1014). The module-level
`stepBlockerEcho` function (the inline per-step echo directly beneath a step's
blocker rows, and the same function invoked at the top of every step's content
block, e.g. `page.tsx:891` for `verify`) and `RecoveryControls`'s
`{blockerCopy(supersedeIneligibilityReason, "verify").message}` render
(`page.tsx:1183`) both call `blockerCopy()` directly and render its safe
fallback text correctly, but neither ever calls `console.warn`. Concretely: a
`supersede_ineligibility_reason` value returned by the server that isn't one
of the three documented codes (`execution_active`/`already_superseded`/
`submission_ambiguous`) renders the safe unrecognized-code sentence with zero
telemetry, and the inline step echo likewise never telemeters for any
unrecognized `workflow.blockers[]` code, even though the cross-step panel
rendering the same row does. This does not affect operator-visible correctness
(fallback copy still renders) but reduces observability of unrecognized codes
reaching the recovery-control write path, which is exactly the surface this
phase is trying to make provable.

**Fix:** Lift the "seen unknown codes" tracking out of `WorkflowBlockers` into
a page-level (or module-level, if telemetry-per-code-for-lifetime-of-page is
intended regardless of remount) `useRef`/singleton shared by all three call
sites, or route `stepBlockerEcho`/`RecoveryControls`'s ineligibility rendering
through a single shared warn-once helper exported from `blockers.ts` alongside
`blockerCopy`.
