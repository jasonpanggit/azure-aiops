<objective>
Make a saved design policy actually change what the server derives, and give the browser a way to ask for the new
answer. This is the second half of TOPO-04: its backend files are disjoint from the correctness cluster, and its
single web file is the shared fetch hook, so nothing in the topology or projection path is touched here.

It runs in wave 3, immediately after the correctness cluster rather than beside it. The two plans modify no file
in common, but plan 12-03 verifies itself by running `tests/test_api_network.py`, which is exactly the module this
plan rewrites — running them concurrently would let one plan's half-written test module decide the other plan's
gate. Sequencing costs one wave and removes the ambiguity entirely; this plan's own dependents (12-08 in wave 6)
are unaffected.

Purpose: RESEARCH identifies the true blocker as server-side, not client-side. The provider runtime serves the
last completed refresh for up to thirty seconds and the policy is bound at service construction, so a policy write
leaves derived gaps stale regardless of what the browser does — a client-side refetch alone cannot fix it.
Separately, `useApi` returns only data, error, and loading, so no mutation can invalidate any loader, and the page
hard-mirrors the engine's rule list client-side while the engine's real supported targets and operators are never
published.

Output: a policy write that invalidates derived analysis, a revision accessor usable as a cache key, an additively
published engine contract, and a refetch handle on the shared hook.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator-authored rule body -> rule engine | Untrusted declarative assertion content crosses into evaluation |
| policy write -> derived analysis cache | A stale cache serves conclusions attributed to a policy that is no longer in effect |
| browser refetch -> live resource-graph path | Client-triggered invalidation can amplify into upstream request load |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-16 | Tampering | Derived gaps served from a cache computed under a superseded policy | high | mitigate | Key the derived-analysis cache on the store revision and invalidate on write (Task 1) |
| T-12-17 | Injection | Operator-authored assertion bodies evaluated by the rule engine | high | mitigate | Server-side validation remains the only semantic authority; the engine stays declarative with no eval; no client validation path is added (Task 2, ASVS V5) |
| T-12-18 | Denial of Service | Refetch bursts amplifying against the live resource-graph path | medium | mitigate | Coalescing window in the hook plus retention of the existing read cache interval (Tasks 1 and 3) |
| T-12-19 | Tampering | Lost-update on concurrent policy writes | medium | mitigate | Preserve and test the existing expected-revision guard, including on the in-memory fallback (Task 1) |
| T-12-20 | Information Disclosure | Invalid-reason strings echoing internal engine internals to the operator | low | accept | The validator's reason strings are already operator-facing and describe the submitted body only |
| T-12-SC | Tampering | npm/pip/cargo installs | low | accept | RESEARCH §Package Legitimacy Audit records zero package installs for this phase; this plan adds none |
</threat_model>
