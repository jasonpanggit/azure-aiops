<objective>
Resolve the one external-semantics question this phase cannot answer from the repository, before the private-link
projection makes its consequences visible to operators.

Purpose: `PRIVATE_LINK_RESOURCE_TYPES` maps Microsoft Fabric capacities to a private-link resource, so the gap
analyzer already raises high-severity missing-private-endpoint findings against them. Today those findings are
invisible on the canvas because the resources are never projected. Plan 12-06 projects them, which makes the
findings prominent. RESEARCH records this as assumption A1 with `[ASSUMED]` confidence: neither web search nor the
documentation provider was reachable during research, so there is no in-repo or external evidence beyond the type
map itself that per-resource private endpoints are the correct control for a Fabric capacity. If A1 is false, the
projection turns an existing false positive into a prominent one — a copy and severity problem, not a rendering
problem. Both RESEARCH §Open Questions and `12-UI-SPEC.md` C-3 require a blocking human checkpoint here.

This plan is deliberately isolated so the checkpoint blocks only the private-link projection chain. Plans 12-01
through 12-04 remain autonomous and unaffected; only 12-06 and its successors wait on this decision.

Output: a recorded, dated disposition that plan 12-06 reads before deciding how to surface Fabric gaps.
</objective>

    1. `Microsoft.Fabric/capacities` supports **per-resource** private endpoints. In this case the existing

       with no copy change.
    2. Fabric Private Link is **tenant-level only** (configured once for the tenant, not per capacity). In this
       case the per-resource gap is a false positive, and plan 12-06 must project the node for visibility while
       qualifying or downgrading the finding rather than amplifying it.
