# Phase 03.5 Plan 07: Minimal approved UI contract Summary

The `/remediation` Approve/Run/Verify steps now render exactly what Plans 03.5-01 through 03.5-06 enforce: per-row satisfied/unmet approval requirements, the locked demo self-approval disclosure (policy banner + audit badge), independent approve/operate disabled-reason text, and the five-state stale-approval status line — replacing the prior opaque JSON-dump paragraph and binary `Latest decision: ...` line, with zero change to the five-step layout, patch picker, retry control, or polling.

## What Was Built

- **`web/src/lib/types.ts`**: `RemediationDecision` gained `approver_roles: string[]`, `approval_policy_version: string`, `self_approved: boolean`, `self_approval_policy_id?: string` (additive).
- **`web/src/lib/services.ts`**: new `RemediationApprovalRequirement` interface (`policy_id`/`role`/`stage`/`satisfied`/`unmet_reason?`/`approval_evidence_required`); `RemediationWorkflow["approval"]` gained `status`/`stale_reasons`/`can_approve`/`approve_ineligible_reason?`/`allow_self_approval`; `RemediationWorkflow["action"]` gained `can_operate`/`operate_ineligible_reason?`.
- **`ApprovalRequirementsList`** (new, page-local component in `page.tsx`): renders the `{satisfiedCount} of {totalCount} requirements satisfied` summary line, one row per requirement with a `Satisfied`/`Unmet` `StatusBadge`, role/policy_id/stage, the mapped closed-vocabulary `unmet_reason` copy, and an evidence-required `<details>` disclosure — replaces the raw `<p>Required: {details(...)}</p>` paragraph.
- **`ApprovalStatusLine`** (new): renders the five-status (`none`/`current`/`stale`/`rejected`/`expired`) `StatusBadge` + exact locked copy, joining `stale_reasons` with "and" (single reason renders without a trailing conjunction) — replaces the binary `Latest decision: ...` line.
- **Demo self-approval policy banner**: rendered above the requirement list using the existing `.callout` shape (its default styling already is the `info` tone) with the exact locked copy, present only when `workflow.approval.allow_self_approval` is true — never an empty shell otherwise.
- **Decision-level self-approved audit badge**: `ExecutionAudit` extended to accept an optional `decisions` prop and render each decision with an `info`-tone `Self-approved (demo exception)` badge (plus the `self_approval_policy_id` when present) beside any decision whose `self_approved` is true, never beside one that is false.
- **Approve/operate disabled reasons**: `Record decision` disabled when `!workflow.approval.can_approve` (in addition to existing conditions) with the exact reason paragraph in normal flow; `Review and run`/`Confirm run` disabled when `!workflow.action.can_operate` (independently of the existing `canRun` gate) with its own exact reason paragraph.
- **Backend, minimal, additive**: `RemediationExecutionService.allow_self_approval()` (new public accessor wrapping the existing private `_allow_self_approval()` callable) and `plan_workflow`'s response gained `approval.allow_self_approval` — the only way the frontend can know whether the demo self-approval policy is currently enabled, since no existing workflow field or settings route exposed it.

## Deviations from Plan

### Auto-added missing functionality

**1. [Rule 2 - Missing critical functionality] `workflow.approval.allow_self_approval` did not exist anywhere**
- **Found during:** Task 2, implementing the self-approval policy banner.
- **Issue:** The UI-SPEC requires the banner to render "whenever the effective governance policy has `agent_policy.allow_self_approval = true`" and explicitly allows reading it from the workflow response OR an existing settings surface — but neither existed. `record_remediation_decision`'s route context has no way to expose this either (it's a construction-time property of `RemediationExecutionService`, not request-scoped data).
- **Fix:** Added `RemediationExecutionService.allow_self_approval()` — a small, public, additive accessor wrapping the already-private `_allow_self_approval()` callable (zero behavior change, resolved per call exactly like the private one) — and projected it as `workflow.approval.allow_self_approval` in `plan_workflow`'s existing `_optional_execution_service(context, scope)` call, which the route already had access to.
- **Files modified:** `src/intelligence/remediation/execution_service.py`, `src/api/routers/remediation.py` (both outside this plan's declared web-only file list, but a minimal, in-budget, additive exception — no new route, no new plumbing beyond one getter and one dict key).

### Auto-fixed Issues

**2. [Rule 1 - Bug] `page.test.tsx`'s fixture builder predated every new field**
- **Found during:** Running the pre-existing test suite after Task 1's type changes.
- **Issue:** `workflowFixture()`'s `approval`/`action` objects and `requirements: [{ role: "Change Manager" }]` carried none of the new fields, so the two pre-existing tests exercising `Record decision`/`Review and run` failed once those buttons started checking `can_approve`/`can_operate` (both `undefined`, falsy, disabling the buttons the tests needed to click).
- **Fix:** Extended the fixture builder with sensible defaults for every new field (`can_approve`/`can_operate` default `true`, `status` derived from the existing `approvalCurrent` flag, `allow_self_approval` default `false`, a properly-shaped single requirement row), all overridable via new named override keys (`canApprove`/`canOperate`/`approvalStatus`/`staleReasons`/`allowSelfApproval`/`approvalRequirements`) consumed by the new Task 3 tests.
- **Files modified:** `web/src/app/remediation/page.test.tsx`

No stubs, no deferred rendering — every new field this plan's contract requires is wired to real server data.
