<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `POST /remediation-plans/{plan_id}/decisions` | The only route that durably records an approval decision -- must require the new `approve` action, not the broader `operate` action a wider population of principals may hold. |
| `GET .../workflow`'s can_approve/can_operate | Purely informational, server-computed -- must never be settable/overridable by request data, and must never be the sole enforcement (the real enforcement stays in the route-level RBAC dependency and the execution-service gate). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.5-13 | Elevation of Privilege | `record_remediation_decision` RBAC gate | critical | mitigate | Switched from `OperatePrincipal` to `ApprovePrincipal`; verified by a dedicated 403 test with an operate-only principal (Task 3). |
| T-03.5-14 | Spoofing | `approver_roles` derivation | high | mitigate | Derived server-side from `principal.grants`, never accepted from the request body (`RemediationDecisionRequest` gains no such field) -- verified by Task 3's role-derivation test. |
| T-03.5-15 | Information Disclosure | `can_approve`/`can_operate` computed via `try/except ApiError` | low | accept | These fields reveal only whether the CURRENT caller holds a capability, not any other principal's grants or any out-of-scope data -- consistent with the existing `ineligibility_reason` pattern already exposed by this route family. |

</threat_model>
