# Phase 03.5 — UI Design Contract

> Visual and interaction contract for unified remediation approval governance. This is a
> narrow, surgical refinement of the existing five-step `/remediation` workflow
> (`web/src/app/remediation/page.tsx`) — it adds requirement-level satisfaction display,
> role/policy attribution, an explicit demo self-approval disclosure, distinct
> approve-vs-operate authorization, and an explicit stale-approval state. It does not
> redesign the page, add steps, or touch blocker/degradation UX, the patch picker, retry
> controls, or polling — those remain Phase 03.6.
>
> **Amended 2026-09-04 (CR-05 fix):** added the minimal role-selection contract (a decision
> attests exactly one required role; the client must select which one whenever more than one
> unmet row is eligible) and per-row satisfied-by disclosure. Still no general UX redesign —
> this amendment is scoped identically to the rest of this document.

## Phase Boundary (do not exceed)

**In scope for this contract:**

1. Approval requirement rows showing satisfied/unmet state with responsible role and policy.
2. Explicit demo self-approval disclosure (policy-level banner + decision-level audit badge).
3. Distinct, server-authoritative `approve` vs `operate` button gating with visible reasons.
4. An explicit stale-approval state, distinct from "never approved," "rejected," and "expired."
5. Preservation of the current five-step layout (`select → review → approve → run → verify`)
   and the current Fluent UI/design tokens.

**Explicitly deferred to Phase 03.6 — do not design or implement here:**

- General blocker/degradation panels for provider/source unavailability.
- Patch picker redesign (`.remediation-patch-picker` / `.remediation-patch-list`).
- Retry-control redesign (`Retry approved snapshot`, retry eligibility copy).
- Bounded client polling UX.

If an implementation task in this phase touches any of the deferred items above except to
preserve their current appearance unchanged, treat it as out of contract.

### Visual direction

- The five-step nav (`.remediation-workflow-steps`), step ordering, and step labels
  (`Select fix`, `Review impact`, `Approve`, `Run`, `Verify`) do not change.
- New content is added *inside* the existing `approve` and `run` step panels only.
- Satisfaction state is never conveyed by color alone — every satisfied/unmet/stale badge
  carries a text label.
- A **stale** approval is visually distinct from both a fresh **current** approval (success
  tone) and a **never-approved** state (neutral/pending tone). Stale always uses the
  amber "Stale" treatment already established for stale exposure data in `03.1-UI-SPEC.md` —
  never success green, never critical red (staleness is expected lifecycle behavior, not
  failure).
- The self-approval disclosure is informational, not alarming: use the `info` tone, not
  `warning` or `critical`.

## Approval Requirement Contract (machine-checkable satisfaction)

Replaces the current unstructured rendering at `page.tsx:568`
(`<p>Required: {details(workflow.approval.requirements)}</p>`), which JSON-dumps
`approval_requirements` with no satisfied/unmet distinction and no role attribution.

### Required data shape

Each row in `workflow.approval.requirements` must carry, at minimum:

| Field | Type | UI use |
|-------|------|--------|
| `policy_id` | string | Rendered as a monospace chip, e.g. `stage-gate`, `change-control` |
| `role` | string | Rendered as the "Responsible role" label on the row |
| `role_id` | string (optional; absent only on a pre-CR-01 legacy row) | Stable id satisfaction actually keys on (Phase 03.5 CR-01/CR-05 fix) — used, not displayed directly, to drive the role-selection control below |
| `stage` | string | Rendered as small secondary text under the role |
| `satisfied` | boolean | Drives the `success`/`warning` `StatusBadge` tone and label |
| `unmet_reason` | closed enum, present only when `satisfied` is `false` | Drives the exact copy row below |
| `approver` | string (optional; present only when `satisfied`) | **(CR-05 fix)** Rendered as "Satisfied by `{approver}`" — discloses exactly which principal's decision satisfied this row, so an operator can never mistake one person's sign-off for genuine multi-stakeholder governance |
| `decision_id` | string (optional; present only when `satisfied`) | **(CR-05 fix)** Rendered alongside `approver` as a monospace decision reference |
| `evidence_required` | string[] | Rendered as a bulleted disclosure list (existing `approval_evidence_required` content, unchanged wording) |

This supersedes the current presentation-only `status: "Required - Not Approved"` string and
opaque `approval_recorded` boolean as the *displayed* satisfaction signal — the row now always
shows a boolean-backed `Satisfied`/`Unmet` badge instead of free text.

**Field-mapping clarification (`evidence_required`):** the wire field name stays
`approval_evidence_required` exactly as it exists today on `approval_requirements` rows — this
contract does not rename or add a backend field. `evidence_required` above is this UI-SPEC's
and `ApprovalRequirementsList`'s prop-level contract name for that same array: the row-rendering
code maps `approval_requirements[i].approval_evidence_required` straight into the component's
`evidence_required` prop, unchanged wording, unchanged ordering, no filtering or transformation.
Only the local component prop is named `evidence_required`; the stored/API field remains
`approval_evidence_required`.

### `unmet_reason` closed vocabulary and copy

| `unmet_reason` | Requirement-row copy |
|----------------|----------------------|
| `pending` | `No decision recorded yet for this role.` |
| `wrong_role_decision` | `A decision exists, but not from the required {role}. This requirement remains unmet.` |
| `stale_action_version` | `The plan's action version changed since the last decision for this role.` |
| `stale_evidence_snapshot` | `The executable preview changed since the last decision for this role.` |
| `stale_policy_version` | `The approval policy was updated since the last decision for this role.` |
| `expired` | `The last decision for this role expired.` |

Each row renders: `StatusBadge` (`Satisfied` / `Unmet`) · `role` (Label size) · `policy_id`
(monospace chip) · `stage` (secondary text) · the mapped copy line above when unmet ·
**(CR-05 fix)** `Satisfied by {approver}` (plus decision id, monospace) when satisfied ·
`evidence_required` bullets in a `<details>`/disclosure identical in interaction pattern to
the existing `Evidence and audit history` disclosure.

### Requirement list header

- Heading: `Approval requirements` (Section heading style).
- Summary line above the list: `{satisfiedCount} of {totalCount} requirements satisfied` —
  never omit the denominator, never show a bare count.
- The `Record decision` control (see Authorization Contract) is visually subordinate to this
  list — requirements are read first, the decision form second, exactly matching current
  DOM order in `page.tsx:557-596`.

### Role selection contract (Phase 03.5 CR-05 fix — minimal, Phase 03.5-scoped)

`record_remediation_decision` now accepts an optional `role_id` field: one decision attests
exactly one required role (`approval_role_id`), so the client must be able to state which row
a new decision is for whenever more than one currently-unmet row is eligible for the calling
principal to attest.

- **Zero or one unmet-and-eligible row:** no selection control is shown/required; the decision
  form behaves exactly as before this fix (the single eligible `role_id`, if any, is submitted
  automatically).
- **More than one unmet-and-eligible row:** a `Required role this decision is for` `<select>`
  appears between the `Decision` field and the `Rationale` field, listing every unmet row's
  `role` text (deduplicated by `role_id`). `Record decision` is disabled until a role is
  selected. This is the full extent of this fix's UI scope — it is explicitly **not** a general
  redesign of the approve step (deferred to Phase 03.6), only the minimal contract needed so an
  operator cannot record an ambiguous decision.
- Submitting sends the selected `role_id` verbatim as the `role_id` field on the decision
  request body.
- The demo same-person self-approval exception (`allow_self_approval`) is unaffected by this
  contract — it still governs whether a *single* principal may satisfy a role they also
  requested, never how many separate decisions a multi-role plan needs. A multi-role plan still
  requires one decision per required role regardless of `allow_self_approval`.

## Demo Self-Approval Disclosure Contract

Two distinct, non-interchangeable surfaces:

### 1. Policy-level banner (Approve step, shown whenever the effective governance policy has
`agent_policy.allow_self_approval = true`)

- Placement: directly above the requirement list, using the existing `.callout` shape with
  `info` tone (not `callout-warning`, not `callout-critical`).
- Copy (locked): `Demo policy exception: self-approval is enabled for this environment.
  Approvers may approve their own requests. Production policy defaults this off.`
- This banner is present for the entire duration `allow_self_approval` is enabled — it is not
  dismissible, since it is a standing governance fact, not a transient notice.
- When `allow_self_approval` is `false` (default/production), render nothing in its place —
  do not show an empty callout shell.

### 2. Decision-level audit badge (Verify step / audit history, per recorded decision)

#### Required data shape (durable, server-set — no client-side identity comparison)

| Field | Type | Set when | UI use |
|-------|------|----------|--------|
| `decision.self_approved` | boolean | Written once, server-side, inside the approval gate at decision-record time — `true` only when the gate itself permitted this specific decision under `allow_self_approval = true` for an approver who was also the request's originator. The field is durable on the stored decision record; it is never recomputed, inferred, or re-derived by the client. | Sole, exhaustive input driving the badge below. There is no `plan.requested_by`-vs-`approver` comparison anywhere in this contract or its implementation — `requested_by` is not a defined field on the plan/workflow projection and must not be introduced solely to power this badge. |
| `decision.self_approval_policy_id` | string, present only when `decision.self_approved` is `true` | Recorded alongside `self_approved` at the same decision-record time, identifying the policy context (e.g. `policy_id`/version) that permitted the exception | Rendered as a monospace detail on the badge, e.g. `Self-approved (demo exception) · stage-gate`. Omitted (badge shows with no suffix) for any legacy decision recorded before this field existed. |

- When `decision.self_approved` is `true`, render an `info` `StatusBadge` labeled
  `Self-approved (demo exception)` immediately beside that decision's entry in the audit list
  (`ExecutionAudit` / `Evidence and audit history` disclosure). The UI reads this one stored
  boolean and renders — it performs no identity matching of its own.
- This badge is permanent, immutable audit history — it renders identically regardless of the
  policy's *current* value, because `self_approved` is fixed at decision-record time (inside
  the approval gate, alongside the decision itself) and never recomputed afterward.
- Never conflate the two surfaces: a decision recorded with `self_approved: true` always shows
  the decision-level badge, independent of whether the policy banner (surface 1) is currently
  visible; a decision recorded with `self_approved: false` never shows it even while the policy
  banner is visible.

## Approve vs Operate Authorization Contract

Server-authoritative; the client never infers eligibility from role heuristics.

### Required data shape (additive fields, non-breaking)

| Field | Type | UI use |
|-------|------|--------|
| `workflow.approval.can_approve` | boolean | Gates the `Record decision` control |
| `workflow.approval.approve_ineligible_reason` | string, present only when `can_approve` is `false` | Rendered directly under the disabled control |
| `workflow.action.can_operate` | boolean | Gates the `Review and run` / `Confirm run` controls, alongside the existing `canRun` evidence/preview/approval gate |
| `workflow.action.operate_ineligible_reason` | string, present only when `can_operate` is `false` | Rendered directly under the disabled control |

### Button behavior

| Control | Enabled when | Disabled copy shown beneath it |
|---------|--------------|--------------------------------|
| `Record decision` (Approve step) | `can_approve` is `true` (in addition to today's rationale/expiry/preview validation) | `You can review this approval but cannot record a decision. Ask an approver to record it.` |
| `Review and run` / `Confirm run` (Run step) | `can_operate` is `true` **and** the existing `canRun` conditions hold | `You can approve work but cannot run it. Ask an operator to run this approved snapshot.` |

- These two gates are independent and both server-derived — a caller may see one, both, or
  neither control enabled. Do not merge them into a single "you can't do this" message; each
  control shows its own reason.
- A principal with only `operate` sees the requirement list and current-approval state (read),
  the `Record decision` control disabled with its reason, and — once a current approval
  exists from someone else — the `Run` controls enabled normally.
- A principal with only `approve` sees the `Record decision` control enabled, and the `Run`
  controls disabled with their reason even after recording an approval themselves.
- This distinction is visible without attempting the action: buttons render `disabled` with
  the reason text present, not merely a toast on click — consistent with the existing
  server-authoritative-eligibility pattern already used for `canRun`/`ineligibility_reason`.

## Stale Approval State Contract

Replaces the current binary `workflow.approval.current` boolean's sole role in the Approve-step
copy at `page.tsx:569` (`Latest decision: {decision} by {approver}` with no staleness signal).

### Required data shape

| Field | Type | UI use |
|-------|------|--------|
| `workflow.approval.status` | closed enum: `none` \| `current` \| `stale` \| `rejected` \| `expired` | Drives the latest-decision summary line and its `StatusBadge` |
| `workflow.approval.stale_reasons` | string[] of the same closed vocabulary as `unmet_reason` (`stale_action_version`, `stale_evidence_snapshot`, `stale_policy_version`), present only when `status` is `stale` | Rendered as the explanatory sentence beneath the badge |

`workflow.approval.current` (existing boolean) remains and is equivalent to
`status === "current"` — additive, not a breaking rename, so existing `canRun`/step-status
logic keyed on `current` is unaffected.

### Latest-decision summary line, by `status`

| `status` | `StatusBadge` | Copy |
|----------|----------------|------|
| `none` | neutral, `No decision` | `No decision recorded yet.` |
| `current` | success, `Approved` | `Approved by {approver} on {decided_at}. This approval matches the current version, evidence, and policy.` |
| `stale` | warning, `Stale` | `Approved by {approver} on {decided_at}, but {joined reasons} since. A new decision is required before running.` — `{joined reasons}` maps each `stale_reasons` entry through the same copy fragments as the Requirement Contract's `stale_*` rows (e.g. `the plan's action version changed`, `the executable preview changed`, `the approval policy was updated`), joined with `and`. |
| `rejected` | critical, `Rejected` | `Rejected by {approver} on {decided_at}: {reason}` |
| `expired` | warning, `Expired` | `Expired on {expires_at}. A new decision is required.` |

- The existing `stale_execution_preview` submit-time error path (`page.tsx:276-279`) remains as
  the last-resort safety net for a race between page load and a concurrent evidence change; it
  does not replace this persistent, pre-submit `stale` state — a caller must be able to see
  staleness *before* attempting to record a decision, not only discover it from a failed submit.
- `Run` never becomes eligible while `status` is `stale`, `rejected`, `expired`, or `none` —
  this is already implied by `canRun`'s dependency on `workflow.approval.current`; this contract
  only makes the *reason* legible where today it is silent.
