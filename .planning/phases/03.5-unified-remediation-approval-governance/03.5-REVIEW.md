## Summary

This phase's stated goal — one evidence-sensitive, per-role, cross-family approval
policy, enforced identically for patch and Defender configuration, with a distinct
`approve` permission and an honestly-disclosed demo self-approval exception — is
architecturally well-factored: `action_version_for()`, `approval_gate.py`'s shared
`requirement_satisfaction()`/`latest_decision_status()`, and the RBAC `approve`/`operate`
split are each individually correct, well-tested in isolation, and a real improvement
over Phase 03's decorative governance (CR-04/CR-05).

However, four **integration-level defects** were found by tracing the same functions
this phase's own plans exercised in isolation against the *actual* production
call graph and the *actual* production dependency-injection wiring in
`src/api/runtime.py` (not touched by any 03.5 plan, but the necessary integration
point for constructor signatures 03.5-05 changed). Every one of the four is
reproduced below with a runnable proof against the real, unmodified codebase — not
a code-reading inference — and none is caught by the phase's own test suite
(2501 backend + 206 web tests, all passing, per `03.5-VERIFICATION.md`), because
every test that exercises `approval_requirements`/self-approval either bypasses the
real `record_remediation_decision` HTTP route (writing decisions directly to the
repository with hand-picked `approver_roles` matching the plan's own literal role
strings) or empties `approval_requirements` to `[]` before calling `execute()`.

**CR-01** is the most severe: the real, only production route for recording an
approval (`record_remediation_decision`) derives `approver_roles` exclusively from
RBAC capacity names (`approver`/`admin`); every `ApprovalEngine` policy in this
codebase — the live planner's own hardcoded defaults ("Change approver", "Security
Response Owner") *and* the Fabric/catalog planner's organizational-role catalog
("Change Manager", "Change Advisory Board", "Stage Gate Approver", ...) — uses role
names that can never equal "approver" or "admin". The result, proven end-to-end
against the real FastAPI app below: **no plan carrying any real `approval_requirements`
row can ever be executed in production, regardless of who approves it or how many
people approve it, including an admin.** This is not the "future gap for richer
organizational catalogs" `STATE.md`/`03.5-VERIFICATION.md` describe — it is total,
for every deployed planner, for the only code path (`record_remediation_decision`)
that ever writes a decision in production.

**CR-02** is a distinct authorization-logic defect in the shared gate itself: the
self-approval separation-of-duties check inspects only the plan's single
overall-latest decision's approver, never the decision that actually satisfies each
required-role row. A requester can self-approve one of several required roles early
and have a different, legitimate approver sign a later-decided role, and the gate
never notices the requester was also an approver. Proven end-to-end.

**CR-03** is a wiring gap between this phase's new `RemediationExecutionService.allow_self_approval`
constructor parameter and the one production factory that builds it
(`src/api/runtime.py::_execution_service_for_scope`): the parameter is never passed,
so it silently defaults to `False` forever, regardless of the administrator's real
`agent_policy.allow_self_approval` setting — which *is* correctly wired to
`PatchingService`. Because the new shared gate now runs and raises before
`PatchingService`'s own check is ever reached (a deliberate, documented change in
03.5-05), this is a real regression: the demo self-approval exception this phase
built UI, audit, and a locked policy banner for is dead in the only place it runs.

**CR-04** is a spec-level design gap, present in `03.5-UI-SPEC.md` itself (not just
the code): `workflow.approval.current`/`canRun` remain keyed solely on whether the
single latest decision is fresh, never on whether every `approval_requirements` row
is satisfied. A plan can show a green "Approved" badge and an enabled "Review and
run" button while every required role is unmet; the backend still correctly refuses
execution, but the UI actively misleads the operator about readiness.

Five Warnings and two Info items are additionally reported below, covering
scope-blind `can_approve`/`can_operate` projection, a self-referential (never-fires)
`policy_version` staleness check at the gate, and a self-approval audit fact
recorded before execution is confirmed to actually happen.

## Narrative Findings (AI reviewer)

### Critical

#### CR-01: `approver_roles` is derived exclusively from RBAC capacity names, which can never satisfy any deployed `ApprovalEngine`'s organizational role names — production approval is permanently broken for every plan carrying real requirements

**File:** `src/api/routers/operations.py:480-509`; `src/intelligence/remediation/approval_gate.py:118-129`; `src/semantic/live_operations.py:317-330`; `tests/fixtures/sample_remediation_planning.json` (production-representative role catalog)

**Issue:** `record_remediation_decision` — the *only* route in this codebase that ever writes a decision — computes:
```python
approver_roles = [
    grant.role for grant in principal.grants if grant.role in {"approver", "admin"}
]
```
This can only ever produce `["approver"]`, `["admin"]`, or both — literal RBAC capacity strings. Meanwhile every `ApprovalEngine` this phase's own live-patch/Defender planners construct uses organizational role strings that never equal either:
```python
_DEFAULT_PATCH_APPROVAL_POLICIES = [{"policy_id": "live-patch-change-approval", "roles": ["Change approver"], ...}]
_DEFAULT_CONFIGURATION_APPROVAL_POLICIES = [{"policy_id": "live-defender-configuration-approval", "roles": ["Security Response Owner"], ...}]
```
and the Fabric/catalog planner's production role catalog (`remediation_approval_policies` Silver table, exercised via `tests/fixtures/sample_remediation_planning.json`) uses `"Change Manager"`, `"Application Owner"`, `"Service Owner"`, `"Support Team"`, `"Business Service Owner"`, `"Operations Risk Owner"`, `"Change Advisory Board"`, `"Stage Gate Approver"`. `approval_gate.requirement_satisfaction()` requires *exact* casefolded string equality between a requirement row's `role` and an entry in a decision's `approver_roles` (`approval_gate.py:118-124`) — `"change approver" != "approver"`, full stop, for every one of these.

Proven end-to-end against the real, unmodified FastAPI app (`tests/test_api_remediation_execution.py`'s own `_client()` fixture, a production-representative Fabric/catalog plan for a `Production`/`Mission Critical` VM, an **admin** principal — the highest privilege in the system):
```
recorded approver_roles: ['admin']
execute status: 409 {"error":{"code":"conflict", ...,
  "details":{"reason":"approval_requirements_unmet",
    "unmet":"[{'role': 'Change Advisory Board', 'unmet_reason': 'wrong_role_decision'}, {'role': 'Business Service Owner', ...},
              {'role': 'Operations Risk Owner', ...}, {'role': 'Application Owner', ...}, {'role': 'Change Manager', ...},
              {'role': 'Service Owner', ...}, {'role': 'Support Team', ...}, {'role': 'Stage Gate Approver', ...} x4]"}}}
```
All 11 requirement rows are refused as `wrong_role_decision` even though an admin recorded a fully valid, current, unexpired approval through the real route. This is not scoped to "richer organizational role catalogs" as `STATE.md`/`03.5-VERIFICATION.md` characterize it — it is universal: the live planner's own hardcoded defaults ("Change approver") fail identically, since "change approver" ≠ "approver" as a casefolded string either. There is no client-supplied `roles` field on `RemediationDecisionRequest` (`src/api/models.py:230-247`) and no other write path exists. **No deployment of this system, as configured, can ever execute a governed remediation plan after this phase's changes land**, unless every `ApprovalEngine` policy's `roles` list happens to literally be `["approver"]`/`["admin"]` — which none of the shipped defaults are.

Before this phase, `_check_approval_gate` only required "some approved decision exists" (CR-04 from the Phase 03 review — correctly identified as insufficiently governed, but *functional*). This phase's fix makes the governance surface *stricter* than the vocabulary it was layered onto can ever satisfy, converting "insufficiently governed" into "completely non-functional."

**Fix:** Either (a) `ApprovalEngine.requirements()` rows must carry a stable RBAC-capacity-compatible role identifier alongside the organizational display role (the CONTEXT.md decision literally says "Requirements carry stable policy/role identifiers, not presentation text alone" — this was not honored), or (b) `record_remediation_decision` must accept and validate a caller-asserted organizational role (checked against a directory/claim, not just RBAC capacity) rather than deriving only RBAC-capacity strings, or (c) `requirement_satisfaction()`'s role match must fall back to "principal held `approve`/`admin` AND the plan's policy has no distinct role-claim source configured" for deployments that have not opted into organizational role catalogs. Whichever direction is chosen, this must be proven with an end-to-end HTTP-level test (decision → execute) against each shipped planner's *actual* default policies, not a hand-constructed test plan with `approval_requirements: []` or a fixture that copies `approver_roles` from the plan's own requirement list.

#### CR-02: Self-approval separation-of-duties only inspects the plan's single overall-latest decision, never the decision that actually satisfies each required role — a multi-role plan can be self-approved for one role and executed

**File:** `src/intelligence/remediation/execution_service.py:270-362,1429-1433`

**Issue:** `_check_approval_gate` resolves self-approval as:
```python
decision = self._latest_decision(plan_id)   # max(decisions, key=decided_at) -- ANY role
...
if requested_by and is_self_approval(requested_by, decision.get("approver")):
    ...
```
`_latest_decision` picks the single most-recently-decided record across *all* roles on the plan, then `is_self_approval` compares the requester only against *that one record's* approver. `requirement_satisfaction()` (called just above, for the per-role check) independently walks *every* decision to find each row's own satisfying record — but the self-approval check never consults that per-row resolution. Proven with a runnable test against the real `RemediationExecutionService`/`PlanRepository`/`PatchingService`:

- Decision 1 (T-10min): `approver="attacker@example.com"`, `approver_roles=["Change Manager"]` — the requester self-approves the "Change Manager" row.
- Decision 2 (T-1min, later): `approver="security@example.com"`, `approver_roles=["Security Response Owner"]` — a legitimate, different approver signs the other required row.
- `service.execute(plan_id, requested_by="attacker@example.com")` → **`result["status"] == "running"`** — execution proceeds.

`_latest_decision` returns Decision 2 (the later one, by `security@example.com`); `is_self_approval("attacker@example.com", "security@example.com")` is `False`, so the self-approval branch never fires — even though `attacker@example.com` is both the requester *and* the recorded approver of a required row. `requirement_satisfaction()` correctly reports both rows satisfied (each from its own matching decision), so the per-role check (correctly closing CR-04's "one decision suffices" gap) passes, and the *only* remaining SoD backstop silently misses the case it exists to catch. `PatchingService._authorize_approval`'s own defense-in-depth check (`src/operations/patching/service.py:271-317`) shares this exact blind spot, since `execution_service.py` passes it the same single `decision.get("approver")` value (`approved_by=str(decision.get("approver") or "")` at lines 214, 441, 754) — it is not independent defense-in-depth against *this* class of bypass, only against the single-decision case.

**Fix:** Self-approval must be checked per satisfying decision, not against the plan's single latest decision:
```python
for row in satisfaction:
    if not row.get("satisfied"):
        continue
    satisfying_decision = _find_satisfying_decision(row, decisions_for_plan)  # the same lookup requirement_satisfaction() does internally
    if requested_by and is_self_approval(requested_by, satisfying_decision.get("approver")):
        if not self._allow_self_approval():
            raise RemediationExecutionError(..., reason="self_approval_not_permitted")
```
This likely requires `approval_gate.requirement_satisfaction()` to optionally return (or a sibling function to expose) the actual satisfying decision per row, not just `satisfied`/`unmet_reason`, so the gate can check identity against the record that *actually* counted.

#### CR-03: `RemediationExecutionService`'s only production factory never passes `allow_self_approval` — the demo self-approval exception is permanently disabled in the live execution path regardless of the administrator's real policy setting

**File:** `src/api/runtime.py:3039-3054` (vs. `2409-2420` and `2924-2933`, which correctly wire the same policy into `PatchingService`)

**Issue:** `_execution_service_for_scope` — the single function passed as `execution_provider` to `ApiContext` (`src/api/runtime.py:3211`) and therefore the only production constructor used for `execute`/`retry`/`supersede` *and* the read-side `plan_workflow`'s `allow_self_approval` disclosure — never passes `allow_self_approval`:
```python
return RemediationExecutionService(
    plan_repository=getattr(planner, "repository", None),
    patching_service=_patching_for_scope(scope),
    defender_configuration_adapter=_defender_configuration_adapter(),
    execution_store=_remediation_execution_store(),
    execution_verifier=_execution_verifier(),
    target_evidence_refresher=_target_evidence_refresher,
    verification_deadline_seconds=deadline_seconds,
    # <- no allow_self_approval kwarg; RemediationExecutionService.__init__'s
    #    default (allow_self_approval: ... = False) silently applies forever.
)
```
Both `PatchingService` production factories in the same file (`_load_patching_service:2409-2420`, `hybrid_patching:2924-2933`) correctly pass `allow_self_approval=_allow_self_approval`, which reads `agent_policy.get("allow_self_approval", False)` live on every call. Proven directly against the real class:
```
RemediationExecutionService.allow_self_approval() as wired in production runtime.py: False
Real agent_policy.allow_self_approval setting:                                       True
```
Because 03.5-05 deliberately moved self-approval enforcement into `_check_approval_gate`, which now runs and raises *before* `PatchingService.trigger()` is ever reached (a documented, intentional change — see `03.5-05-SUMMARY.md`'s "Gate-timing change" deviation), `PatchingService`'s own correctly-wired check is now unreachable dead code on the self-approval path for the live/production execution path: the shared gate's hardcoded-`False` default refuses every self-approval attempt first, no matter what an administrator configures. This is a functional regression for the patch family specifically (pre-phase, an admin-enabled self-approval *would* proceed via `PatchingService`'s own check) and means the demo self-approval banner/audit badge this phase built end-to-end UI for (`page.tsx:630-634`, `832-838`) can never actually render `allow_self_approval: true` or a `self_approved: true` decision from the real production wiring, no matter how `agent_policy.yaml` is configured. Zero test in `tests/test_api_runtime.py` covers this wiring, which is why it shipped clean through `03.5-VERIFICATION.md`'s full-suite regression.

**Fix:**
```python
return RemediationExecutionService(
    ...,
    allow_self_approval=_allow_self_approval,
)
```

#### CR-04: `workflow.approval.current`/`canRun` are keyed solely on the single latest decision's freshness, never on whether every `approval_requirements` row is satisfied — the UI can show "Approved" and an enabled Run button for a plan the server will always refuse to execute

**File:** `src/api/routers/remediation.py:342-386,452-459`; `web/src/app/remediation/page.tsx:383-386,679-692`; `.planning/phases/03.5-unified-remediation-approval-governance/03.5-UI-SPEC.md:296-298` (the design decision itself, not just the implementation)

**Issue:** `plan_workflow` computes `approval_current = latest_status["status"] == "current"`, where `latest_status` comes from `latest_decision_status()` — which evaluates only the plan's single most-recently-decided record's own freshness (action_version/snapshot/policy_version/expiry), completely independent of `requirement_satisfaction()`'s per-row result computed two lines later in the same function. The UI-SPEC itself documents this as intentional: *"`workflow.approval.current` (existing boolean) remains and is equivalent to `status === "current"` — additive, not a breaking rename, so existing `canRun`/step-status logic keyed on `current` is unaffected."* `page.tsx`'s `canRun` and the Run-step's "Review and run"/"Confirm run" buttons gate on exactly this flag (`page.tsx:383-386`), never on `workflow.approval.requirements.every(r => r.satisfied)`.

Proven directly against the shared pure functions this phase built, with a two-role requirement set and one decision that satisfies *neither* role:
```
per-row satisfaction: [{'role': 'Change Manager', 'satisfied': False, 'unmet_reason': 'wrong_role_decision'},
                       {'role': 'Security Response Owner', 'satisfied': False, 'unmet_reason': 'wrong_role_decision'}]
plan-level status: current
==> UI would render "Approved"/canRun=true while 2 of 2 required rows are UNMET.
```
The backend execution gate is *not* bypassed here — `_check_approval_gate` independently and correctly checks `requirement_satisfaction()` and refuses with `approval_requirements_unmet` regardless of what the UI shows. But the Approve step's `ApprovalStatusLine` renders a green `Approved` badge with the exact locked copy *"This approval matches the current version, evidence, and policy"*, and the Run step shows no warning and an enabled "Review and run" button, for a plan that will unconditionally 409 the moment the operator clicks through. This is a direct contradiction between what this phase's own workflow-projection route claims and what its own execution gate enforces — an operator-facing "audit truthfulness" failure baked into the approved UI-SPEC, not introduced by an implementation shortcut.

**Fix:** `approval_current` (and by extension `canRun`) must additionally require every requirement row satisfied:
```python
requirements_satisfied = all(row.get("satisfied") for row in requirements)
approval_current = latest_status["status"] == "current" and requirements_satisfied
```
This is a UI-SPEC-level correction, not just a code fix — the "additive, not a breaking rename" framing in `03.5-UI-SPEC.md:296-298` needs revisiting for a future phase, since it is the actual source of the gap.

### Warnings

#### WR-01: `can_approve`/`can_operate` in `plan_workflow` check only whether the principal holds the role anywhere, never whether their grant's scope actually reaches this plan — a scoped-out principal can see an enabled button that will 404 on submission

**File:** `src/api/routers/remediation.py:358-371`; `src/api/rbac.py:136-146`

**Issue:** `context.authorizer.require(principal, "approve"|"operate")` (`rbac.py:136`) only checks `principal.grants_for(action)` is non-empty — it takes no `scope` parameter and cannot know whether *this specific plan* falls inside any of those grants' scopes. A principal holding `Grant("approver", scope=Subscription("sub-2"))` and `Grant("reader", scope=unrestricted)` viewing a `sub-1` plan (visible because their *read* scope is unrestricted) will see `can_approve: true` — CONTEXT.md's D-05 promise ("using server authority rather than client guesses") is only half-honored: it is server-computed, but not scope-aware, unlike the actual write route (`record_remediation_decision`), which correctly narrows via `effective_scope(principal, "approve", scope)` and 404s the plan for exactly this principal. The operator sees an enabled "Record decision" button, clicks it, and receives a confusing "Remediation plan not found" rather than an accurate disabled state with a scope-based reason.

**Fix:**
```python
try:
    context.authorizer.effective_scope(principal, "approve", scope)
    # additionally verify the *plan's own* scope attributes fall within the narrowed result,
    # mirroring _filter_scoped's own check, before declaring can_approve True.
except ApiError:
    can_approve = False
```

#### WR-02: `stale_policy_version` at the execution gate is a tautology — it can never fire, because "current" policy_version is sourced from the very decision being evaluated

**File:** `src/intelligence/remediation/execution_service.py:319-326`

**Issue:** `_check_approval_gate` passes `policy_version=str(decision.get("approval_policy_version") or "")` — the *decision's own* recorded field — as the "current" value `requirement_satisfaction()` compares every decision against. For the row matching this exact decision, `_staleness_reasons` compares `decision.get("approval_policy_version")` to itself: always equal, by construction, never stale. This is a stronger defect than the documented "empty/interim simplification" framing in `03.5-05-SUMMARY.md`/`STATE.md` suggests — it is not merely inert (skipped), it is self-referentially guaranteed to always pass, silently defeating the intended "the `ApprovalEngine` policy changed since this decision was recorded" detection at the one enforcement point that actually blocks execution. (The read-side `plan_workflow`/`plan_approvals` routes do *not* have this defect — they correctly source `policy_version` from `_policy_version_for(planner)`, the plan's live engine — so this is an execution-gate-only gap, invisible to the UI.)

**Fix:** Thread the plan's live `ApprovalEngine.policy_version` into `_check_approval_gate` the same way `_policy_version_for(planner)` does at the route layer, rather than reusing the decision's own recorded value.

#### WR-03: `self_approved`/`self_approval_policy_id` are durably recorded before execution is confirmed to actually proceed — a failed downstream validation still leaves a "self-approval was used" audit fact

**File:** `src/intelligence/remediation/execution_service.py:319-362` vs. `204,211-234` (later, per-call, potentially-failing steps)

**Issue:** `record_self_approval(decision_id, policy_id="demo-self-approval")` is called inside `_check_approval_gate` (line 359), which returns before `_validated_execution_snapshot` (line 204/295, called separately in `execute()`), `self._store.create_or_get`/`transition` (lines 211-234), or the adapter submission ever run. If any of those later steps raises (stale snapshot, target no longer found, store conflict), the decision has already been durably, irreversibly marked `self_approved: true` — an audit fact asserting a self-approval was consumed to execute something that never actually executed. `record_self_approval`'s idempotency guard prevents a *second* write on retry, but does not retroactively correct the premature first one.

**Fix:** Defer `record_self_approval` until after the point where execution is guaranteed to proceed (e.g., after `_store.create_or_get`'s `claimed` check succeeds), or record a distinct "self-approval evaluated, permitted" fact separate from "self-approval consumed by a completed execution."

#### WR-04: `RemediationDecisionStore.append()` accepts and stores `approver_roles` for **rejected**/**expired** decisions identically to approved ones, but they can never be consulted for either satisfaction or staleness

**File:** `src/api/routers/operations.py:488-509`; `src/intelligence/remediation/approval_gate.py:116-129`

**Issue:** `record_remediation_decision` computes and stores `approver_roles` unconditionally for every `decision` value (`approved`/`rejected`/`expired`), but `requirement_satisfaction()` filters to `decision.get("decision") == "approved"` before ever consulting `approver_roles` (`approval_gate.py:116`). This is not incorrect, but it is dead data on two of three decision kinds and a minor footgun for a future reader who assumes a rejected decision's `approver_roles` is meaningful for anything (e.g. an audit report cross-referencing "who was authorized to reject this").

**Fix:** Either document explicitly that `approver_roles` is only ever meaningful on `approved` records, or omit it for non-approved decisions to avoid a false impression of significance.
