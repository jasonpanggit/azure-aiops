# Phase 03.5 Plan 06: Decision/workflow routes require approve and project the shared satisfaction/staleness functions Summary

`POST /remediation-plans/{plan_id}/decisions` now requires the `approve` RBAC action (not `operate`) and durably records server-derived `approver_roles`/`approval_policy_version`; `GET .../workflow` and `GET .../approvals` now project the exact same `requirement_satisfaction()`/`latest_decision_status()` functions the execution gate uses, plus RBAC-derived `can_approve`/`can_operate` fields — closing the loop so what the gate enforces and what the operator is shown can never diverge.

## What Was Built

- **`record_remediation_decision`** (`operations.py`): parameter switched from `OperatePrincipal` to `ApprovePrincipal`; the internal `operate_scope` variable renamed to `approve_scope` throughout the function body (no behavioral change to scope narrowing itself); `decisions.append(...)` extended with server-derived `approver_roles` (from the principal's `approver`/`admin`-satisfying grants only) and `approval_policy_version` (read from `planner.generator.approvals.policy_version` when reachable, `""` otherwise — a documented interim simplification for planners exposing no single reachable engine, e.g. `LiveRemediationPlanner`'s two per-family engines).
- **`plan_approvals`** (`remediation.py`): `approval_requirements` in the response is now `approval_gate.requirement_satisfaction(...)` output (each row now carries `satisfied`/`unmet_reason` in addition to its existing `policy_id`/`role`/`stage`/`status`/`approval_evidence_required`/`approval_recorded` keys) instead of the raw stored list.
- **`plan_workflow`** (`remediation.py`): gained a `principal: CurrentPrincipal` parameter (additive — the route remains read-gated overall; this is informational only). The inline `approval_current` boolean (previously comparing only `snapshot_hash`, never `action_version`, a real pre-existing staleness-detection bug) is replaced by `approval_gate.latest_decision_status(...)`; the response's `"approval"` dict gains `"status"`/`"stale_reasons"` (from that call) and `"can_approve"`/`"approve_ineligible_reason"`; the response's `"action"` dict gains `"can_operate"`/`"operate_ineligible_reason"`. Both eligibility pairs are computed via `try: context.authorizer.require(principal, "approve"|"operate") except ApiError` — never raising out of the route, never overriding the route's own RBAC gate.
- A new `_policy_version_for(planner)` helper (shared by both routes) reads `getattr(planner, "generator", None).approvals.policy_version` when reachable.
