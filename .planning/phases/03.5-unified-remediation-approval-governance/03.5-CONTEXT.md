# Phase 03.5: Unified Remediation Approval Governance - Context

**Gathered:** 2026-09-04
**Status:** Ready for planning
**Mode:** Autonomous decisions derived from Phase 03 deep review

<domain>
## Phase Boundary

Enforce one evidence-sensitive approval policy across patch and Defender action
families, make requirements machine-checkable, preserve an explicit audited
demo self-approval exception, and separate approve authorization from operate
authorization. This phase includes the minimal UI needed to show requirement
satisfaction accurately; broader blocker/degradation UX remains Phase 03.6.

</domain>

<decisions>
## Implementation Decisions

### Approval Policy
- Evaluate every plan's `approval_requirements` against durable decisions inside one execution-service gate shared by all action families.
- Requirements carry stable policy/role identifiers, not presentation text alone.
- A decision is current only when it satisfies the current action version, preview snapshot, expiry, policy version, and required approver roles.
- Refusals identify each unmet requirement using a closed machine-readable reason.

### Separation of Duties
- Move requester-versus-approver enforcement into the shared approval gate so patch and Defender configuration behave identically.
- `allow_self_approval` is the only exception, defaults off, and is recorded on the durable decision/audit projection.
- Demo mode may enable self-approval explicitly; production policy remains fail-closed.

### Authorization
- Add a distinct `approve` RBAC action and dependency.
- Approve-only principals can record decisions but cannot execute; operate-only principals can execute currently approved work but cannot create approval decisions.
- Scope enforcement remains identical for approve and operate actions.

### Evidence Versioning
- Create one shared `action_version_for(...)` helper used by live and Fabric planners.
- Include stable action identity, target, selected/eligible scope, and a deterministic evidence digest based on evidence content timestamps/identifiers.
- Never include query/current wall-clock time.
- Evidence mutations deliberately stale prior approvals once and visibly.

### UI Contract
- Show each approval requirement with satisfied/unmet state and responsible role/policy.
- Explain self-approval as an explicit demo-policy exception when enabled.
- Disable approval submission when the caller lacks `approve`; disable run when the caller lacks `operate`, using server authority rather than client guesses.
- Preserve the existing five-step layout and current Fluent UI/design tokens.

### the agent's Discretion
- Exact policy-version string format and principal role-claim mapping may follow existing RBAC and decision-store conventions.

</decisions>

<specifics>
## Specific Ideas

Tests must prove two-role requirements cannot be satisfied by one wrong-role
decision, Defender actions enforce the same SoD rule as patching, approve and
operate permissions are mutually enforceable, demo self-approval is explicit
in audit data, and changing an evidence content timestamp stales approvals from
both live and Fabric planners.
