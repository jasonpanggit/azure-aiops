## WR-06 fix (2026-09-04T17:35:52+08:00)

**Status: fixed.** `03.5-REVIEW.md`'s WR-06 finding is closed; summarized here for the verification record:

- **Explicit, validated maximum lengths, with clear `ValueError` messages, replace silent truncation at every point identity is derived or a row's uniqueness key is computed:** `ApprovalEngine.__init__` now rejects any `policy_id` over `MAX_POLICY_ID_LENGTH` (200) immediately at construction, before it is ever used to derive a `role_id`; `_validate_policy` now rejects any `roles` entry over `MAX_ROLE_LENGTH` (200) and any explicit `role_ids` value over `MAX_ROLE_ID_LENGTH` (256, the stored schema limit); `requirements()` now rejects any `action.deployment_stages` entry over `MAX_STAGE_LENGTH` (128) at call time (the only point a stage name is known). Each rejection names the specific offending field and its bound. This closes WR-06 manifestation 1 outright: a `role`/`stage`/`policy_id` long enough to reach the old truncation boundary can no longer exist by the time `_row()` runs, so two distinct catalog-declared values can never again collapse onto the same stored value with no error.
- **`_normalized_role_identity` now caps only its own human-readable slug prefix, never the collision-resistant digest suffix:** the previously separate, downstream `_row()`-level `[:256]` slice on the *composed* `"<prefix>:<digest>"` string (which could truncate the digest itself away) is removed; the identity function itself now computes the digest first and truncates only the prefix as needed to fit `MAX_ROLE_ID_LENGTH`, guaranteeing the digest — the part CR-06 actually relies on for collision resistance — always survives intact. This closes WR-06 manifestation 2: an implicitly-derived `role_id` can no longer lose its distinguishing suffix to truncation, so `requirements()`'s own call-time uniqueness check (CR-06) can no longer be spuriously tripped by truncation-induced collisions between genuinely distinct rows.
- **`_row()`'s remaining slices are now defensive, no longer load-bearing for correctness:** `role`/`stage` are sliced to their respective validated maxima purely as a display-text safety net (unreachable in practice, since upstream validation already guarantees these bounds); a resolved `role_id` that still somehow exceeded `MAX_ROLE_ID_LENGTH` now raises a `ValueError` naming it an internal derivation defect, rather than being silently truncated — the exact "unsafe blind slicing" pattern WR-06 called out is gone from every identity-bearing field.
- **Plan generation now fails deterministically and diagnostically, not with uncaught downstream ambiguity:** for `policy_id`/`role`/explicit `role_id`, the invalid-length rejection now happens at `ApprovalEngine`/`RemediationPlanner` construction time — before any specific resource's plan generation is ever attempted — with a message naming the exact field and bound, closing the reviewer's own manifestation-2 repro (previously an opaque "colliding role_id" `ValueError` raised only for the specific resource that happened to reach it, with no production caller catching it).
