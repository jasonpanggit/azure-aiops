### CR-01: `approver_roles` derived exclusively from RBAC capacity names could never satisfy any deployed `ApprovalEngine`'s organizational role names

**Files modified:** `src/intelligence/remediation/approval_engine.py`, `src/intelligence/remediation/approval_gate.py`, `src/api/routers/operations.py`, `tests/test_api_remediation_execution.py`, `tests/test_remediation_execution_supersede.py`, `tests/test_remediation_identity_and_audit_continuity.py`, `web/src/lib/services.ts`
**Commit:** none (working-tree only, per explicit instruction)
**Applied fix:** Introduced a coherent, machine-checkable mapping between policy role identity and principal/RBAC claims, honoring the CONTEXT.md decision ("Requirements carry stable policy/role identifiers, not presentation text alone") that the original implementation had not honored:
- Every `approval_requirements` row (`ApprovalEngine._row()`) now carries a stable `role_id` field, separate from its organizational-display `role` text. Each policy may optionally declare a `role_ids: {display_role: stable_id}` mapping; any role left unmapped defaults to `ApprovalEngine.DEFAULT_ROLE_ID` (= `api.rbac.ROLE_APPROVER`, `"approver"`) — this is the migration/default behavior: every shipped policy (live-planner defaults *and* the Fabric/catalog organizational-role catalog) is satisfiable out of the box without first requiring a directory-backed role-claim integration, while remaining extensible for deployments that want finer per-role RBAC granularity later.
- `record_remediation_decision` now records `approver_roles` as the RBAC `approve`-action capacity itself (`ROLE_APPROVER`) plus every literal qualifying grant role the principal holds (e.g. `admin`) — not just the raw literal grant roles as before — so an admin-recorded decision (`["admin"]` before the fix) now also carries `"approver"`, matching the new default `role_id`.
- `approval_gate.requirement_satisfaction()` now matches each row's `role_id` (falling back to `role` only for a legacy/durable requirement row generated before this fix, preserving evaluability of previously-generated plans — the explicit migration path).
- Added a new end-to-end HTTP regression test (`test_admin_decision_via_real_http_route_satisfies_shipped_fabric_planner_defaults`) that reproduces the reviewer's own proof-of-concept against the unmodified production-representative fixture (`tests/fixtures/sample_remediation_planning.json`, 11 real requirement rows) — decision recorded via the real route → all rows satisfied → execute succeeds (202/`running`). This specific test shape did not exist anywhere in the suite before this fix, per the review's own call-out.
- Web `RemediationApprovalRequirement` type gained optional `role_id`/`approver`/`decision_id` fields (additive; no UI logic change required since `role` display text is unchanged).

### CR-02: Self-approval separation-of-duties only inspected the plan's single overall-latest decision, never the decision that actually satisfied each required row

**Files modified:** `src/intelligence/remediation/approval_gate.py`, `src/intelligence/remediation/execution_service.py`
**Commit:** none
**Applied fix:** `requirement_satisfaction()` now attaches `approver`/`decision_id` to every **satisfied** row, identifying exactly which decision satisfied it. `_check_approval_gate` builds a deduplicated (by `decision_id`) candidate list of **every** decision that matters — the plan's overall-latest decision (the pre-existing baseline, still the only candidate for a plan with zero distinct requirement rows) **plus** every required row's own satisfying decision — and checks requester-vs-approver identity against each one. A requester who self-approved even one required row can no longer execute regardless of who legitimately signed the others. (An initial per-row-only implementation regressed self-approval enforcement to a no-op for zero-requirement-row plans; fixed by also always checking the overall-latest decision, verified by re-running `test_self_approval_refused_for_both_families_when_disallowed`.)

### WR-03: `self_approved`/`self_approval_policy_id` were durably recorded before execution was confirmed to actually proceed

**Files modified:** `src/intelligence/remediation/execution_service.py`
**Commit:** none
**Applied fix:** `_check_approval_gate` no longer calls `record_self_approval` itself; it returns the set of decision ids found to be a self-approval of a satisfied row (`self_approved_decision_ids`) alongside the resolved `decision`. A new `_finalize_self_approvals()` method performs the actual durable write, and is invoked from `execute()`/`retry()`/`supersede()` only after their own store claim (`create_or_get`'s `claimed` check, `claim_retry`+`transition`, `create_superseding`+`transition` respectively) has durably succeeded — never before. `plan_eligibility()` discards the returned set entirely (its `requested_by=""` guarantees it is always empty; it is a pure, non-mutating read). ### CR-06: `_normalized_role_identity`'s lossy, human-readable slugification is not collision-resistant

**Files modified:** `src/intelligence/remediation/approval_engine.py`, `tests/test_remediation_approval_gate.py`
**Commit:** none (working-tree only, per this session's explicit no-commit/no-branch/no-stash instruction)
**Applied fix:**
- `_normalized_role_identity` now appends a 16-hex-char SHA-256 digest,
  computed over the exact raw (non-normalized), JSON-encoded `parts`
  tuple, to the existing lossy slug prefix (kept only for human
  debuggability). Two distinct raw inputs can now never produce the same
  `role_id` except by cryptographic coincidence, regardless of how
  similarly they slugify (closes the `P-1`/`P_1` and stage-name
  punctuation/case-variant collisions reproduced in the review).
- Because every implicitly-derived id now always carries a `:<digest>`
  suffix, it can never coincidentally equal a bare reserved RBAC sentinel
  (`"approver"`/`"admin"`/`"operator"`/`"reader"`) — closing the
  `"Approver"`/`"- - -"` reserved-sentinel-collapse repro. A reserved
  sentinel can now only ever be reached through an explicit, policy-
  authored `role_ids` opt-in.
- `ApprovalEngine.__init__` now validates, at construction (catalog-load)
  time, that no two distinct policy-declared roles (explicit or implicit)
  resolve to the same non-reserved `role_id`, raising `ValueError`
  immediately rather than silently allowing one decision to satisfy two
  requirement rows discovered only later. Two distinct roles explicitly,
  deliberately opting into the same reserved sentinel remain permitted
  (the intended CR-05 RBAC-compatibility behavior).
- `ApprovalEngine.requirements()` performs the same uniqueness check over
  the final generated row set (stage-gate rows included), since stage
  names are only known at call time, not construction time.
- 10 new regression tests added to `tests/test_remediation_approval_gate.py`
  covering: `P-1`/`P_1` distinct-policy_id collision (reviewer's own
  repro, cross-satisfaction proven false); role-text case/punctuation
  variants; deployment-stage case/punctuation variants; the reviewer's
  own reserved-sentinel-collapse repro (now refused authorization);
  construction-time rejection of colliding explicit non-reserved
  `role_ids` (across policies and within one policy); construction-time
  acceptance of explicit, deliberate reserved-sentinel sharing;
  deterministic/stable identity across repeated calls; and unchanged live
  single-role compatibility (the two shipped patch/Defender-configuration
  policies, unaffected since they never invoke the derivation function).

### WR-06: `_row()`'s pre-existing `[:256]`/`[:128]` storage truncation could strip the CR-06 digest suffix (or the row's own distinguishing content) for sufficiently long `policy_id`/`role`/`stage` text

**Files modified:** `src/intelligence/remediation/approval_engine.py`, `tests/test_remediation_approval_gate.py`
**Commit:** none (working-tree only, per this session's explicit no-commit/no-staging/no-branch/no-reset/no-stash/no-push/no-deploy instruction)
**Applied fix:**
- Added four explicit, validated maximum lengths as module-level
  constants — `MAX_POLICY_ID_LENGTH` (200), `MAX_ROLE_LENGTH` (200),
  `MAX_STAGE_LENGTH` (128), and `MAX_ROLE_ID_LENGTH` (256, unchanged from
  the pre-existing `_row()` storage bound). Each identity-bearing field
  is now rejected with a clear, field-specific `ValueError` the moment it
  is known to exceed its bound, instead of silently truncated later
  inside `_row()`:
  - `policy_id` — validated in `ApprovalEngine.__init__`, immediately
    after the existing empty/duplicate check and before it is ever used
    to derive a `role_id`.
  - `role` text and explicit `role_ids` mapping values — validated in
    `_validate_policy`, at construction time.
  - `stage` — validated in `requirements()`, at call time, since
    deployment stage text is only known once `action.deployment_stages`
    is supplied (never at policy construction time).
- `_normalized_role_identity` no longer depends on a downstream slice of
  its *composed* `"<prefix>:<digest>"` string to stay within the stored
  schema limit. It now computes the 16-hex-char SHA-256 digest first,
  then caps only the human-readable slug prefix as needed so the total
  returned length never exceeds `MAX_ROLE_ID_LENGTH` — the digest suffix,
  which is what actually carries CR-06's collision resistance, can now
  never be truncated away by this function or by any downstream slice.
- `_row()`'s `role`/`stage` slices are retained, but only as a
  defensive, display-only safety net — unreachable in practice once the
  above validation guarantees these bounds upstream. Its former `role_id`
  slice is replaced with a `ValueError` raised if a resolved id somehow
  still exceeds `MAX_ROLE_ID_LENGTH`, naming it an internal
  identity-derivation defect rather than silently truncating it away
  (the exact "unsafe blind slicing" pattern WR-06 called out).
- Both of WR-06's own reproduced manifestations are closed: manifestation
  1 (two role strings identical for their first 256 characters silently
  merging into one required-approval row with no error) now raises a
  clear `ValueError` at construction instead of silently merging;
  manifestation 2 (an overlong `policy_id` surfacing only later, for
  whichever resource's plan generation happened to reach it, as a
  comparatively opaque "colliding role_id" `ValueError`) now raises the
  same clear, field-specific `ValueError` immediately at
  `ApprovalEngine`/`RemediationPlanner` construction time, before any
  resource's plan generation is ever attempted — deterministic and
  diagnostic, not uncaught downstream ambiguity.
- No production call site (`remediation_generator.py:69`,
  `live_operations.py:550`, `live_operations.py:715`) was modified to
  catch the now-clearer `ValueError`s: an invalid, overlength
  catalog-authored value is a genuine data-authoring defect meant to fail
  loud at the source, exactly like this same engine's own pre-existing
  `conditions`/`roles` validation already does — not a case for a
  production code path to silently absorb. `src/fabric/sync_service.py`'s
  ingestion path was likewise not modified: the same Fabric-sourced
  `approval_policies` dataset already flows through the single choke
  point this fix's construction-time validation now covers
  (`RemediationPlanner.__init__`'s `ApprovalEngine(approval_policies)`
  call, `remediation_planner.py:110`) — an overlong value originating
  from the Fabric lakehouse table is caught there deterministically, with
  no separate ingestion-boundary bound needed. Both choices keep this fix
  narrowly scoped to WR-06 itself, per this session's explicit
  no-unrelated-edits instruction.
- 12 new regression tests added to `tests/test_remediation_approval_gate.py`
  covering: boundary tests at max/max+1 for `policy_id`, `role`, `stage`,
  and explicit `role_id` respectively (8 tests, each pairing an at-max
  accept with an over-max clear-message reject); two long `policy_id`

  proof mirroring the existing P-1/P_1 CR-06 test); `_normalized_role_identity`'s
