# Phase 03.5 Plan 05: Execution-service gate enforces per-role satisfaction and cross-family separation of duties Summary

`RemediationExecutionService._check_approval_gate` is now the single, real enforcement point for per-role `approval_requirements` satisfaction and requester-vs-approver separation of duties, for **both** the patch and Defender-configuration action families — closing the CR-04/CR-05 gap where Defender configuration had zero self-approval protection at all, and where a multi-role plan could execute on one wrong-role decision.

## What Was Built

- **`is_self_approval(requested_by, approved_by)`** already existed in `approval_gate.py` (landed ahead-of-schedule in Plan 03.5-03 for the identical import-cycle reason this plan's Task 1 independently identifies). `PatchingService._authorize_approval` now calls it in place of its own inline `.casefold()` comparison — zero behavior change, verified by all 12 pre-existing `test_patch_approval_gate.py` tests passing unmodified.
- **`_check_approval_gate(plan, *, requested_by="")`** gained a `requested_by` keyword parameter (all four call sites — `execute`, `retry`, `supersede`, `plan_eligibility` — updated; `plan_eligibility` passes `""`, which `is_self_approval` treats as never-equal, keeping that pure-RBAC eligibility projection identity-blind by design) and, after the pre-existing action_version/expiry/business-eligibility/snapshot checks:
  1. Evaluates `approval_gate.requirement_satisfaction(...)` against `plan["approval_requirements"]` and every decision on file for the plan (`self._plans.decisions.list(plan_id)`); any unsatisfied row raises `RemediationExecutionError(reason="approval_requirements_unmet", details={"unmet": [...]})` naming each unmet row's `policy_id`/`role`/`stage`/`unmet_reason`.
  2. When `requested_by` is non-empty and matches the decision's approver (`is_self_approval`): raises `RemediationExecutionError(reason="self_approval_not_permitted")` before either adapter is ever reached, unless `self._allow_self_approval()` is true — this is the actual CR-04/CR-05 fix, since previously only the patch path (via `PatchingService.trigger`) had any check at all. When allowed, durably records the fact via `record_self_approval(decision_id, policy_id="demo-self-approval")` before returning.
- **`RemediationExecutionService.__init__`** gained `allow_self_approval: Callable[[], bool] | bool = False`, normalized identically to `PatchingService`'s own pattern, defaulting fully closed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Role-vocabulary mismatch broke every pre-existing integration test carrying real, multi-role `approval_requirements`**
- **Found during:** Full-suite regression run after Task 2 landed.
- **Issue:** Once `_check_approval_gate` started actually consulting `approval_requirements`, every pre-existing test that recorded a decision *without* `approver_roles` (bypassing the API route via `planner.repository.decisions.append()` directly, or going through the real API route against a rich Fabric-catalog scenario plan carrying organizational-role requirement rows like "Change Advisory Board"/"Stage Gate Approver") failed with `approval_requirements_unmet`, since an empty/RBAC-shaped `approver_roles` list can never satisfy an organizational-role requirement row.
- **Fix:** For direct-append test helpers (`_approve()` in `tests/test_api_remediation_execution.py`, `tests/test_remediation_execution_supersede.py`, `tests/test_remediation_identity_and_audit_continuity.py`), pass `approver_roles=[row["role"] for row in plan["approval_requirements"]]` so the test approves under every role the specific plan actually requires -- these tests exercise execution mechanics, not per-role SoD (which Plan 03.5-05's own new tests cover narrowly). For two tests exercising the real API route end-to-end against the rich multi-role Fabric scenario planner (`test_defender_configuration_preview_approval_and_execute_are_snapshot_bound`, `test_scoped_execute_uses_the_same_hybrid_providers_as_preview_and_approval`), overrode the locally-constructed plan's `approval_requirements` to `[]` since their actual purpose (snapshot binding, hybrid-provider scope routing) is orthogonal to approval governance.
- **Files modified:** `tests/test_api_remediation_execution.py`, `tests/test_remediation_execution_supersede.py`, `tests/test_remediation_identity_and_audit_continuity.py`
- **Follow-up (documented limitation, not fixed in this plan):** `record_remediation_decision` (Plan 03.5-06) derives `approver_roles` from RBAC capacity (`approver`/`admin`), which can never literally match an organizational-policy role string like "Change Manager". Today this means a plan whose `ApprovalEngine` policies use organizational role names can only be satisfied by a decision explicitly recorded with matching role strings (which the live-planner's own default single-policy engines do, by construction). Bridging this for richer organizational-role catalogs recorded via the real API route is a real gap for a future phase (a directory-backed role-claim model, or extending RBAC `Grant` to carry named organizational roles) — documented in `STATE.md`.

**2. [Rule 1 - Bug] Gate-level self-approval enforcement preempted a pre-existing test's PatchingService-toggle scenario**
- **Found during:** Full-suite regression run after Task 2 landed (`test_remediation_submission_accounting.py::test_only_the_genuine_submission_counts_after_self_approval_refusals`).
- **Issue:** This pre-existing test used a stateful toggle (`_AllowAfter(2)`) passed only to `PatchingService`, expecting the first two `execute()`/`retry()` calls to be refused *non-raising* (recorded as a `failed` execution, budget-neutral) deep inside `PatchingService.trigger`, and the third to reach a genuine provider rejection. Once the shared gate started enforcing self-approval *before* an execution record even exists, the first refusal now raises synchronously with no execution record created at all, so `retry()` (which needs an existing record) had nothing to retry against.
- **Fix:** Threaded the same `allow_self_approval` toggle into `RemediationExecutionService`'s constructor too (the two enforcement points now share one policy source in this specific test, matching "share semantics" per this plan's own instruction) and rewrote the test to call `execute()` three times in sequence (first two via `pytest.raises`, proving zero budget consumed since no record exists at all; the third reaching the genuine provider rejection) instead of `execute()` once + `retry()` twice. The underlying security property this test proves — self-approval refusals never consume submission budget — is unchanged; only the code path producing that refusal moved earlier (a deliberate consequence of D-02: self-approval is now caught before any adapter is ever reached, for both families identically).
- **Files modified:** `tests/test_remediation_submission_accounting.py`
- **Design confirmation:** `RemediationExecutionService.allow_self_approval` does **not** automatically fall back to `PatchingService`'s own policy when omitted (an earlier attempt at this fallback was reverted) — the two are independent by default, matching this plan's literal spec ("mirror that exact `callable(...)`-check pattern... for consistency", "defaulting closed exactly like `MAX_EXECUTION_ATTEMPTS`'s sibling constants"). Callers that need the two synchronized (as this fixed test now does) pass the same callable to both constructors explicitly.
