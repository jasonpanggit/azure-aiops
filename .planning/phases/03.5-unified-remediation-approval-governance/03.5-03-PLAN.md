<objective>
Build the one shared, pure (no I/O, no clock reads) evaluation engine that
answers "is this approval_requirements row satisfied against these
decisions right now" and "what is the plan's overall latest-decision
status" (D-01). This is the machine-checkable core the phase goal names
directly: "requirements carry stable policy/role identifiers... A decision
is current only when it satisfies the current action version, preview
snapshot, expiry, policy version, and required approver roles. Refusals
identify each unmet requirement using a closed machine-readable reason."

Purpose: today `_check_approval_gate` only checks that *some* decision
exists, is approved, matches action_version, and isn't expired — it never
looks at `approval_requirements` at all (CR-04: "one decision suffices"),
and the read-side `plan_workflow` route computes a *different*,
snapshot-hash-only definition of `approval_current` (missing action_version
and policy_version checks entirely). This plan gives both call sites one
function to share so they cannot diverge.
Output: `src/intelligence/remediation/approval_gate.py` with
`requirement_satisfaction()` and `latest_decision_status()`.
</objective>

  <name>Task 1: requirement_satisfaction() — the two-role SoD-shaped satisfaction check</name>
  <files>src/intelligence/remediation/approval_gate.py, tests/test_remediation_approval_gate.py</files>
  <behavior>
    - `requirement_satisfaction(requirements: list[dict], decisions: list[dict], *, current_action_version: str, current_snapshot_hash: str, policy_version: str, now: datetime) -> list[dict]`
      returns one output row per input requirement row, each input row's
      `policy_id`/`role`/`stage`/`approval_evidence_required` copied through
      unchanged, plus two new keys: `satisfied: bool` and
      `unmet_reason: str` (only present/non-empty when `satisfied is False`),
      using exactly this closed vocabulary and precedence (first match
      wins, checked in this order per candidate decision): no `approved`
      decision from a matching role at all → `pending`; a decision exists
      but every one of them came from a role other than this row's `role`
      → `wrong_role_decision`; the best-matching-role decision's
      `action_version != current_action_version` → `stale_action_version`;
      its `execution_snapshot.snapshot_hash != current_snapshot_hash` (only
      compared when both sides are present) → `stale_evidence_snapshot`;
      its `approval_policy_version != policy_version` → `stale_policy_version`;
      its `expires_at` is in the past relative to `now` → `expired`.
      A row is `satisfied: true` only when a matching-role decision passes
      every one of those checks.
    - Two required rows with roles "Change Manager" and "Security Response
      Owner", one `approved` decision on file with `approver_roles:
      ["security response owner"]` (casefolded) matching only the second
      role → exactly the second row `satisfied: true`, the first row
      `satisfied: false, unmet_reason: "pending"`.
    - Role matching is casefolded (`decision["approver_roles"]` entries are
      already stored casefolded per Plan 03.5-01; this function casefolds
      `row["role"]` before comparing so a mismatch cannot occur from
      casing alone).
    - An empty `requirements` list returns `[]` (no requirements means
      nothing to evaluate — matches every existing execution_service
      fixture test that passes `"approval_requirements": []`).
  </behavior>
  <action>
    Create `src/intelligence/remediation/approval_gate.py`. Implement
    `requirement_satisfaction` per the behavior spec above. For each
    requirement row, filter `decisions` to `decision == "approved"` entries
    whose `approver_roles` (list, casefolded, from Plan 03.5-01) contains
    `row["role"].strip().casefold()`; if none, `unmet_reason = "pending"`
    unless at least one *other-role* approved decision exists on the plan
    at all, in which case still `"pending"` is correct per the vocabulary
    table (03.5-UI-SPEC.md's `pending` copy is "No decision recorded yet
    for this role" — this is per-row, not plan-wide, so `wrong_role_decision`
    is reserved for the case where a matching-role decision search finds
    zero matches for genuinely no reason to prefer over `pending`; use
    `wrong_role_decision` specifically when the row's `role` was never
    satisfied but at least one decision exists for a *different* role on
    this same `stage`, matching the UI-SPEC copy "A decision exists, but
    not from the required {role}"). Among matching-role candidates, select
    the most recent (`max` by `decided_at`) as the row's determining
    decision, then run the ordered staleness checks. Do not mutate the
    input `requirements`/`decisions` lists or their dict elements — build
    and return new dicts (`{**row, "satisfied": ..., "unmet_reason": ...}`
    with the key omitted/empty when satisfied).
  </action>

  <name>Task 2: latest_decision_status() sharing the same staleness logic</name>
  <files>src/intelligence/remediation/approval_gate.py</files>
  <behavior>
    - `latest_decision_status(decisions: list[dict], *, current_action_version: str, current_snapshot_hash: str, policy_version: str, now: datetime) -> dict`
      returns `{"status": "none"|"current"|"stale"|"rejected"|"expired",
      "stale_reasons": list[str], "latest": dict | None}` exactly per
      03.5-UI-SPEC.md's "Stale Approval State Contract" table.
    - No decisions at all → `{"status": "none", "stale_reasons": [], "latest": None}`.
    - The most-recently-`decided_at` decision is `"rejected"` →
      `{"status": "rejected", ...}` regardless of any earlier approved
      decision (a later rejection is authoritative).
    - The most recent decision is `"approved"` and is expired → `"expired"`.
    - The most recent decision is `"approved"`, unexpired, but fails one or
      more of action_version/snapshot_hash/policy_version →
      `"stale"` with `stale_reasons` containing every one of
      `stale_action_version`/`stale_evidence_snapshot`/`stale_policy_version`
      that applies (can be more than one simultaneously — order:
      action_version, then evidence_snapshot, then policy_version, matching
      the Requirement Contract's ordering so `{joined reasons}` copy
      composes predictably).
    - The most recent decision is `"approved"`, unexpired, and passes every
      check → `"current"`.
  </behavior>
  <action>
    Implement `latest_decision_status` reusing the same per-decision
    staleness predicates as `requirement_satisfaction` (extract a small
    private `_staleness_reasons(decision, *, current_action_version,
    current_snapshot_hash, policy_version) -> list[str]` helper that both
    public functions call, so the two functions can never disagree about
    what "stale" means for the same decision). Select the latest decision
    by `max(decisions, key=lambda d: d["decided_at"])`. Branch on
    `decision["decision"]` first (`rejected` → status `rejected`
    unconditionally), then expiry (`expired`), then staleness-reasons
    (empty list → `current`, non-empty → `stale`).
  </action>
