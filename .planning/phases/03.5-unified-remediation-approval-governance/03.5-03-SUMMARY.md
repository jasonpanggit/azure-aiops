# Phase 03.5 Plan 03: Shared approval-requirement satisfaction and staleness evaluation engine Summary

Built `src/intelligence/remediation/approval_gate.py`, the one shared, pure (no I/O, no clock reads) evaluation engine answering "is this approval_requirements row satisfied against these decisions right now" (`requirement_satisfaction()`) and "what is the plan's overall latest-decision status" (`latest_decision_status()`) — closing the CR-04 "one decision suffices" gap by construction, since Plan 03.5-05's execution gate and Plan 03.5-06's read routes both consume these same two functions.

## What Was Built

- **`requirement_satisfaction(requirements, decisions, *, current_action_version, current_snapshot_hash, policy_version, now) -> list[dict]`**: decorates each input requirement row with `satisfied: bool` and (when unsatisfied) `unmet_reason` from the closed vocabulary `pending | wrong_role_decision | stale_action_version | stale_evidence_snapshot | stale_policy_version | expired`. Role matching is casefolded on both sides. A two-role requirement set with one matching-role decision produces exactly one satisfied row and one unmet row — never both satisfied from a single decision. Does not mutate inputs.
- **`latest_decision_status(decisions, *, current_action_version, current_snapshot_hash, policy_version, now) -> dict`**: returns `{"status": "none"|"current"|"stale"|"rejected"|"expired", "stale_reasons": [...], "latest": dict|None}`. A later rejection always wins over an earlier approval. A decision stale in two dimensions reports both reasons, in the documented order (action_version, then evidence_snapshot, then policy_version).
- **`_staleness_reasons()`** (private): the single predicate both public functions call — proven single-sourced by a Task 3 test that imports and calls it directly, not merely comparing the two public functions' outputs on a shared fixture.
- **`is_self_approval(requested_by, approved_by) -> bool`**: added ahead of Plan 03.5-05's own Task 1 (which independently arrived at the same conclusion — see 03.5-05's summary) since this module has no dependency on `operations.patching`, avoiding inverting the existing `execution_service.py -> patching/service.py` dependency direction. Casefolded/stripped equality; empty strings never match.
