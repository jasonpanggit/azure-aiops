## User Constraints (from CONTEXT.md)

### Locked Decisions

### Unified exposure truth

- Exposure will move to one scope-aware read model consumed by all Exposure surfaces: overview, patch priorities, Defender posture, container-image exposure, CVE and KB detail, SLA, Copilot, and remediation correlation.
- Live Azure Update Manager evidence must overlay the persisted Defender/image evidence. It must not replace Defender findings simply because a request is scoped.
- Source families remain separately attributable. The UI and API must expose enough provenance to tell Azure Update Manager, Defender recommendation/subassessment, Defender posture, container-image, and external-enrichment evidence apart.
- CVE and KB collection/detail membership is derived only from findings visible in the caller's authorized scope. A public catalog lookup may enrich an already-authorized identifier, but catalog search is a distinct endpoint and visibly labeled external catalog data.

### Source freshness and failure behavior

- Checkpoints and last-known-good state are tracked per connection and per source family. One failing connection or family must not invalidate healthy sources.
- A failed refresh may retain that source's last successful data with an explicit stale/degraded state. The system must not silently substitute an older full-scope snapshot for a scoped failure.
- Provider failures, timeouts, malformed responses, and authorization failures are metadata/control-plane outcomes. They must never be normalized into domain entities.
- A failed source refresh must never publish a successful empty partition and must never false-clear earlier data.
- Evidence metadata must distinguish complete, partial, stale, unavailable, and healthy-empty states, with source-family counts and timestamps.
- Operators need actionable source state without leaking sensitive provider payloads: source/connection identity safe for display, last attempt, last success, age, status, and a stable error code plus sanitized summary.
- A single failing Azure connection must not abort otherwise healthy live results.

### Temporal vulnerability state

- Vulnerability and patch evidence becomes immutable observation/event data plus a separately projected current-state table.
- At minimum, temporal history must represent missing, installed, resolved, and reintroduced events without deleting prior evidence.
- An installation closes an earlier missing state only when it is a successful operation for the same normalized machine-and-KB/CVE target and its event time is later.
- Later missing evidence reopens the exposure and increments reintroduction history rather than being suppressed by an old install record.
- Store provider event time, first detected time, last observed time, ingestion time, run time, publication time, enrichment time, and the supporting source/operation identifiers as distinct fields where applicable.
- Patch SLA aging uses tenant-scoped `first_detected_at`; publication time must never be used as a substitute. Unknown first detection stays unknown and produces an unavailable/indeterminate SLA result.
- Preserve the first-ever tenant-scoped detection across reintroduction episodes. Reintroduction may carry a separate episode timestamp, but the SLA clock remains bound to the original tenant observation.
- Out-of-order data is resolved deterministically: provider operation status first, then source sequence/generation, ingestion time, and stable identity as tie-breakers.

### Container-image ontology

- Container registry, logical image/repository, immutable digest, running workload, application, and business service are separate concepts.
- A digest may have multiple tags; a tag may move to a newer digest. Workload-to-image links use immutable digest identity when available.
- Container vulnerability evidence belongs to the image digest. Runtime/business impact is derived by traversing workload -> application -> business service relationships.
- Registry-as-server inference is forbidden. Missing workload evidence stays missing/unknown rather than being synthesized from registry metadata.
- Ontology rebuilds and Fabric round-trips must preserve image and workload relationships, not just aggregate image rows.

### Scale and interaction contract

- Large Exposure collections use server-side filtering and sorting plus opaque cursor pagination. Client-side slicing and unbounded arrays are not acceptable collection contracts.
- Default table page size is 50 rows; users may choose 25, 50, or 100.
- Collection responses expose exact total counts, loaded range, active sort/filter state, continuation, read-model generation/snapshot ID, and conservative aggregate completeness.
- Default sorting remains deterministic and operational: highest priority/risk first with a stable identity tie-breaker. User sort choices persist in URL state.
- Search/filter inputs debounce at approximately 300 ms. Changing scope, search, filters, sort, or page size resets the cursor and returns to the first page.
- The first filtered page must meet a p95 server response target of <= 2 seconds at 100,000 findings under representative test conditions.

### Exposure page behavior

- Overview remains lean. Full patch and Defender/container tables stay on their dedicated pages.
- Page sections load and fail independently. A failed source shows an inline retry/fallback state while healthy source sections remain usable.
- On source failure, retain and clearly label last-known-good content when available. If none exists, render unavailable/unknown rather than zero or healthy.
- The freshness/evidence area shows per-source state and timestamp plus one conservative aggregate label. Collapsed detail is fine only if stale/partial/unavailable state remains visible.
- A successful zero-row result is treated as healthy empty; failed or missing data is never rendered as zero exposure.

### UI, accessibility, and responsive behavior

- Phase 03.1 is a surgical reliability/scale pass, not a redesign. Preserve the existing operations-workbench visual language and route split.
- Dense tables must support desktop, tablet, and mobile without data loss: controlled horizontal scroll or responsive priority-column/card behavior is acceptable; clipping and viewport overflow are not.
- Long identifiers, digests, CVSS vectors, errors, and remediation text must wrap or expose accessible full content.
- Loading, empty, stale, partial, and unavailable states are visually distinct, keyboard accessible, and announced appropriately. Color is never the only status indicator.
- Respect `prefers-reduced-motion` across Exposure, including card hover, skeletons, chart transitions, critical metric animations, and header effects.
- Use existing shared components and tokenized styles. Replace undefined CSS variables and do not add one-off inline styling for standard buttons, tables, or dialog behavior.

### Risk-exception mutation safety

- Recording or revoking risk exceptions requires a confirmation step that names the exact CVE/target scope and the effect on counts.
- Single and bulk revocation use the same governed server-side transition contract, require permission, and return an audit identifier.
- Bulk revocation must report succeeded, failed, and not-attempted items; it must stop scheduling further client-side requests after a failure unless the backend supplies an atomic bulk operation.
- Mutation failures remain visible and retryable; console-only errors and silent continuation are not acceptable.

### Navigation and remediation handoffs

- Collection-to-detail navigation preserves allowlisted origin, scope, filters, search, sort, page size, and scroll/row context. Back navigation restores the originating view.
- Return URLs are restricted to internal Exposure routes; arbitrary redirect targets are forbidden.
- Detail routes opened directly remain valid and default to their owning Exposure context.
- The primary CTA label is `Open governed remediation`. Do not expose ambiguous action copy such as `Remediate` or `Create patch plan`.
- Exposure passes identifiers, selected scope, evidence generation, completeness, and originating route context only. The server re-derives executable targets and owns authorization, eligibility, approval, idempotency, and execution.
- Exposure does not directly run patching or create a second remediation execution path.

### Rollout and reversibility

- Build a deterministic tracer fixture first covering multi-source merge, stale fallback, ordered temporal events, image digest lineage, pagination, and authorization scope.
- Introduce new tables/contracts additively and dual-write before switching readers.
- Run the new read model in shadow mode and reconcile counts and identities by authorized scope and source class before any consumer cutover.
- Cut consumers over behind explicit flags with a documented observation window and rollback threshold.
- Retain legacy tables and read paths during the rollback window. Rollback means restoring the prior reader flag and/or Delta version; no destructive migration occurs until reconciliation passes.
- Live validation must use more than one Azure connection and must exercise Azure Update Manager, Defender findings, container-image evidence, Fabric persistence, Copilot, remediation correlation, and authenticated UI viewports.

### the agent's Discretion

- Exact physical table names, checkpoint record shape, event identifiers, cursor encoding, background refresh cadence, and feature-flag mechanism.
- Whether source-health detail is returned inline with every response or through a shared nested metadata structure, provided every Exposure consumer receives equivalent truth.
- Exact desktop table density, mobile card composition, disclosure design, and chart summary presentation within the locked UI/accessibility contracts.
- How broad the shadow reconciliation tolerance is, as long as scope/source mismatches and false-clear behavior are hard failures.

- Historical trend dashboards beyond the temporal state needed for correctness and audit.
- New remediation action types, autonomous execution behavior, or approval-policy redesign.
- Broad application-wide visual redesign or token-system replacement.
- General-purpose external vulnerability catalog browsing inside scoped tenant Exposure.

## Summary

**Researched:** 2026-09-03  
**Domain:** Governed exposure read model, temporal vulnerability evidence, Fabric/Delta projection, scoped keyset pagination, and resilient operational UI  
**Confidence:** HIGH for repository behavior; MEDIUM for the recommended architecture; LOW for unvalidated live-service performance

The current implementation has two incompatible collection truths. Scoped API requests select an AUM-only live service, while the persisted service contains Defender and container evidence; the live normalizer also applies different severity/classification semantics. [VERIFIED: `src/api/routers/vulnerability.py:20-34`; `src/semantic/live_operations.py:66-108`] Acquisition failures are converted into row-shaped dictionaries with the verbatim values `"status": "failed"` and `"provider_status": "failed"`, and ingestion still normalizes and publishes a generation. [VERIFIED: `src/onboarding/discovery_source.py:24-73`; `src/onboarding/ingestion_service.py:94-143`] The existing generation store and Delta writer already provide the right atomicity and rollback foundations: generations are prepared before a single pointer switch, while Delta supports the verbatim modes `"overwrite"`, `"append"`, `"merge"`, and `"snapshot-merge"` plus restore. [VERIFIED: `src/storage/datasets.py:36-135,167-325`; `src/storage/delta_writer.py:17-26,113-115,184-222`]

The safest implementation is therefore **not** another request-time hybrid. Publish AUM as a high-cadence, separately checkpointed durable source partition; combine its latest usable partition with persisted Defender/image partitions into one immutable, generation-pinned Gold Exposure projection. Every API, Copilot tool, remediation correlator, and UI query must read that projection through a scope-required port. This makes totals and cursors stable, lets failed families retain their own last-known-good partition, and prevents a scoped live failure from falling back to an unauthorized or differently scoped aggregate.

The migration must be additive: typed acquisition outcomes first, source-partition manifests and immutable observations second, deterministic current-state and Gold projections third, and shadow consumers last. Historical data must not invent `first_detected_at`; records without a trustworthy provider observation time remain unknown for SLA. The selected production deployment-evidence hierarchy is Defender subassessment digest identity joined only to exact immutable digests observed by Azure Monitor Container Insights (`KubePodInventory` plus `ContainerInventory`/`ContainerImageInventory`) through the repository's bounded Logs adapter. ARG discovers cluster/workspace/resource context but cannot prove a running digest. Missing tables, stale joins, tag-only rows, or digest mismatches remain explicitly unknown.

**Primary recommendation:** Build one generation-pinned Gold Exposure read model from durable per-connection/per-family partitions, then cut all consumers over behind independent flags only after scoped shadow reconciliation and the 100k keyset-pagination benchmark pass.

### Pattern 1: Durable Overlay, Not Provider Selection

Build a new Gold generation from the union of:

1. latest usable AUM partitions;
2. latest usable Defender finding/posture partitions;
3. latest usable image/digest partitions;
4. durable enrichment facts; and
5. ontology-resolved application/business-service links.

Merge identity is tenant + canonical target + target kind + canonical weakness identity. Keep evidence source-specific. An AUM install can close an AUM missing episode for the same normalized target and KB/CVE only; it must not erase still-current Defender evidence. The aggregate exposure remains active while any authoritative current evidence is active. Derive operational severity conservatively from active source evidence while returning each source's original severity and timestamp.

Collection requests never invoke ARG or rebuild the model. “Live AUM” means the latest successfully published, high-cadence AUM partition whose attempt/success age is visible. This is the only architecture compatible with exact totals, stable cursor traversal, shadow reconciliation, and LKG.

### Pattern 2: Typed Outcome + Partition Manifest

`fetch()` should produce one outcome per connection and query/source family:

```python
@dataclass(frozen=True)
class AcquisitionOutcome:
    connection_id: str
    source_family: str
    attempted_at: datetime
    completed_at: datetime | None
    rows: tuple[Mapping[str, object], ...] | None
    error_code: str | None
    error_summary: str | None
```

Interpretation:

- `rows=()` with no error after all provider pages complete is **healthy-empty**.
- `rows=None` with an error is failure and cannot replace the effective partition.
- On failure with LKG, carry the old partition forward and retain its original successful timestamps/generation; only attempt metadata changes.
- On failure without LKG, publish no domain rows and state **unavailable**.
- Mixed healthy and failed connections are **partial**, even if total row count looks plausible.
- Sanitize error summaries at acquisition; never persist provider response bodies, tokens, or full command lines.

Expose a derived state with precedence:

```text
unavailable > partial > stale > healthy-empty > complete
```

Keep orthogonal fields (`represented_connections`, `expected_connections`, `last_attempt_at`, `last_success_at`, `effective_generation_id`, `carried_forward`, `row_count`, `event_watermark`) so the precedence label does not destroy detail. The locked labels are quoted verbatim as `"complete"`, `"partial"`, `"stale"`, `"unavailable"`, and `"healthy-empty"`. [VERIFIED: `.planning/phases/03.1-exposure-reliability-and-scale/03.1-CONTEXT.md:41-51`]

Extend `metadata_source_status`; do not create an unrelated health subsystem. Its current rows are table-oriented and use verbatim statuses `"succeeded"`, `"skipped"`, and `"failed"`. [VERIFIED: `src/fabric/sync_service.py:1932-2003`] Add connection/family dimensions and both attempted/effective generation fields so a carried-forward partition cannot masquerade as newly acquired.

### Pattern 3: Immutable Temporal Observations + Replayable Current Projection

Use an append-only Silver observation table and a separately replaceable current-state table.

**Stable observation identity:** SHA-256 over tenant, connection, source family, normalized target, weakness kind/id, provider operation ID, provider event time, normalized status, and canonical payload fingerprint. Do not use Python's process-randomized `hash()`.

**Current key:** tenant + normalized target + target kind + weakness kind + weakness ID. Include source family in the evidence key, not the aggregate key.

**Order tuple:**

1. provider event time;
2. successful provider operation status before unsuccessful/unknown status at the same time;
3. source sequence or generation;
4. ingestion time; and
5. stable observation ID.

The locked event labels are verbatim `"missing"`, `"installed"`, `"resolved"`, and `"reintroduced"`. [VERIFIED: `.planning/phases/03.1-exposure-reliability-and-scale/03.1-CONTEXT.md:54-65`] A successful later install/resolution closes only matching evidence. A later missing event starts a new episode and increments `reintroduction_count`. Any late event appends normally, then replays only the affected current key from all its observations.

Keep these fields semantically separate:

| Field | Meaning | Backfill rule |
|-------|---------|---------------|
| `event_time` | Provider-reported occurrence/assessment/operation time | Parse provider value; nullable if absent |
| `first_detected_at` | Earliest trustworthy tenant-scoped detection ever | Minimum trustworthy event time; never publication time |
| `episode_started_at` | Start of current missing/reintroduced episode | Derived during replay |
| `last_observed_at` | Latest ordered evidence time | Derived; may differ from ingestion |
| `ingested_at` | When adapter accepted the row | New run timestamp |
| `run_at` | Acquisition run identity/time | Source checkpoint |
| `published_at` | Generation activation time | Publication metadata only |
| `enriched_at` | External catalog refresh time | Enrichment fact only |

Backfill old rows only when their provider payload has a trustworthy timestamp. Otherwise set `first_detected_at=null` and SLA state indeterminate. A future observation cannot retroactively prove an earlier detection date.

### Pattern 4: Container Identity and Fabric Round-Trip

Model these first-class identities:

| Concept | Stable identity | Notes |
|---------|-----------------|-------|
| Registry | normalized registry resource ID/host | Never a server/workload substitute |
| Logical image | registry + repository | Tags are aliases, not identity |
| Digest | normalized immutable digest (`sha256:…`) | Primary vulnerability target |
| Workload/controller | cluster + namespace + controller kind/name + pod UID | Only from observed Container Insights runtime evidence |
| Application | existing canonical application identity | Linked from observed/mapped workload |
| Business service | existing canonical service identity | Traversed through application |
| Vulnerability observation | digest + CVE/assessment + source event identity | Immutable Silver evidence |

Recommended relationships:

```text
ContainerRegistry -CONTAINS-> ContainerImage
ContainerImage -HAS_DIGEST-> ContainerImageDigest
ContainerImageDigest -DEPLOYED_AS-> ContainerWorkload
ContainerWorkload -RUNS_APPLICATION-> Application
BusinessService -CONTAINS-> Application
VulnerabilityObservation -AFFECTS-> ContainerImageDigest
VulnerabilityObservation -IDENTIFIES-> Vulnerability
```

Create granular Silver tables for image, digest, digest vulnerability observation, and observed workload deployment; keep dual-writing the current aggregate image table during migration. Update `schema_registry`, `dataset_mapper`, `entity_builder`, `relationship_builder`, graph query adapters, and round-trip tests together. A relationship must survive source row -> ontology -> Fabric entity/relationship tables -> readback -> rebuilt ontology.

Acquire workload context with fixed, bounded KQL over `KubePodInventory`, `ContainerInventory`, and `ContainerImageInventory`. Use Defender subassessment `imageDigest` as the vulnerability target authority. A deployment edge is valid only when the observed image ID normalizes to the same immutable `sha256` digest and cluster/container observation windows overlap; repository/tag equality is supporting context, never identity. Do not emit `DEPLOYED_AS`, `RUNS_APPLICATION`, or service impact when Container Insights is absent, stale, incomplete, or has no exact digest match. Return workload coverage as unavailable/unknown rather than infer.

### Pattern 5: Gold Read Model and Cursor Contract

Materialize rows optimized for operational reads, not raw event replay:

- canonical exposure/target/weakness IDs;
- current state and priority tuple;
- first detection/current episode/last observation timestamps;
- per-source evidence and completeness summaries;
- Defender/AUM/image source flags;
- enrichment snapshot and age;
- digest/workload/application/business-service IDs where observed;
- `read_model_generation_id`;
- precomputed filter/sort dimensions.

Keep enough recent Gold generations addressable for cursor TTL and rollback. Do not overwrite away the generation referenced by an unexpired cursor. Either retain generation partitions or reject an expired/evicted cursor with a typed conflict requiring restart; never silently continue against a newer generation.

The opaque client contract is a signed token containing:

```json
{
  "version": 1,
  "generation": "immutable-read-model-generation",
  "scope_hash": "hash-of-effective-scope",
  "query_hash": "hash-of-filters-sort-page-size",
  "last": ["priority-sort-value", "stable-exposure-id"],
  "expires_at": "timestamp"
}
```

Clients treat the token as opaque. The server recomputes effective scope and query hashes before use. Default keyset ordering is priority/risk descending, then stable exposure ID ascending. Sort columns are allowlisted; values remain bound parameters. A cursor cannot change page size, search, filters, sort, scope, or principal context.

Each collection response should have one consistent envelope:

```typescript
interface CursorPage<T> {
  data: T[];
  total: number;
  page_size: 25 | 50 | 100;
  loaded_start: number;
  loaded_end: number;
  next_cursor: string | null;
  generation_id: string;
  query: ExposureQueryState;
  completeness: ExposureCompleteness;
}
```

The page-size literals are locked verbatim as `"25, 50, or 100"` with default `50`, and search debounce is approximately `300 ms`. [VERIFIED: `.planning/phases/03.1-exposure-reliability-and-scale/03.1-CONTEXT.md:85-91`] The server computes `COUNT(*)` under the same effective scope/filter/generation as the page query.

## Source-Family Checkpoint and Completeness Contract

### Family boundaries

Checkpoint at the narrowest independently failing and independently replaceable unit:

```text
connection × source family × authorized subscription set
```

Recommended source families:

- AUM assessment summaries/details;
- AUM installation operations;
- Defender recommendations/assessments/subassessments;
- Defender alerts;
- Defender attack paths;
- Defender secure scores/controls;
- container image findings;
- observed container workloads from Azure Monitor Container Insights;
- each external enrichment catalog.

Do not derive the checkpoint solely from query table name. Several semantic products can originate from the same successful raw query; they may share acquisition outcome but still have separate normalized partition counts.

### Attempt/effective partition algorithm

1. Snapshot the expected authorized connections and subscription scope.
2. Run each source family independently; isolate exceptions per connection.
3. Validate provider response shape and full paging before calling it successful.
4. Normalize only successful rows through one canonical normalizer.
5. Stage new successful partitions, including valid empty partitions.
6. For failed partitions, reference/carry the prior successful partition unchanged.
7. Build immutable observations and current/Gold projection from effective partitions.
8. Validate referential integrity, counts, source status, and no false clears.
9. Atomically activate the generation and its manifest.
10. Emit reconciliation and health telemetry after activation.

### Aggregate state derivation

| Condition | State | Count semantics |
|-----------|-------|-----------------|
| Every expected connection/family completed, fresh, non-empty or mixed rows | complete | Exact |
| Every expected connection/family completed and all effective rows are zero | healthy-empty | Exact zero |
| Some expected connection/family has no usable partition, others are usable | partial | Exact only for represented scope; never present as tenant total |
| Every expected partition is represented but at least one is carried forward beyond freshness threshold | stale | Exact for the pinned LKG generation, not current provider truth |
| No usable partition for the required section | unavailable | Value is null/unknown, not zero |

Store state per family and derive section/aggregate state conservatively using the precedence above. Totals must include represented/expected connection counts so a partial result cannot be mistaken for a complete smaller estate.

1. **Schema first:** register additive nullable columns/tables; bump the current verbatim schema `"2.0.0"` to an additive minor version. [VERIFIED: `src/fabric/schema_registry.py:535-551`]

8. **Observe and roll back if thresholds fail.**
9. **Only after the rollback window:** retire request-time hybrid wiring and legacy write/read paths in a separate cleanup.

### Backfill invariants

- Existing publication/acquisition time is not first detection.
- Existing install rows without a successful operation status do not close missing state.
- Unknown provider time remains null and orders after trusted provider-time evidence only via explicit deterministic fallback metadata.
- Re-running backfill is idempotent because observation IDs are stable.
- Rebuilding current/Gold from the same observations produces byte-equivalent keys, state, ordering, and counts.

## Common Pitfalls

### Pitfall 1: “Live” request path bypasses governed truth
**What goes wrong:** Scoped endpoints again show AUM-only data or drift between pages.  
**Why:** Provider selection happens in the router.  
**Avoid:** Persist high-cadence AUM partitions and read only generation-pinned Gold.  
**Warning signs:** ARG calls in collection routes, changing totals while traversing one cursor.

### Pitfall 2: LKG retained at the wrong granularity
**What goes wrong:** One failed connection retains or clears an entire mixed dataset.  
**Why:** Source families/connections share physical partitions.  
**Avoid:** Make connection × family × authorized scope independently replaceable and attributable.  
**Warning signs:** A single `freshness` timestamp or one row count for all connections.

### Pitfall 3: Failure is confused with successful empty
**What goes wrong:** Previous exposure disappears and UI displays zero.  
**Why:** Error sentinels normalize or failed datasets overwrite old data.  
**Avoid:** Typed `rows=None/error` versus successful `rows=()`.  
**Warning signs:** Domain rows with status failed; empty partition accompanied by provider error.

### Pitfall 4: Old installs permanently suppress reintroduced missing state
**What goes wrong:** Exposure never reopens.  
**Why:** Presence-based matching instead of event ordering.  
**Avoid:** Ordered append-only observations and per-key replay.  
**Warning signs:** Any `installed_keys` set used without event/status comparison.

### Pitfall 5: Backfill fabricates SLA certainty
**What goes wrong:** Publication day becomes first detection and overdue state is wrong.  
**Why:** Existing model requires a timestamp.  
**Avoid:** Nullable `first_detected_at` and explicit backfill quality.  
**Warning signs:** `published_at` or ingestion time assigned to first detection.

### Pitfall 6: Gold projection is scalable but cursor is not stable
**What goes wrong:** Duplicates/omissions after a refresh.  
**Why:** Cursor does not pin generation or Gold retains only one overwrite.  
**Avoid:** Retain addressable generations through cursor TTL or return typed expiry conflict.  
**Warning signs:** Cursor contains only offset or last ID.

### Pitfall 7: Exact total and page use different predicates
**What goes wrong:** Range says 1–50 of N but traversal yields a different set.  
**Why:** Scope/filter logic is duplicated.  
**Avoid:** Compile one validated query specification into both count and keyset statements.  
**Warning signs:** Separate filter builders or post-query scope filtering.

### Pitfall 8: Ontology rebuild drops edges
**What goes wrong:** Image rows exist but runtime/service impact vanishes after Fabric round-trip.  
**Why:** Relationships are rebuilt from entities without image handlers.  
**Avoid:** Round-trip tests for every proposed entity and edge.  
**Warning signs:** Tests assert only row counts, not exact edge triples.

### Pitfall 9: Workload lineage is inferred from tags or registries
**What goes wrong:** Business impact is confidently wrong.  
**Why:** No runtime deployment source exists.  
**Avoid:** Nullable links and explicit coverage state.  
**Warning signs:** Registry ID appears as server/workload ID.

### Pitfall 10: Independent API calls still render as one state
**What goes wrong:** Healthy sections disappear during one source refresh/failure.  
**Why:** Route computes `allLoading`/`anyError`.  
**Avoid:** Section-owned state wrappers and same-scope LKG retention.  
**Warning signs:** One top-level conditional around all content.

### Pitfall 11: SQL endpoint is treated as universally available
**What goes wrong:** Production falls back to full Delta materialization and misses SLO.  
**Why:** Optional builder silently returns `None`.  
**Avoid:** Startup/readiness capability signal and benchmark the actual deployed path.  
**Warning signs:** No ODBC driver in image or telemetry cannot identify adapter.

### Pitfall 12: Telemetry leaks high-cardinality/sensitive identifiers
**What goes wrong:** ARM IDs, tenant IDs, CVEs, or provider errors become metric labels.  
**Why:** Convenient dimensions are added without cardinality/privacy review.  
**Avoid:** Low-cardinality labels only; put sanitized IDs in access-controlled logs/traces.  
**Warning signs:** resource/tenant/error-message attributes on counters/histograms.

## Code Examples

The following are proposed implementation patterns, not copied contracts.

### Deterministic projector

```python
def project_current(observations: Sequence[ExposureObservation]) -> ExposureCurrent:
    ordered = sorted(
        observations,
        key=lambda item: (
            item.event_time_is_unknown,
            item.event_time_or_min,
            item.operation_precedence,
            item.source_sequence,
            item.ingested_at,
            item.observation_id,
        ),
    )
    state = ExposureCurrent.empty(ordered[0].current_key)
    for observation in ordered:
        state = state.apply(observation)
    return state
```

`apply()` must be pure. An installed/resolved observation closes only matching, earlier, active evidence with successful provider status; a later missing observation creates a reintroduction episode.

### Scope-bound keyset query

```python
def list_exposures(
    *,
    effective_scope: EffectiveScope,
    query: ExposureQuery,
    cursor: str | None,
) -> CursorPage[ExposureRow]:
    token = cursor_codec.decode_and_validate(
        cursor,
        scope_hash=effective_scope.fingerprint(),
        query_hash=query.fingerprint(),
    )
    spec = compile_exposure_query(
        scope=effective_scope,
        query=query,
        generation_id=token.generation_id if token else active_generation(),
        after=token.last_sort_tuple if token else None,
    )
    return read_adapter.execute(spec)
```

The compiler allowlists columns/operators and emits bound values. It is the single source for both `COUNT(*)` and page predicates.

## Open Questions (RESOLVED)

1. **RESOLVED — authoritative workload/controller -> immutable image digest evidence**
   - **Decision:** Defender for Cloud subassessment `imageDigest` is authoritative for digest-level vulnerability identity. Azure Monitor Container Insights supplies deployment context through fixed bounded queries over `KubePodInventory`, `ContainerInventory`, and `ContainerImageInventory`, using the existing per-connection Logs client and dynamically discovered authorized workspaces.
   - **Rationale:** ARG can discover AKS/workspace ARM resources but cannot prove runtime pod/controller digests. Microsoft Learn documents the required controller, namespace, pod, container, image ID, repository, and observation-time fields. Emit deployment/application/service edges only for an exact normalized immutable digest match within the configured observation window; tag-only or absent evidence is `unknown`.

2. **RESOLVED — cursor TTL and Gold generation retention**
   - **Decision:** Cursor TTL is configurable with a 15-minute default. Retain Gold generations for seven days and at least the latest two successful generations, whichever retains more, while never evicting a generation referenced by an unexpired cursor. Evicted/expired generations return a typed restart conflict.
   - **Rationale:** Fifteen minutes bounds replay risk while supporting normal operator traversal; seven days covers refresh/canary rollback without silently rebasing active cursors.

3. **RESOLVED — production Exposure adapter**
   - **Decision:** The existing `FabricSqlReader` over the Lakehouse SQL analytics endpoint is the deployed production adapter. Production new-reader startup/enablement fails unless endpoint metadata, `pyodbc`, Microsoft ODBC Driver 18, Entra token connectivity, required Gold tables/columns, bound count/page queries, and the 100k p95 gate pass. Delta remains a functional local/test and explicit rollback path, not a production scale-certified substitute.
   - **Rationale:** Existing Delta reads materialize full tables; only the repository SQL seam pushes scope/filter/count/keyset work into Fabric. The current silent fallback is incompatible with an authoritative 100k SLO.

4. **RESOLVED — per-source-family freshness**
   - **Decision:** Typed configurable defaults are AUM `1800s`, Defender findings/posture `21600s`, container images `86400s`, Container Insights workloads `900s`, and external enrichment `86400s`. Age exactly equal to the threshold is fresh; age greater by one second is stale. Every response names `freshness_threshold_seconds` and `freshness_source_family`.
   - **Rationale:** Cadences differ materially; one global timestamp would let a fast source mask a stale family. Boundary tests cover each family and configuration overrides.

5. **RESOLVED — cursor key storage and rotation**
   - **Decision:** Store active and previous HMAC keys as versioned secrets in the existing Azure Key Vault, inject them into the API Container App through user-assigned-managed-identity Key Vault secret references, and identify tokens by `kid`. Rotation creates a new version, promotes active to previous, keeps a 30-minute overlap (twice the default TTL), verifies both old and new tokens, then retires the previous key only after overlap and unexpired-token checks.
   - **Rationale:** The repository already provisions Key Vault, managed identity, RBAC, and secret-backed Container App environment variables. A two-key ring gives fail-fast startup and non-breaking rotation without storing key material in source or Terraform state.
