## ⚠️ BLOCKING CONSTRAINT — READ BEFORE RESUMING

Phase 7 was paused mid-execution (07-02 complete, 07-03 not started) because of a
**fundamental architecture pivot**: Fabric is now intended to become the **unified data
platform** for the whole system, not a downstream analytics/semantic plane.

- New direction: Fabric pipelines ingest and refresh data directly from ARG, LAW, and
  any other required sources; Fabric performs data cataloguing and ETL to curate the
  tables that power web, API, Hermes, etc. **Every component becomes a pure consumer**
  of Fabric-curated data — no component queries ARG/LAW directly anymore, not even for
  interactive/live features.
- This directly contradicts the currently-documented architecture in
  `FABRIC_INTEGRATION.md`, which states Fabric is "the governed semantic and analytics
  plane... **not** the source of operational truth," with Azure services remaining
  authoritative and Fabric receiving curated *projections* via an Ontology Steward
  pattern (one-way: discovery engines → Steward → OneLake → Fabric IQ Ontology).
- It also contradicts Phase 7's own decisions (`07-CONTEXT.md`, D-01/D-02/D-15), which
  have the new `intelligence/inventory` Python domain **issue its own ARG query** to
  acquire PaaS resources and own acquisition/normalization/retention/publication
  in-process. That is Python-side ingestion — the opposite of "Fabric owns ingestion."

**Do not resume 07-03 (or 07-04–07-06) as currently written without first re-confirming
scope.** They assume Python owns ARG acquisition; under the new model that acquisition
belongs in Fabric pipelines instead.

### Feasibility research already done (don't re-research this)
- Fabric's ARG connector (Data Factory/Dataflows Gen2) is **Import mode only** — no
  DirectQuery, no push/streaming. Practical refresh latency floor is ~15+ minutes,
  driven by pipeline schedule interval.
- LAW → Fabric has no native low-latency connector either; typical patterns are Copy
  Data/REST pulls or bridging through Event Hub for anything faster than batch. Fabric's
  own "workspace monitoring" Eventhouse is for monitoring Fabric's *own* pipeline runs,
  not a general LAW ingestion accelerator.
- **User has explicitly accepted this tradeoff**: minutes of staleness everywhere,
  including previously-interactive features (e.g. the live network path-analysis
  feature with a 30s ARG cache, fixed and deployed this same session as unrelated work).
  This is a settled decision, not open for debate unless the user revisits it.
- **Subscription differentiation**: settled as row-level tagging only —
  `subscription_id`/`tenant_id` columns on every curated table (already present per
  `src/fabric/dataset_mapper.py`), with the existing API-layer authorization continuing
  to enforce which subscriptions a user/connection can query. Fabric/OneLake itself does
  **not** need row-level security or per-tenant workspaces.
