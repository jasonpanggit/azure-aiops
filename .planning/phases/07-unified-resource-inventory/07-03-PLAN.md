<objective>
Replan and execute ownership inversion for the Fabric pivot: inventory becomes independently runnable and publishes governed Fabric/OneLake-backed inventory datasets/tables, while preserving the current OS/software read contract and removing Hermes as the inventory lifecycle owner.

Purpose: INV-07 after the 2026-08-26 Fabric pivot. The prior 07-03 plan was superseded because it moved inventory into a neutral generation store without defining Fabric as the authoritative data platform. This plan first defines the Fabric-backed inventory contract, then moves the OS/software pipeline behind it.

Output: a Fabric inventory publication contract, an independently runnable inventory pipeline that publishes through that contract, compatibility reads preserving the Phase 6 observable behavior, and executable tests proving no Hermes graph sync is required.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide the Fabric inventory table contract shape</name>
  <decision>How OS/software compatibility rows are represented in Fabric/OneLake while preserving current API/read behavior.</decision>
  <context>
The Fabric pivot is settled: Fabric/OneLake is the unified inventory data platform. This decision only selects the first contract shape for the current OS/software families.

The current inventory API and characterization suite read four logical datasets:
- `inventory/os_observations`
- `inventory/source_status`
- `inventory/software_observations`
- `inventory/software_source_status`

Fabric already has a schema registry, quality validator, Delta writer, OneLake writer, and `FabricSyncService`, but the existing Fabric mapping is graph/ontology oriented (`bronze_resources`, `silver_vm_inventory`, ontology tables). Inventory needs its own governed table contract instead of hiding behind graph tables.
  </context>
  <options>
    <option id="compat-table-names">
      <name>Use dedicated Fabric inventory tables preserving existing logical dataset names as table aliases</name>
      <pros>Preserves current API/test shape; enables direct migration from DatasetStore snapshots; reduces immediate blast radius</pros>
      <cons>Table names need aliasing/normalization because Fabric table names cannot use slash-delimited dataset names directly</cons>
    </option>
    <option id="new-fabric-names-with-adapter">
      <name>Use new Fabric-native table names with an adapter that exposes the old logical dataset names</name>
      <pros>Clean Fabric naming from day one; makes future PaaS/resource-family tables easier to standardize</pros>
      <cons>Requires an explicit compatibility adapter and stronger tests to prove old row shapes are unchanged</cons>
    </option>
  </options>
  <recommended>new-fabric-names-with-adapter</recommended>
  <resume-signal>Select: compat-table-names, new-fabric-names-with-adapter, or describe an alternative</resume-signal>
  <reversibility rating="costly">Changing table names after Phase 8/9 consumers adopt the read port requires a compatibility migration.</reversibility>
</task>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Azure Resource Graph -> inventory pipeline | Untrusted provider payloads enter the inventory domain directly |
| Log Analytics ConfigurationData -> inventory pipeline | Untrusted workspace query results enter the inventory domain directly |
| inventory pipeline -> Fabric/OneLake | Inventory writes the platform source of truth and must pass schema/quality gates |
| Fabric-backed inventory -> compatibility read model | Current API contracts are preserved while persistence moves |
| Hermes sync -> inventory refresh peer call | Operational chaining must not make Hermes the owner again |
