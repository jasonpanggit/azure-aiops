  <files>src/intelligence/inventory/read_port.py, src/intelligence/inventory/service.py, src/intelligence/inventory/__init__.py, tests/test_inventory_read_port.py</files>
  <read_first>
    - src/intelligence/inventory/service.py (the cross-family scoped query built in plan 07-05 task 3 — the port must be built over the same query, not a parallel one)
    - src/intelligence/inventory/registry.py (registered families — the port enumerates across them)
    - src/intelligence/inventory/models.py (ResourceObservation and the payload field — the port's return contract)
    - src/api/scope.py (Scope, Scope.matches, scope_attributes — the scope enforcement the port must apply)
    - src/api/routers/inventory.py (the cross-family route from plan 07-05 — the consumer that must share the port's query)
    - src/intelligence/governance/finops.py (an example of a subsystem that currently has zero dataset reads and would be a future port consumer — read only enough to confirm the port signature suits it)
  </read_first>
  <behavior>
    - Listing resources for an effective scope returns only rows matching that scope; a row in a non-selected subscription is absent.
    - An unrestricted scope returns rows across every registered family.
    - Filtering by family returns only that family's rows; filtering by resource type narrows further.
    - Looking up a single resource by its ARM id returns it when in scope and returns nothing when out of scope, rather than raising differently for the two cases.
    - When a family is unavailable, the port reports that family's absence rather than silently returning a short list that looks complete.
  </behavior>
  <action>
    Define one read port over the inventory read model: list resources for a scope with optional family and resource-type narrowing, and fetch one resource by ARM id for a scope. Name and signature are the agent's discretion; keep it small, since six subsystems will adopt it and every parameter added now is a parameter each must reason about.

    Scope is a required parameter on every method, not an optional filter. A port whose default is unscoped will eventually be called unscoped, and that is a cross-tenant disclosure rather than a bug. There must be no code path that returns rows without applying scope.

    Build the port over the same underlying scoped query the cross-family route uses, so a scope-enforcement fix in one place cannot leave the other behind.

    An out-of-scope single lookup must be indistinguishable from a genuinely absent resource. Returning a distinguishable not-authorized signal would let a caller enumerate resource existence outside its scope.

    Report family unavailability through the return rather than swallowing it. A caller receiving a short list with no signal cannot tell a small estate from a degraded family, and that ambiguity is exactly what INV-09 exists to remove.

    Export the port from the inventory package so consumers import one obvious name rather than reaching into a module path.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internal subsystem -> read port | Six future consumers cross this boundary; the port is the single scope-enforcement chokepoint |
| caller-supplied scope -> port query | Scope must be the server-derived effective scope, never a client-supplied selector |
| source tree -> enforcement guard | The guard is the durable control preventing scope bypass via direct dataset reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-07-22 | Elevation of Privilege | read port scope parameter | critical | mitigate | Scope is required on every port method with no unscoped code path; task 1 requires a test that omitting scope is a call error and a negative test for out-of-scope rows |
| T-07-23 | Information Disclosure | single-resource lookup | high | mitigate | Out-of-scope and absent are indistinguishable to the caller, preventing existence enumeration outside scope; asserted by test in task 1 |
