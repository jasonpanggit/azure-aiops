    - tests/test_inventory_characterization.py (the harness written in task 1 — reuse it, do not duplicate it)
  </read_first>
  <behavior>
    - Retention: after a successful run publishes software rows, a second run whose software fetch fails republishes the previously published software rows AND reports a non-ready source state for that family. The result is never an empty set paired with a ready state.
    - Retention negative case: a genuinely successful refresh that legitimately returns zero rows publishes zero rows paired with a ready state, and is therefore distinguishable from the retained case.
    - Publication timing: inventory datasets are readable only from the active generation; before any run completes, the read model reports no snapshot rather than an empty estate.
    - Preservation: across two successive runs, a row's created timestamp from run one survives into run two, and per-source watermarks are carried forward rather than reset.
  </behavior>
  <action>
    Extend the fixture (or add a sibling fixture) so a failing/degraded software refresh can be simulated deterministically — the fake source must be able to return a non-ready software status without raising. Prefer extending tests/fixtures/mock_inventory_arg.json with an additive key over creating a parallel fixture, so the existing fixture escape hatch keeps working unchanged.

    Write the four behavior tests described above, each as a two-run sequence against one temp store root so publication order and read order genuinely interact — that interaction is the whole point of the retention rule and cannot be exercised by a single run.

    Assert the retained-versus-empty distinction explicitly by comparing both the row set and the source state in the same assertion. A test that checks only row count would pass against a regression that publishes retained rows with a ready state, which is precisely the failure the rule exists to prevent.

    Assert timestamp and watermark preservation by capturing the values published by run one and comparing them to run two, rather than against literals.
  </action>
