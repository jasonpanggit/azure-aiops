  <behavior>
    - Retention: after a successful run publishes software rows, a second run whose software fetch fails republishes the previously published software rows AND reports a non-ready source state for that family. The result is never an empty set paired with a ready state.
    - Retention negative case: a genuinely successful refresh that legitimately returns zero rows publishes zero rows paired with a ready state, and is therefore distinguishable from the retained case.
    - Publication timing: inventory datasets are readable only from the active generation; before any run completes, the read model reports no snapshot rather than an empty estate.
    - Preservation (conditional — establish empirically first): determine whether inventory rows currently preserve created timestamps and per-source watermarks across two successive runs. If they do, pin that. If they do not, pin the actual observed behavior instead and record the finding.
  </behavior>
  <action>
    Extend the fixture (or add a sibling fixture) so a failing/degraded software refresh can be simulated deterministically — the fake source must be able to return a non-ready software status without raising. Prefer extending tests/fixtures/mock_inventory_arg.json with an additive key over creating a parallel fixture, so the existing fixture escape hatch keeps working unchanged.

    Write the behavior tests described above, each as a two-run sequence against one temp store root so publication order and read order genuinely interact — that interaction is the whole point of the retention rule and cannot be exercised by a single run. Drive every run through the `tests/inventory_harness.py` seam from task 1, never through a driver directly.

    Assert the retained-versus-empty distinction explicitly by comparing both the row set and the source state in the same assertion. A test that checks only row count would pass against a regression that publishes retained rows with a ready state, which is precisely the failure the rule exists to prevent.

    **Preservation — determine the truth before writing the test.** 07-CONTEXT.md states inventory "rides along with" `_preserve_created_timestamps` and `_preserve_source_watermarks`. Verify that claim against the code before asserting it. Read both helpers: `_preserve_created_timestamps` operates on `situations/evidence`, `entities/*`, and `relationships/relationships`; `_preserve_source_watermarks` reads `situations/source_status` and writes `graph.source_status`, while inventory's software status lives on a separate field. If neither helper touches any `inventory/*` dataset, then **inventory has no such preservation behavior today**, and "no such behavior exists; nothing to preserve" is a valid and expected finding — record it explicitly in the plan summary and write the test to pin the actual observed behavior (for example, that a created timestamp is regenerated per run) rather than manufacturing a passing preservation test for behavior that does not exist.

    Whichever way the finding lands, state it unambiguously in the summary, because plan 07-03 task 2's requirement to reproduce preservation inside the inventory pipeline is **conditional on this finding** and is dropped if the behavior does not exist.

    Where preservation does exist, assert it by capturing the values published by run one and comparing them to run two, rather than against literals.
