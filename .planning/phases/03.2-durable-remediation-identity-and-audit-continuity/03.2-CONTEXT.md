# Phase 03.2: Durable Remediation Identity and Audit Continuity - Context

**Gathered:** 2026-09-03
**Status:** Ready for planning
**Mode:** Autonomous decisions derived from Phase 03 deep review

<domain>
## Phase Boundary

Give each remediation target/action family a stable plan identity, preserve
approval and execution audit continuity across evidence refreshes, and make
execution reads independent of regenerated plan availability. This phase does
not redesign retry accounting, verification scheduling, approval policy, or
operator presentation; those belong to Phases 03.3-03.6.

</domain>

<decisions>
## Implementation Decisions

### Stable Identity
- Derive the live plan ID from canonical target ARM ID, subscription, and governed action family only.
- Keep mutable patch selections and evidence outside the plan ID; they remain bound by the approved execution snapshot.
- Preserve the existing public plan-ID prefix where practical and provide compatibility for durable records created under the old identity.

### Durable Audit Access
- Authorize execution reads from immutable scope attributes stored on the execution record, not from the continued existence of a regenerated plan.
- Keep plan-specific list routes scoped through the current plan, but direct execution reads must survive plan disappearance.
- Preserve immutable decision and execution history; do not silently rewrite historical records.

### Request Consistency
- Resolve one planner/repository view per request so scope validation and execution use the same generation.
- A missing plan repository must fail closed through typed eligibility/provider errors, never `AttributeError`.
- Add health/diagnostic coverage for execution records whose legacy plan IDs no longer resolve.

### Migration and Compatibility
- New records use stable identity immediately.
- Legacy records remain readable and verifiable through their stored execution scope and snapshot.
- Avoid broad data migration in this phase; use compatibility reads and explicit diagnostics.

### the agent's Discretion
- Exact helper placement, canonicalization utility reuse, and typed error/status names may follow existing repository patterns.

</decisions>

## Existing Code Insights

### Reusable Assets
- `canonical_resource_key` already normalizes ARM IDs.
- `RemediationExecutionStore` persists snapshot, plan ID, and scope-bearing execution metadata with CAS transitions.
- API `Scope` and authorizer helpers already support resource/subscription/connection matching.

### Established Patterns
- Mutation parameters come only from server-owned, hash-bound snapshots.
- Out-of-scope resources are reported as not found.
- Provider unavailability is represented with typed API errors rather than raw exceptions.

### Integration Points
- `src/semantic/live_operations.py` live opportunity/plan identity.
- `src/api/routers/remediation.py` workflow and execution reads.
- `src/api/runtime.py` planner/execution-service construction.
- `src/intelligence/remediation/execution_service.py` repository guards.
- `src/intelligence/remediation/execution_store.py` durable scope attributes and legacy compatibility.
