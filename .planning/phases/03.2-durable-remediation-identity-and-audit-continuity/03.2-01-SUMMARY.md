# Phase 03.2 Plan 01: Durable Remediation Identity and Audit Continuity Summary

**Stable target+subscription+action-family plan identity, scope-attribute-authorized execution reads, fail-closed CR-06 guards, and an orphaned-execution diagnostics route — closing Phase 03 deep-review Recommendation 1.**

## Accomplishments

- `LiveRemediationPlanner._opportunity()` and `_configuration_opportunity()` (for mapped Defender actions) now derive `plan_id`/`opportunity_id` from `canonical_resource_key(target_id) + subscription_id + governed action family` only — never from `missing_kbs` — so a successful patch install no longer erases its own audit trail (CR-01).
- `RemediationExecutionStore.create_or_get()` accepts and persists `scope_attributes`; new module-level `execution_scope_attributes(record)` derives a legacy-compatible subscription-only fallback from `execution_snapshot.target_id` and fails closed (`{}`) when nothing is derivable.
- `get_execution`, `retry_execution`, and `cancel_execution` all authorize via the new `_authorize_execution_scope(scope, record)` helper (execution's own scope), not via `_get_scoped_plan` (plan's continued existence). `list_plan_executions` is deliberately unchanged.
- `execute()`, `retry()`, and `plan_eligibility()` fail closed with a typed `plan_repository_unavailable` reason instead of raising `AttributeError` when `plan_repository=None` (CR-06).
- New `RemediationExecutionService.orphaned_executions()` and `GET /api/v1/remediation/diagnostics/executions` report legacy/unresolvable execution records without any data migration (D-04).

## Decisions Made

- Manual-review Defender-configuration opportunities keep the recommendation-sensitive hash (never executed, so audit continuity doesn't apply, and distinguishability across multiple non-actionable rows for one asset still matters).
- `execution_scope_attributes()` prefers stored `scope_attributes`, falls back to a subscription-only derivation from `execution_snapshot.target_id`, and returns `{}` (fail closed) otherwise — legacy records without derivable scope stay readable only to unrestricted callers.
- `get_execution` now resolves the execution service unrestricted and authorizes separately, since `poll_verification` never touches `self._plans`/`self._patching` — matching the existing two-phase pattern already used by `retry_execution`/`cancel_execution`.
