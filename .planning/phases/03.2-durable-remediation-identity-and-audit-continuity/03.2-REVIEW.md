#### WR-05: `hybrid_remediation`'s TTL-cache *write* path is unsynchronized, so the fix for WR-01 does not fully close the request-consistency gap it targets — **RESOLVED**

**Resolution (2026-09-04T00:56:05+08:00):** `src/api/runtime.py` now imports `threading` and `_ttl_cached_value` (the sole populator of `_hybrid_remediation_cache`) is thread-safe. A new `_ttl_cache_lock(cache, key)` helper lazily creates and returns a `threading.RLock()` scoped to one specific `(id(cache), key)` pair, guarded only briefly by a module-level `_ttl_cache_locks_guard` while the lock object itself is looked up/created (never held across a `build()` call). `_ttl_cached_value` keeps its lock-free warm-cache read for the common case; on a miss it acquires the per-key lock, re-checks the cache (covering a caller that queued behind another that already refreshed the entry), and only then calls `build()` and writes `cache[key]` — all while holding that one key's lock. Two genuinely concurrent callers racing the *same* `(root, subscription-set)` key now serialize on the same lock and observe the identical built object; callers racing *different* keys (or a different TTL-cache family dict) use different lock objects and never block each other, so a slow build for one subscription scope cannot stall an unrelated one. `RLock` (not a plain `Lock`) is used specifically so a hypothetical future reentrant call from `build()` back into `_ttl_cached_value` for the same `(cache, key)` on the same thread could not deadlock against itself.
**Files changed:** `src/api/runtime.py`, `tests/test_api_runtime.py`

**Original finding (unmodified, for record):**

**File:** `src/api/runtime.py:352 (`_hybrid_remediation_cache`), 355-374 (`_ttl_cached_value`), 2791-2814 (`hybrid_remediation`)`
**Issue:** WR-01's fix correctly locks `PlanRepository.replace_generation()`/`list()`/`get()` so two threads can't corrupt *one* repository instance. But it does not address the layer above: `_ttl_cached_value` populates the module-level `_hybrid_remediation_cache` dict with a bare `cache.get(key)` read followed by an unsynchronized `cache[key] = (now, value)` write — no lock, and `grep -n "threading" src/api/runtime.py` returns nothing (confirmed: the file imports no `threading` module at all).

Two genuinely concurrent HTTP requests for the same `(root, subscription-set)` cache key, landing during the same cache-miss window (Starlette dispatches these plain `def` routes to its worker thread pool, exactly as WR-01's own fix comment documents), can each call `_build_planner()` and each write their own `(now, planner)` tuple to `cache[key]`; whichever write lands last "wins" the slot. Concretely, within a *single* request R:
1. R's first call (from `operations.py::_require`'s remediation branch, via `_get_scoped_plan`) resolves `planner_A` and returns it.
2. A concurrent request S, racing on the same key, also misses the cache and overwrites `cache[key]` with `planner_S` *after* R's write.
3. R's second call (from `runtime.py::_execution_service_for_scope` -> `_planner_for_scope`, made moments later in the same request) now reads the cache and gets `planner_S`, not `planner_A`.

This defeats exactly the invariant 03.2-02 exists to guarantee and that `test_hybrid_remediation_provider_resolves_one_generation_per_request_window` only proves under single-threaded conditions (two sequential calls in one test, never two concurrent callers racing the same key). Impact is partially mitigated in practice by 03.2-01's stable plan-identity design (both planners would derive the same `plan_id` for the same underlying resource from the same subscription scope) and by the shared singleton `_remediation_decision_store()`/execution store, so this is unlikely to cause an outright 404 or a lost approval — but the specific "same object within one request" contract this phase's own comment and test assert is not actually enforced under concurrent load, which is the same class of gap WR-01 was raised to close one layer down.
**Fix:** Add a `threading.Lock()` around the cache dict's read-then-write critical section in `_ttl_cached_value` (or at minimum around the three per-cache-family dicts it serves), e.g.:
```python
_hybrid_remediation_cache_lock = threading.Lock()

def _ttl_cached_value(cache, key, *, ttl_seconds, now, build):
    with _hybrid_remediation_cache_lock:
        cached = cache.get(key)
        if cached is not None and now - cached[0] < ttl_seconds:
            return cached[1]
    value = build()  # build outside the lock to avoid holding it during I/O
    with _hybrid_remediation_cache_lock:
        cached = cache.get(key)
        if cached is not None and now - cached[0] < ttl_seconds:
            return cached[1]  # another thread built it first; use theirs for consistency
        cache[key] = (now, value)
        return value
```
At minimum, add a concurrency regression test analogous to `test_plan_repository_serializes_replace_generation_and_reads` — two threads racing `hybrid_remediation` on the same key — before relying on the "one instance per request" guarantee under multi-worker-thread production traffic.

**Resolution:** `execution_diagnostics` now derives `write_scope = context.authorizer.effective_scope(principal, "operate")` and returns `service.orphaned_executions()` only when `write_scope.is_unrestricted()`; a restricted operator now receives an empty list instead of system-wide records, applying the same fail-closed rule `_authorize_execution_scope` already applies to a single legacy execution (since `orphaned_executions()` only ever returns records whose scope attributes are empty by definition, `write_scope.matches({})` is always `False` for a restricted scope). `scope=write_scope.to_dict()` also now reflects the caller's real grant instead of always claiming `Scope.unrestricted()`.

**Test added:** `test_diagnostics_route_hides_orphans_from_a_scoped_operator` (`tests/test_api_remediation_execution.py`) — proves a `SUBSCRIPTION_OPERATOR_TOKEN`-scoped caller sees `[]` while the unrestricted `OPERATOR_TOKEN` caller still sees the orphaned record.

**File:** `src/api/routers/remediation.py:491-500`
**Issue:** Every other route in this file narrows to the caller's actual grant before touching data — e.g. `execute_plan` (`write_scope = context.authorizer.effective_scope(principal, "operate"); _get_scoped_plan(context, write_scope, plan_id)`), `retry_execution`/`cancel_execution` (`_authorize_execution_scope(write_scope, record)`), and `get_execution` (`_authorize_execution_scope(scope, record)`). `execution_diagnostics`, added by this phase, is the one exception: it unconditionally resolves the execution service via `Scope.unrestricted()` and returns `service.orphaned_executions()` — which includes every subscription's `execution_id`, `plan_id`, and `status` system-wide — gated only by `OperatePrincipal` (i.e. *any* principal holding an `operator`/`admin` role satisfies the dependency, per `src/api/rbac.py::_ACTION_ROLES[ACTION_OPERATE]`).

This codebase's own RBAC model explicitly supports narrowly-scoped operate grants: `Grant.scope` is validated against `GRANTABLE_DIMENSIONS = ("subscription", "business_service")` (`src/api/rbac.py`), meaning a real deployment can and does issue an `operator` role scoped to one subscription. Such a caller hitting `GET /api/v1/remediation/diagnostics/executions` today receives orphaned-execution records for every other onboarded subscription too — a cross-tenant existence/status disclosure that this phase's own threat model does not cover (T-03.2-04 addresses only the `get_execution` 404-shape question, which is a different, already-accepted risk).

Because `orphaned_executions()` only returns records whose `execution_scope_attributes()` is *already empty* (that is the definition of "orphaned"), naively narrowing with `write_scope.matches(execution_scope_attributes(record))` would make the route return nothing for every restricted caller (which may in fact be the intended, secure behavior, consistent with "legacy records without derivable scope stay readable only to unrestricted callers" — the same rule the phase already applies to `get_execution`). The fix is to apply that same rule here instead of hardcoding `Scope.unrestricted()`.
**Fix:**
```python
@router.get(
    "/diagnostics/executions",
    summary="Report orphaned/legacy remediation executions",
)
def execution_diagnostics(context: Context, principal: OperatePrincipal) -> dict[str, Any]:
    write_scope = context.authorizer.effective_scope(principal, "operate")
    service = _execution_service(context, Scope.unrestricted())
    orphans = [
        row for row in service.orphaned_executions() if write_scope.is_unrestricted()
    ]
    return envelope(
        {"orphaned_executions": orphans},
        evidence=_execution_evidence("diagnostics"),
        scope=write_scope.to_dict(),
    )
```
(Or, more granularly, reject with `ApiError(ErrorCode.PROVIDER_UNAVAILABLE, ...)`/403 for non-unrestricted callers if diagnostics is meant to be an admin-only surface — either way, the route must not silently serve system-wide data to a scoped operator.)

```python
    self._plans = tuple(copy.deepcopy(plans))
```
There is no lock here (unlike `RemediationExecutionStore`, which already uses `self._lock` around every read/write). All remediation router handlers are plain `def` (not `async def`), which Starlette dispatches to its worker thread pool, so two genuinely concurrent HTTP requests that land on the same `(root, subscription-set)` cache key within the 30s window can now call `generate_plans()` on the *same* `PlanRepository` object from two OS threads at once. The attribute swap itself won't corrupt (CPython's GIL makes the assignment atomic), but the computation feeding it (`self._patch_targets()`, `self._configuration_assessments()`, network/vulnerability-service calls) is not synchronized, so a slower request's `replace_generation()` call can overwrite a faster, later request's more-current generation with stale data — a lost-update race that is new in this phase and is not mentioned in either plan's STRIDE threat register (T-03.2-05/06 only reason about single-writer tampering/DoS, not concurrent writers).
**Fix:** Add a lock around `replace_generation()` (and ideally around the read paths in `list()`/`get()` for a consistent snapshot), e.g.:
```python
def __init__(self, ...):
    ...
    self._lock = threading.Lock()

def replace_generation(self, plans: list[dict[str, Any]]) -> None:
    with self._lock:
        ...
        self._plans = tuple(copy.deepcopy(plans))
```
At minimum, add a concurrency-focused regression test (two threads calling `generate_plans()` on the same cached planner) before this ships to a multi-worker-thread deployment.
