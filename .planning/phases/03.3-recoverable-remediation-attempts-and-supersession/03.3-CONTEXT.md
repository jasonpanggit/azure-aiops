# Phase 03.3: Recoverable Remediation Attempts and Supersession - Context

**Gathered:** 2026-09-03
**Status:** Ready for planning
**Mode:** Autonomous decisions derived from Phase 03 deep review

<domain>
## Phase Boundary

Separate provider-submission safety accounting from ordinary execution attempts,
classify failures at the adapter boundary, and provide an audited supersession
path after an external blocker is resolved. This phase does not introduce the
background verification worker or change approval governance.

</domain>

<decisions>
## Implementation Decisions

### Submission Accounting
- Persist `provider_submitted` per attempt and derive the retry ceiling from submitted or submission-ambiguous attempts only.
- Validation, authorization, approval, target-precondition, and other proven pre-submission refusals do not consume the Azure submission budget.
- A transport failure after the provider request may have crossed the mutation boundary must fail closed as submission-ambiguous and consume budget until reconciled.

### Failure Classification
- Use a closed, machine-readable vocabulary: provider authorization, target precondition, provider transient, provider rejected, submission ambiguous, and internal/pre-submit validation.
- Preserve human-readable provider details while keeping eligibility decisions keyed to stable failure codes.
- Every terminal failed attempt must project a non-empty class-specific ineligibility reason.

### Supersession
- Supersession is explicit, authorized, and audited; it never mutates or deletes the old execution history.
- Require a fresh currently-approved plan snapshot and re-run eligibility before creating the replacement execution.
- Record bidirectional immutable lineage (`superseded_by` and `supersedes`) and an operator-supplied bounded reason.
- Refuse supersession for active executions or ambiguous provider submissions that could still be running.

### Compatibility and Safety
- Existing execution records default conservatively: a recorded provider job ID proves submission; otherwise legacy attempts remain pre-submission unless their status/details prove ambiguity.
- Keep ordinary retry idempotent and bounded.
- Do not use plan/action hash churn as a recovery mechanism.

### the agent's Discretion
- Exact schema version and whether supersession is represented by a dedicated store method or a constrained creation path may follow existing CAS patterns.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `RemediationExecutionStore` already provides durable CAS claims and append-only attempt history.
- `RemediationExecutionService` centralizes eligibility, retry, and action-family submission.
- `PatchExecutionUnavailable` and the Azure adapter are the existing provider-failure boundary.

### Established Patterns
- Provider work is never reported cancelled without a provider cancellation API.
- Retry must revalidate the current approved snapshot and target.
- Execution identity is permanent; replacement requires an explicit new lineage rather than state edits.

### Integration Points
- `src/operations/patching/azure_adapter.py` and `service.py` for provider classification.
- `src/intelligence/remediation/execution_store.py` for attempt schema and supersession lineage.
- `src/intelligence/remediation/execution_service.py` for retry budgets and eligibility.
- `src/api/routers/remediation.py` for the supersede route.
- Web controls are deferred to Phase 03.6, but API projections must expose the necessary fields.

</code_context>

<specifics>
## Specific Ideas

The key E2E-shaped regression is: repeated pre-submit 403/precondition
refusals leave the submission budget intact; after the external blocker is
fixed, an authorized supersede creates a linked replacement that can submit and
reach success without editing stored records.

</specifics>
