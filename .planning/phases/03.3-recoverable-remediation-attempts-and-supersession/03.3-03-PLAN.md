<objective>
Add the audited supersede capability: when an execution has exhausted its submission budget (or is otherwise terminally failed/cancelled) but is not ambiguous, an operator can create a brand-new, freshly-approved-and-revalidated execution that explicitly references the old one, without ever mutating the old execution's audit trail. This is the escape valve CONTEXT.md's Supersession decision and Recommendation 2's acceptance criteria describe: fixing an external blocker (like the live-evidence RBAC denial) must not require silently resetting or discarding the original attempt history.

Purpose: Plan 03.3-02 makes the three-attempt budget mean what it says (only real submissions count) -- but a real, persistent external blocker (e.g. genuine RBAC denial) can still legitimately exhaust it. CONTEXT.md is explicit that the fix is a new, audited execution, not raising the ceiling or mutating history.
Output: `execution_store.py` gains `create_superseding`; `execution_service.py` gains `supersede()` and `execution_view` projects supersede eligibility; `remediation.py` gains `POST .../supersede`; `web/src/lib/services.ts` gains the full set of new field projections plus a `supersede` client method; a new E2E-shaped regression test proves the whole "budget exhausted -> blocker fixed -> supersede -> succeed, old history untouched" story end-to-end.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Operator-supplied `reason` (POST body) -> stored `superseded_reason` | Free-text operator input, persisted verbatim into the audit trail; never interpolated into any Azure API call, file path, or query -- it is pure audit metadata. |
| POST /supersede -> re-run approval/target eligibility | The endpoint must not become a bypass of the approval workflow; it re-validates from scratch rather than trusting the old execution's already-approved status. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.3-05 | Elevation of Privilege | `RemediationExecutionService.supersede` | critical | mitigate | `supersede()` re-runs the exact same `_check_approval_gate`/`_validated_execution_snapshot`/`_resolve_target` calls `execute()` uses against a fresh plan lookup, rather than copying the old execution's already-approved snapshot forward; a plan whose approval was revoked since the original execution cannot be superseded. |
| T-03.3-06 | Tampering | operator-supplied `reason` field | medium | mitigate | Bounded length (`Field(min_length=1, max_length=500)`) at the Pydantic layer; stored only as opaque audit text, never parsed or interpolated into any downstream request, path, or query. |
| T-03.3-07 | Repudiation | `create_superseding`'s dual-record write | high | mitigate | Both the new record's creation and the old record's `superseded_by`/`superseded_reason` mutation happen under the store's single existing lock in one atomic call, so lineage can never be observed in a half-written state (new record visible without the old record pointing back, or vice versa). |
| T-03.3-08 | Denial of Service | repeated supersede chaining | low | mitigate | `superseded_by` is settable exactly once per record (CAS-checked in `create_superseding`); a second supersede attempt on an already-superseded record is rejected with `already_superseded`, bounding chain growth to one hop per exhausted execution rather than allowing unbounded churn. |

</threat_model>
