# Phase 03.3 Plan 02: Submitted-Attempt Counting Summary

**`execution_store.py`/`execution_service.py` now count only proven-or-ambiguous provider submissions against `MAX_EXECUTION_ATTEMPTS`, with `submitted_attempt_count` as the single shared source of truth for both `execution_view`'s read-side projection and `claim_retry`'s write-side CAS gate, plus a conservative legacy-compatible default for pre-migration records.**

## Performance

- **Duration:** ~25 min
- **Tasks:** 3/3 completed
- **Files modified:** 3 (2 source modules, 1 existing test file adjusted); 1 new test file (7 tests)

## Accomplishments

- `execution_store.py`: `_new_attempt` and `create_or_get`'s record dict literal both default to `provider_submitted=False, failure_class=""`; `_transition_locked`'s attempt-copy-through whitelist now includes `provider_submitted`/`failure_class`; new module-level `submitted_attempt_count(record) -> int` (counts only attempts with truthy `provider_submitted`) and `is_submission_ambiguous(record) -> bool` (Plan 03.3-03's supersede guard), both exported in `__all__`; `claim_retry`'s max-attempts CAS gate now checks `submitted_attempt_count(record) >= max_attempts` instead of raw `attempt_count`; `_with_defaults` backfills a conservative legacy default (`_legacy_provider_submitted`) for any pre-migration attempt missing the new keys, matching CONTEXT.md's Compatibility and Safety decision verbatim (provider_job_id present -> submitted; else an ambiguity marker in failure text -> submitted; else pre-submission); `_SCHEMA_VERSION` bumped `2.0.0` -> `2.1.0`.
- `execution_service.py`: `_submit_and_record`'s target-revalidation-failure except clause now persists `provider_submitted=False, failure_class="target_precondition"`; the adapter-exception except clause branches by type (`PatchValidationError` -> always `False`/`internal_validation`; `DefenderConfigurationUnavailable`/`PatchExecutionUnavailable` -> read directly off the caught exception with a fail-closed fallback); the success path persists `provider_submitted=True, failure_class=""`; `poll_verification`'s verifier-detected-failed branch adds `failure_class="provider_rejected"`; `execution_view` now derives `remaining_attempts`/`retryable` from `submitted_attempt_count(view)` and projects a new `submitted_attempt_count` field.
- New `tests/test_remediation_submission_accounting.py` (7 tests): repeated pre-submission refusals never consume budget (including a 4th retry after 3 pre-submission cycles, proving `claim_retry`'s own gate isn't fooled either); repeated submitted failures exhaust the budget and the 4th retry raises `max_attempts_exceeded`; two self-approval-guard refusals + one genuine submitted rejection leave `remaining_attempts == 2` (only the third counted) -- the exact live-evidence regression CONTEXT.md describes; a verifier-detected failure carries `failure_class == "provider_rejected"`; three legacy-record-shape tests (provider_job_id present, ambiguity marker present, neither present) proving the conservative default in all three directions.

## Decisions Made

- `PatchValidationError` is unconditionally `provider_submitted=False, failure_class="internal_validation"` since it structurally cannot fire after `self._adapter.submit()` is reached.
- `DefenderConfigurationUnavailable`/`PatchExecutionUnavailable` classification is read directly off the caught exception (Plan 03.3-01's contract), with the same fail-closed fallback (`True`/`submission_ambiguous`) the adapters' own constructors use, for defense in depth against a future adapter that forgets to classify.
- `poll_verification`'s verifier-detected-failed transition only adds `failure_class`, not `provider_submitted` -- the attempt was already marked submitted at the earlier "running" transition, and `_transition_locked`'s copy-through is additive (only overwrites keys present in the current call's `fields`), so no double-write or stale-overwrite risk.

## Deviations from Plan

- **Fix:** Updated the assertion to `remaining_attempts == 3` (the full budget remains available, since the cancelled attempt never touched Azure) with an explanatory comment.
