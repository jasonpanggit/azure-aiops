# Phase 03.3 Plan 03: Audited Supersession Summary

**A new `POST .../supersede` endpoint creates a freshly-approved, freshly-identified replacement execution for an exhausted-but-non-ambiguous record, with bidirectional immutable lineage, an atomic dual-record store write, and API/client contract projections -- closing Recommendation 2's escape valve.**

## Performance

- **Duration:** ~40 min
- **Tasks:** 3/3 completed
- **Files modified:** 6 (4 source modules, 1 web contract file, 1 existing test file); 1 new test file (8 tests)

## Accomplishments

- `execution_store.py`: new `create_superseding(old_execution_id, *, expected_revision, plan_id, requested_by, approved_by, execution_snapshot, rollback_guidance, scope_attributes, reason, now)` atomically (under the store's single lock, one write) CAS-validates the old record is still eligible, mints a new record with identity `f"{plan_id}|{snapshot_hash}|{action_version}|supersedes:{old_execution_id}"` (collision-proof even for a byte-identical snapshot), sets `supersedes` on the new record, and sets `superseded_by`/`superseded_reason` on the old record without touching its `attempts`/`history`. `_with_defaults` backfills `supersedes`/`superseded_by`/`superseded_reason` on every read; `create_or_get`'s record literal also carries these fields at creation time (fixing an exact round-trip mismatch caught by an existing test -- see Deviations).
- `execution_service.py`: new `supersede(execution_id, *, requested_by, reason)` -- validates a non-empty reason, checks eligibility via the new shared `_supersede_eligibility(record)` helper, fetches the current plan, re-runs the *fresh* `_check_approval_gate`/`_validated_execution_snapshot`/`_resolve_target` (never reusing the old execution's approved snapshot), calls `store.create_superseding(...)`, transitions the new record to `running`, and reuses `_submit_and_record` unchanged. `execution_view` now projects `supersedable`/`supersede_ineligibility_reason` from the same shared helper.
- `api/models.py` gains `SupersedeExecutionRequest(ApiModel)` (`reason: str = Field(min_length=1, max_length=500)`); `api/routers/remediation.py` gains `POST /api/v1/remediation/executions/{execution_id}/supersede`, mirroring `retry_execution`'s exact narrow-then-resolve structure, mapping `RemediationExecutionError` reasons to `NOT_FOUND`/`INVALID_REQUEST`/`CONFLICT` and adapter exceptions to `PROVIDER_UNAVAILABLE`.
- `web/src/lib/services.ts`: `RemediationExecutionAttempt` gains `provider_submitted`/`failure_class`; `RemediationExecution` gains `provider_submitted`/`failure_class`/`submitted_attempt_count`/`supersedes`/`superseded_by`/`superseded_reason`/`supersedable`/`supersede_ineligibility_reason`; `remediationApi.supersede(executionId, reason, scope?)` added. `page.tsx`/`page.test.tsx` confirmed untouched (`git diff --stat` empty) -- UI wiring deferred to Phase 03.6 per plan scope.
- New `tests/test_remediation_execution_supersede.py` (8 tests): one full router-level E2E supersede (Task 1); five service-level eligibility-guard/edge-case tests (active execution refused, submission-ambiguous refused, already-superseded refused, second supersede call hits the store CAS check rather than creating a third record, `execution_view`'s `supersedable`/`supersede_ineligibility_reason` agreeing with `supersede()`'s own decision for both an eligible and an active execution) (Task 2); one full CONTEXT.md-narrative E2E regression (budget exhausted -> retry refused -> blocker fixed -> supersede succeeds -> old history provably untouched -> bidirectional lineage) (Task 3). Two new router-level tests added to `tests/test_api_remediation_execution.py` (response includes `supersedes`; out-of-scope caller gets 404).

## Decisions Made

- `SupersedeExecutionRequest` uses `ApiModel` (the shared `extra="forbid"` wire-model base every other request body in this codebase uses), not a bare inline `pydantic.BaseModel` as the plan's literal text suggested -- consistent with `RemediationDecisionRequest` and every other request DTO, and a stronger contract (rejects unknown fields) than the plan's minimum requirement.
- The route uses `status_code=202`, matching `execute_plan`/`retry_execution`'s existing convention (an accepted request whose result -- success or failure -- resolves synchronously in the response body); the plan's Task 1 `<behavior>` text mentioned 200/201, but the plan's own `<action>` instruction to mirror `retry_execution`'s "exact structure" produces 202, and 202 is what every other write endpoint in this router already returns.
- `supersede()`'s eligibility guard is checked in the service (fast, specific error before ever touching the store) and re-checked atomically by the store's own CAS in `create_superseding` (defense in depth against a race between two concurrent supersede calls on the same execution).

## Deviations from Plan

**1. [Rule 1 - Bug] Added `supersedes`/`superseded_by`/`superseded_reason` to `create_or_get`'s record literal (not just `_with_defaults`)**
- **Found during:** Full regression run after Task 1/2 implementation (`tests/test_remediation_execution_service.py::test_execution_store_persists_record_surviving_round_trip` failed: a freshly-created record round-tripped through disk gained 3 extra keys it didn't have before the write).
- **Issue:** The plan's Task 1 action only specified adding these fields via `_with_defaults` (the read-side backfill for pre-migration records) and via `create_superseding`'s new-record literal, but did not mention `create_or_get`'s existing record literal -- the ordinary (non-superseding) execution-creation path. This caused every *new* record's in-memory shape (immediately after `create_or_get`) to differ from its shape after one write/read round-trip (`_with_defaults` adding the three keys on read), breaking an existing byte-for-byte equality test and, more importantly, meaning a freshly created record's caller-visible shape was inconsistent with its own persisted shape.
- **Fix:** Added `"supersedes": "", "superseded_by": "", "superseded_reason": ""` to `create_or_get`'s record dict literal, matching the same fields already present in `create_superseding`'s new-record literal.
- **Files modified:** `src/intelligence/remediation/execution_store.py`
- **Commit:** uncommitted (working-tree only)

No other deviations beyond the two documented in "Decisions Made" above (SupersedeExecutionRequest base class, 202 status code), both of which follow established codebase convention more closely than the plan's literal text and do not change the plan's functional contract.
