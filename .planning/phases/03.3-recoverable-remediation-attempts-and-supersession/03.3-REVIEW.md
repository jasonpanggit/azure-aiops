## Critical Issues (all resolved — see Final Re-Review Summary above)

### CR-01 [RESOLVED 2026-09-04]: `retry()` never checks `is_submission_ambiguous`, so an operator (or any future automated retry) can fire a second concurrent Azure request while the first submission-ambiguous attempt may still be running

**File:** `src/intelligence/remediation/execution_service.py:399-483` (`retry`); contrast with `:1011-1029` (`_supersede_eligibility`); `src/intelligence/remediation/execution_store.py:660-671` (`is_submission_ambiguous`)

**Issue:** `is_submission_ambiguous(record)` exists specifically to express "the mutating call's outcome is unknown because the transport failed after the request may have already reached Azure — it may still be executing" (its own docstring, `execution_store.py:663-666`). Plan 03.3-03 wires this into `_supersede_eligibility` (`execution_service.py:1028`) so `supersede()` refuses an ambiguous execution (`test_supersede_refuses_a_submission_ambiguous_execution`). But `retry()` — the ordinary, far-more-commonly-reached recovery path that every operator uses first — has no equivalent guard. `retry()`'s only gates are `status in {"failed","cancelled"}` and `submitted_attempt_count(record) >= max_attempts` (`execution_store.py:314`, `claim_retry`'s CAS). An execution whose single attempt failed as `submission_ambiguous` is `status == "failed"` and has `submitted_attempt_count == 1 < 3`, so `retry()` happily reclaims it and calls `_submit_and_record` again — issuing a **second, genuinely concurrent** `installPatches`/Defender-configuration PUT request against the same target while the first request's true outcome (accepted-and-running vs. never-arrived) is still unknown. This is precisely the double-mutation hazard (e.g., two concurrent patch installs/reboots on one production host) that `provider_submitted`/`failure_class="submission_ambiguous"` was introduced to make *visible* — but visibility without a corresponding refusal in the path operators actually use does not prevent the hazard.

I reproduced this directly against the real `RemediationExecutionService`/`RemediationExecutionStore` (adapter raises `PatchExecutionUnavailable(..., provider_submitted=True, failure_class="submission_ambiguous")` on every call):

```
execute status failed
is_submission_ambiguous after 1st attempt: True
adapter calls so far: 1
retry status failed
adapter calls after retry: 2          # <-- second live-shaped call fired immediately
supersedable (correctly refused): False submission_ambiguous
retryable (NOT refused): True
```

No test in `tests/test_remediation_submission_accounting.py` or `tests/test_remediation_execution_supersede.py` exercises "retry immediately after a submission-ambiguous failure," which is why this was not caught by the phase's own verification (`03.3-VERIFICATION.md`'s 17 truths cover supersede's ambiguity refusal but never claim retry is guarded the same way).

CONTEXT.md's own Submission Accounting decision reads: *"...must fail closed as submission-ambiguous and **consume budget until reconciled**."* "Until reconciled" only has teeth if something actually withholds further submission attempts pending reconciliation; today nothing does for `retry()`.

**Fix:** Apply the same shared guard `retry()` already has the pieces for:
```python
# execution_service.py, inside retry(), immediately after the existing
# status-in-{"failed","cancelled"} check:
if is_submission_ambiguous(record):
    raise RemediationExecutionError(
        "This execution's last attempt may still be running against the "
        "provider; retry is refused until it is reconciled or superseded",
        reason="submission_ambiguous",
        details={"execution_id": execution_id},
    )
```
`is_submission_ambiguous` is already imported into `execution_service.py` for `_supersede_eligibility`, so this is a same-module, already-available call. If immediate reconciliation genuinely belongs to Phase 03.4 (the deferred verification worker), then until that worker exists, the only currently-safe recovery for an ambiguous execution should be `supersede()` (which already refuses it too, forcing an explicit operator decision) — not silently permitting `retry()` to double-submit. `execution_view`'s `retryable`/`ineligibility_reason` projection should also reflect this so the API/web contract cannot report `retryable: true` for an ambiguous record.

## Warnings (all resolved — see Final Re-Review Summary above)

### WR-01 [RESOLVED 2026-09-04]: `create_superseding` does not enforce the store's `max_executions` capacity guard that `create_or_get` enforces

**File:** `src/intelligence/remediation/execution_store.py:91-153` (`create_or_get`, has the guard) vs `:176-275` (`create_superseding`, does not)

**Issue:** `create_or_get` explicitly bounds store growth: `if len(state["executions"]) >= self.max_executions: raise ValueError("Remediation execution store is full")` (default `max_executions=5000`, `:70`). `create_superseding` appends a brand-new record (`state["executions"].append(new_record)`, `:262`) under the exact same lock, with no equivalent check. Every legitimate supersede requires exhausting a real 3-attempt budget first, so this is not a trivially cheap attack, but it is a real, silent gap in an invariant this same class already enforces elsewhere: an operator (or a buggy/looping client retrying `supersede` calls across many distinct exhausted executions) can grow the store past the configured cap that `create_or_get` would otherwise refuse to exceed, defeating the purpose of the cap (bounding JSON file size, write cost, and lock-hold duration for every other caller).

**Fix:**
```python
# create_superseding, immediately after the old_record eligibility check,
# before minting new_record:
if len(state["executions"]) >= self.max_executions:
    raise ExecutionClaimConflict("execution_store_full", old_record)
```

### WR-02 [RESOLVED 2026-09-04]: `supersede()` resolves the target twice — once explicitly, once again inside `_submit_and_record` — with no test or comment establishing this is intentional

**File:** `src/intelligence/remediation/execution_service.py:546-547` (`supersede()`'s explicit `self._resolve_target(plan, decision)` call) vs `:262` (`_submit_and_record`'s own `self._resolve_target(plan, decision)` call, reached immediately afterward via `self._submit_and_record(plan=plan, decision=decision, ...)`)

**Issue:** `execute()` and `retry()` each call `_resolve_target` exactly once (inside `_submit_and_record`). `supersede()` calls it once explicitly before `create_superseding` (to satisfy "re-run target-eligibility checks fresh... before creating the replacement execution") and then a second time when `_submit_and_record` runs its own internal `_resolve_target(plan, decision)` immediately after. Both calls read the same `(plan, decision)` pair back-to-back with no intervening store mutation, so today this is provably harmless (verified: no exception is swallowed between the two calls, and the second call's result is the one that actually reaches the adapter). But it is wasted work with no test asserting it's needed twice, and it creates a latent trap: if `_resolve_target` (or anything it calls, e.g. `self._patching.target(target_id)`) ever gains a side effect, becomes non-deterministic, or is changed to consult live/mutable inventory, the two calls could silently diverge — the snapshot persisted by `create_superseding` would then not match what `_submit_and_record` actually validates against moments later.

**Fix:** Remove the explicit `self._resolve_target(plan, decision)` call from `supersede()` (line 547) — `_check_approval_gate` and `_validated_execution_snapshot` already provide the "fresh approval" revalidation this method's docstring promises, and `_submit_and_record`'s own call is the one whose result is authoritative. If the explicit call was added specifically to fail fast *before* minting a new execution record (so an ineligible target never gets a wasted execution_id), replace it with a comment saying so and add a regression test that proves the two calls cannot diverge (or accept the current risk explicitly).

## Info (all resolved — see Final Re-Review Summary above)

### IN-01 [RESOLVED 2026-09-04]: The legacy `provider_submitted` backfill heuristic is coupled to exact adapter message wording by convention only, with no test tying the two together

**File:** `src/intelligence/remediation/execution_store.py:748` (`_AMBIGUITY_MARKERS`) vs `src/operations/patching/azure_adapter.py:172-179`, `src/operations/defender_configuration.py:238-248` (the `f"Azure Resource Manager was unreachable: {exc}"` message templates the markers are designed to match)

**Issue:** `_legacy_provider_submitted` conservatively treats a pre-migration attempt as submitted only if its `failure_details`/`message` contains one of `("unreachable", "timed out", "timeout", "connection", "ambiguous")`. This works today because both real transport-failure raise sites hard-code the literal word "unreachable" in their message. But nothing enforces that coupling: a future wording change to either message (e.g., rephrasing "was unreachable" to "could not be reached") would silently make `_legacy_provider_submitted` misclassify *future* pre-2.1.0-shaped legacy attempts as pre-submission (the safe-for-new-records direction is moot since new records always carry the real field explicitly; the risk is purely for records written between now and whenever such a wording change lands, then read back after it). No test asserts the marker list stays a superset of what the adapters' own transport-failure messages actually contain.

**Fix:** Add a small cross-module test (or a shared constant) asserting the literal adapter transport-failure message text contains at least one of `_AMBIGUITY_MARKERS`, so a future wording change fails CI instead of silently degrading legacy-record accuracy.

### IN-02 [RESOLVED 2026-09-04]: No regression test exercises "retry immediately after a submission-ambiguous failure"

**File:** `tests/test_remediation_submission_accounting.py`, `tests/test_remediation_execution_retry.py`

**Issue:** This exact gap is what let CR-01 ship unnoticed — every existing submission-accounting/supersede test either (a) exhausts the budget with non-ambiguous `provider_authorization` rejections, or (b) tests that *supersede* refuses an ambiguous record, but none tests that *retry* does (or currently, does not) refuse one.

**Fix:** Once CR-01 is fixed, add `test_retry_refuses_a_submission_ambiguous_execution` (mirroring `test_supersede_refuses_a_submission_ambiguous_execution`) asserting `service.retry(execution_id)` raises `RemediationExecutionError(reason="submission_ambiguous")` and that the adapter's `submissions` list length does not grow.
