<objective>
Classify every failure the Azure patch adapter and the Azure Defender-configuration adapter can raise with two new orthogonal signals: whether the mutating call is proven to have reached Azure (`provider_submitted`), and *why* it failed, using the closed six-value vocabulary from CONTEXT.md (`provider_authorization`, `target_precondition`, `provider_transient`, `provider_rejected`, `submission_ambiguous`, `internal_validation`). This is the adapter boundary the phase's Failure Classification and Submission Accounting decisions (D: Submission Accounting, D: Failure Classification) depend on -- later plans read these two fields off the caught exception to decide whether an attempt consumes the Azure submission budget. No execution-store or execution-service behavior changes here; this plan only makes the two real ARM-calling adapters tell the truth about what they know.

Purpose: Live evidence (`.planning/debug/remediation-e2e.md:2026-09-03T19:05`) proved a genuine Azure ARM 403 rejection still returns `provider_job_id=""`, so `provider_job_id` presence can no longer be trusted as a proxy for "did this reach Azure". The adapter is the only place that actually knows whether its own mutating HTTP call was attempted, so classification has to happen there, not be inferred later from an empty job id.
Output: `PatchExecutionUnavailable` and `DefenderConfigurationUnavailable` both carry `.provider_submitted: bool` and `.failure_class: str`, set correctly at every raise site in `azure_adapter.py` and `defender_configuration.py`, backed by a shared `classify_azure_response_failure(status_code) -> str` helper.
</objective>

| T-03.3-01 | Tampering | AzureArmPatchExecutionAdapter._post / AzureArmDefenderConfigurationAdapter._request, _raise_for_status | medium | mitigate | `failure_class`/`provider_submitted` are derived only from the HTTP status code and exception type, never from response body content, so a compromised or spoofed Azure response body cannot inject an attacker-chosen classification; the response body remains used only for the existing truncated human-readable message. |
