# Phase 03.3 Plan 01: Provider Failure Classification Summary

**Both real Azure-calling adapters now classify every raise with `provider_submitted`/`failure_class` from a closed six-value vocabulary, backed by one shared `classify_azure_response_failure(status_code)` helper -- the adapter-boundary foundation Plan 03.3-02's submission-accounting logic reads directly off the caught exception.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 3/3 completed
- **Files modified:** 5 (2 adapter source modules, 1 shared adapters module, 2 test files)

## Accomplishments

- `PatchExecutionUnavailable.__init__` (`operations/patching/adapters.py`) and `DefenderConfigurationUnavailable.__init__` (`operations/defender_configuration.py`) both gained `provider_submitted: bool = True` and `failure_class: str = "submission_ambiguous"` keyword-only parameters with identical fail-closed defaults.
- New `classify_azure_response_failure(status_code: int) -> str` in `operations/patching/azure_adapter.py`: `provider_authorization` for 401/403, `provider_transient` for 429/5xx, `provider_rejected` for every other >=400. Exported in `__all__` and imported by `defender_configuration.py` (no new dependency edge -- that module already imports `ARM_ENDPOINT`/`ARM_SCOPE`/`TokenCredential` from the same source).
- `AzureArmPatchExecutionAdapter._post`'s single mutating POST boundary: `httpx.HTTPError` -> `provider_submitted=True, failure_class="submission_ambiguous"`; `response.status_code >= 400` -> `provider_submitted=True, failure_class=classify_azure_response_failure(...)`.
- Every pre-submission raise site in `azure_adapter.py` (`_token`'s two raises, `_install_patches_body`'s empty-selection raise, `_install_patches_request`'s/`_node_image_request`'s unsupported-inventory-kind and missing-node-pool raises, `_require_resource_id`'s two raises) now explicitly sets `provider_submitted=False` with a specific `failure_class` (`provider_authorization`, `internal_validation`, or `target_precondition`).
- `AzureArmDefenderConfigurationAdapter` mirrors the same contract across its GET (`inspect()`) vs PUT (`submit()`) boundary: `_request`'s `httpx.HTTPError` branch distinguishes by `method` (PUT -> submitted/ambiguous, GET -> not-submitted/provider_transient); `_raise_for_status` classifies by `operation` (`"update"` -> submitted + shared classifier, `"read"` -> not-submitted + shared classifier); `submit()`'s two pre-PUT precondition raises (state_hash/etag drift) and `_validated_snapshot_request`'s two raises (unsupported action, altered/tampered request) are all `provider_submitted=False, failure_class` in `{target_precondition, internal_validation}`; `UnconfiguredDefenderConfigurationAdapter`'s two raises and `inspect()`'s invalid-JSON/non-dict raises are `provider_submitted=False, failure_class="internal_validation"`.
- 18 new/extended assertions across `tests/test_patching_azure_adapter.py` (24 total tests, was 18) and `tests/test_defender_configuration_execution.py` (19 total tests, was 15), covering every classification path named in the plan plus the additional `_validated_snapshot_request`/state-hash-drift pre-submission cases.

## Decisions Made

- Constructor defaults for both exception types are fail-closed (`provider_submitted=True, failure_class="submission_ambiguous"`) so any future unclassified raise still consumes the retry budget rather than silently exempting itself (T-03.3-02 mitigation).
- Classified `_validated_snapshot_request`'s two raises (called directly inside `AzureArmDefenderConfigurationAdapter.submit()`, before any HTTP call) as `provider_submitted=False, failure_class="internal_validation"` even though the plan's Task 3 action text did not name this specific helper by name. This fires within the same `submit()` call chain the plan explicitly scopes, and Plan 03.3-02's second `except` clause reads `provider_submitted`/`failure_class` directly off whatever `DefenderConfigurationUnavailable` `self._defender_configuration.submit(...)` raises -- leaving it at the fail-closed default would have incorrectly consumed the Azure submission budget for a tampered/invalid snapshot that never reached Azure, directly violating CONTEXT.md's Submission Accounting decision ("validation... refusals do not consume the Azure submission budget"). Documented as a deviation below.
- `build_defender_configuration_snapshot`/`_plan_target_id`/`_validate_scope`'s raises were deliberately left unclassified (default `provider_submitted=True`). These are never called from within `AzureArmDefenderConfigurationAdapter.submit()`'s chain -- only from `_resolve_target` (which unconditionally reclassifies any `DefenderConfigurationUnavailable` as `target_precondition`/`False` regardless of the inner exception's own attributes, per Plan 03.3-02 Task 1) and from preview/approval-snapshot-building code paths outside the submission-accounting flow. Their default attributes are inert for accounting purposes.

## Deviations from Plan

**1. [Rule 1 - Bug] Classified `_validated_snapshot_request`'s two raises (not explicitly named in Task 3's action text)**
- **Found during:** Task 3, while grepping every `raise DefenderConfigurationUnavailable(` call site per the plan's own `<verification>` instruction ("confirm each one explicitly passes `provider_submitted=`... except the two Unconfigured*/Unconfigured... sites and the shared `_post`/`_request` transport/status branches").
- **Issue:** `_validated_snapshot_request` is called directly inside `AzureArmDefenderConfigurationAdapter.submit()`, strictly before `self.inspect()`/`self._request("PUT", ...)`. Its two raises (unsupported action id, altered/tampered request) are proven pre-submission by construction -- exactly the class of refusal CONTEXT.md's Submission Accounting decision says must not consume budget -- but the plan's Task 3 action text enumerated only `submit()`'s two precondition raises (state_hash/etag) and did not name this helper.
- **Fix:** Added `provider_submitted=False, failure_class="internal_validation"` to both raises, matching the semantics of `inspect()`'s invalid-JSON/non-dict raises (a response/request-shape problem, never a mutation).
- **Files modified:** `src/operations/defender_configuration.py`
- **Commit:** uncommitted (working-tree only)

No other deviations. All other `<action>` instructions in Tasks 1-3 were implemented exactly as specified, including exact helper names, keyword-argument names, and classification values.
