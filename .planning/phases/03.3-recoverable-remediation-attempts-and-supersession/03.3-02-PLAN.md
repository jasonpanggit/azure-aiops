<objective>
Make the execution store and execution service actually count only proven-or-ambiguous provider submissions against `MAX_EXECUTION_ATTEMPTS`, using the `provider_submitted`/`failure_class` signal Plan 03.3-01 added to the two adapter exceptions. This is the core of Recommendation 2: today `attempt_count` (every attempt, including refusals that never touched Azure) drives the retry ceiling; after this plan, a new `submitted_attempt_count` derived from each attempt's own `provider_submitted` flag drives it instead, while `attempt_count`/`attempts` keep recording every attempt for audit purposes unchanged.

Purpose: Live evidence showed two self-approval-guard refusals (never reached Azure) and one genuine Azure 403 (did reach Azure, still `provider_job_id=""`) consumed the same three-attempt budget, permanently blocking the remediation the moment the external RBAC blocker was fixed. This plan closes exactly that gap.
Output: `execution_store.py` gains `submitted_attempt_count`/`is_submission_ambiguous` helpers, a legacy-compatible default for pre-existing records, and a `claim_retry` gate keyed on submitted attempts; `execution_service.py`'s `_submit_and_record` classifies every pre-submission and adapter-boundary failure onto the current attempt; `execution_view` projects `remaining_attempts`/`retryable` from the new count.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Persisted execution-store JSON -> `_with_defaults` | On-disk records written by an older schema version are untrusted relative to the new field contract; `_with_defaults` is the sole point where legacy data is normalized before any counting logic sees it. |
| Caught adapter exception -> `_submit_and_record` | `provider_submitted`/`failure_class` read off a caught exception via `getattr(..., default)` are trusted only as far as Plan 03.3-01 guarantees; this plan's fail-closed defaults (`True`/`submission_ambiguous`) apply if that contract is ever violated by a future adapter. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.3-03 | Elevation of Privilege | `_with_defaults`' legacy `provider_submitted` backfill | high | mitigate | The ambiguity-marker match is a substring check over `failure_details`/`message`, which is server-authored text (never raw user input), so an operator cannot forge an unlimited-retry legacy record by crafting a message; the check only ever narrows (marks as submitted, i.e. more conservative), never grants extra unearned attempts. |
| T-03.3-04 | Denial of Service | `claim_retry`'s submitted-attempt CAS gate | low | accept | A persistent external blocker that always returns a submitted failure (e.g. a permanent RBAC denial) legitimately exhausts the budget after three real attempts; this is the correct, intended behavior (Recommendation 2's whole point is a *bounded* budget) and is resolved via supersede in Plan 03.3-03, not by loosening this gate. |
