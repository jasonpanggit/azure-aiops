## Why This Plan Exists

`remediation_planning_snapshot()` in `src/fabric/sync_service.py` reads `silver/remediation_action_catalog` and `silver/remediation_approval_policies`. A repository-wide search finds those table names in only three places: the schema registry, that reader, and test fixtures. Nothing writes them. `RemediationOpportunityEngine.identify()` iterates `self.catalog`; with an empty catalog it returns an empty list, so `RemediationGenerator` produces no plans and the Remediation page shows no recommendations, regardless of how well the Defender correlation works.

Research flagged this as assumption A3 with a high downside if descoped. The planner decision recorded in `02-02-PLAN.md` is that it is in scope here.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Catalog author -> governed catalog content | Authored content becomes the only source of proposed remediation steps. |
| Seeder -> Silver Delta tables | A write path into governed configuration data. |
| Catalog content -> generated plan steps | Anything in the catalog is surfaced to approvers as a proposed action. |
