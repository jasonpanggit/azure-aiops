<objective>
Fix startup readiness at its root by making `ProviderRuntime._refresh_locked` process all scheduled required providers before scheduled optional providers, while keeping insertion order stable within each class and preserving the existing serialized refresh, publication, retry, and readiness contracts.

Purpose: Optional Fabric-heavy loaders currently can run before required `exposure_query` and MAF Copilot loaders, leaving the process unready even though the required providers have not yet been attempted. Required-first scheduling lets required capabilities publish promptly without hiding required failures or conflating liveness with readiness.

Output: One surgical runtime ordering change, deterministic provider/runtime/HTTP regressions, full affected validation, and a pushed PR to `main`.
</objective>

<edge_cases>
- No scheduled providers: refresh skips provider work and retains existing metadata/health behavior.
- Only required or only optional scheduled providers: insertion order is unchanged.
- A required provider is configured false: it is still attempted in the required partition and `_refresh_provider` preserves the existing disabled-state handling.
- A required loader fails: later required providers are still attempted because `_refresh_provider` contains the exception and records unavailable/degraded state.
- A required provider has a retry window or unchanged cache key: its existing skip behavior remains intact and does not alter ordering of other scheduled providers.
- Deferred providers remain deferred even when marked required because `scheduled=False` remains the outer eligibility condition.
- Optional work blocks after required publication: `/health` reads the current snapshot immediately and `/ready` uses the existing non-blocking refresh call.
</edge_cases>
